# Component: operation

## 📌 Purpose & Scope

- **Core Responsibility:** Owns the *physical rail-network reference data* — the canonical registry of transit `Line`s, `Station`s, rolling-stock `Vehicle`s (and their `VehicleType`s), and station-level `Asset`s (lifts/escalators). It is the shared spine that every other domain app (spotting, incident, chartography, reporting, telegram) points its foreign keys at, plus it exposes read-only analytics (spotting/status trends) derived by joining that reference data against event data owned elsewhere.
- **Domain/Layer:** Django business-logic + persistence layer (GIS-enabled), surfaced through two interfaces: a Strawberry GraphQL read API and a small DRF `APIView` set for CSV/JSON chart feeds. No write path exists in GraphQL — mutations are deliberately stubbed out.

## 🔌 Interface & Data Flow

### Inputs (GraphQL arguments, filters, orderings)

Root query fields are contributed by `OperationScalars` (mixed into `rosak.schema.Query`): `lines`, `stations`, `stationLines`, `vehicles`, `vehicleTypes`, `assets`.

| Filter (`operation/schema/filters.py`) | Notable inputs |
| --- | --- |
| `LineFilter` | `id`, `code`, `display_name`/`display_color` via `FilterLookup[str]` |
| `StationFilter` | `display_name`, nested `line` / `station_line`, plus a custom **geospatial** `location` filter taking JSON `{x, y, z, radius}` → `location__distance_lt` with `Distance(km=…)` |
| `StationLineFilter` | `display_name`, `internal_representation`, nested `station`/`line` |
| `VehicleFilter` | `id`, `status` (reused by `spotting` and `incident` filters) |
| `VehicleTypeFilter` | custom `line_id` resolver → `Q(vehicles__vehicle_lines__id=value)` |
| `AssetFilter` | `id`, `asset_type`, `officialid`, nested `station` |

- Ordering: `VehicleOrder` (`id`, `identification_no`, `status`, `in_service_since`).
- Field-level arguments: `Line.vehicles(spotted_today: Boolean)`, `Vehicle.spottingCount(after, before)`, and the trend resolvers `Line.vehicle_spotting_trends(...)` / `Vehicle.spotting_trends(...)` taking `start`, `end`, `date_group: DateGroupings`, `type_group`, `free_range`, `add_zero`.
- REST inputs are URL path params only (`line_id`, `vehicle_id`, `source_str`, `start_date`, `end_date`) — see `operation/urls.py`, mounted at `/operation/`.
- **Input types:** `operation/schema/inputs.py` is entirely commented out (`LineInput`, `AssetInput`, `StationInput`, and their `*PartialInput` variants). `operation/schema/mutations.py` is an empty file and `OperationMutations` is a `pass`-body class. Writes happen exclusively via Django admin or other apps' tasks.
- **Signals:** none defined. Change tracking is instead done declaratively via `simple_history.HistoricalRecords()` on `Vehicle` and `Asset` (see migration `0017_historicalvehicle_historicalasset`).

### Outputs (GraphQL types, REST payloads)

- **Strawberry types** (`operation/schema/scalars.py`): `Line`, `Station`, `StationLine`, `Vehicle`, `VehicleType`, `Asset`. Computed/aggregate fields worth naming:
  - `Line.vehicle_types`, `Line.vehicles(spotted_today)`, `Line.chartography_sources` (walks `LineVehicleStatusCountHistory` → `Snapshot` → `Source`), `Line.vehicle_spotting_trends`, `Line.calendar_incidents`.
  - `VehicleType` exposes seven per-status counters (`vehicle_status_in_service_count`, `…_not_spotted_…`, `…_out_of_service_…`, `…_decommissioned_…`, `…_married_…`, `…_testing_…`, `…_unknown_…`) plus `vehicle_total_count` — one field per `VehicleStatus` member, hand-written rather than generated.
  - `Vehicle.last_spotting_date`, `Vehicle.spottingCount`, `Vehicle.spottings`, `Vehicle.incidents`, `Vehicle.incident_count`, `Vehicle.can_expand` (UI affordance: true when the row has any incident or spotting), `Vehicle.spotting_trends`.
- **Plain types** (`operation/schema/types.py`): `LineVehicleSpottingTrend`, `VehicleSpottingTrend` — flat time-bucket rows carrying `date_key`, `year/month/day`, `day_of_week`, `week_of_month`, `week_of_year`, `is_last_day_of_month`, `is_last_week_of_month`, `count`, `event_type` (and the `Vehicle` for the line variant).
- **REST views** (`operation/views.py`): `LineVehiclesSpottingTrend` returns a **CSV** body (built with `polars`), `LineVehiclesStatusTrendCount` and `VehicleSpottingTrend` return JSON. The last also returns a `mappings.yearWeek` index dictionary for chart axis compaction.
- **Celery:** the app emits no tasks of its own and has no `tasks.py`; it is a *consumer-side dependency* of `chartography.tasks.aggregate_line_vehicle_status_*` and `spotting.tasks.report_spotting_today` (both scheduled in `rosak/celery.py`).

### Dependencies

- **Third-party:** `django.contrib.gis` (PointField, `Distance`), `django-colorfield` (`ColorField`), `django-choices-field` (`TextChoicesField`), `django-model-utils` (`TimeStampedModel`), `django-simple-history`, `django-advanced-filters`, `django-ordered-model`, `strawberry-django`, `polars`, `pendulum`, DRF.
- **Imports *from* other apps:** `common.Media` (M2M through tables), `common.utils.get_trends` / `get_default_start_time`, `incident.CalendarIncident` + `incident.models.VehicleIncident` + `incident.admin` inlines, `spotting.models.Event` + `spotting.enums`, `chartography.models` (`Source`, `Snapshot`, `LineVehicleStatusCountHistory`) + `chartography.schema.scalars.Source`, `generic.schema.enums.DateGroupings`, `generic.schema.scalars.GeoPoint`, `generic.views.GeometricForm`.
- **Imported *by* (reverse deps — this app is the hub):** `incident` (FKs to `Line`/`Vehicle`/`Station`; reuses `StationFilter`/`VehicleFilter` and `Line`/`Station`/`Vehicle` scalars), `spotting` (FKs to `Vehicle`, two FKs to `Station`; reuses `VehicleFilter`, `StationLine`), `chartography` (FKs to `Line`, imports `VehicleStatus`), `reporting` (FK to `Asset`, reuses the `Asset` scalar), `common` (`operation.models`, `Vehicle` scalar), `telegram_provider` (`Line`, `Vehicle`, `VehicleLine`, `VehicleStatus`), and `rosak.schema` / `rosak.context` for wiring.

## ⚙️ Internal State & Logic

- **Models** (`operation/models.py`): `Line`, `Station`, `StationMedia`, `StationLine`, `Asset`, `AssetMedia`, `Vehicle`, `VehicleLine`, `VehicleType`. Most inherit `TimeStampedModel`; `Vehicle`, `VehicleLine`, `VehicleType`, and the two media join tables are plain `models.Model`.
- **Relationship shape:** `Line ↔ Station` many-to-many *through* `StationLine`; `Line ↔ Vehicle` many-to-many *through* `VehicleLine`; `Vehicle → VehicleType` FK; `Asset → Station` FK; `Station`/`Asset` → `common.Media` through `StationMedia`/`AssetMedia`; `Line → incident.CalendarIncident` direct M2M (auto join table, `through` intentionally left commented).
- **Enums** (`operation/enums.py`): `AssetType` (ESCALATOR, LIFT), `AssetStatus`, `VehicleStatus` (7 members incl. the domain-specific `MARRIED` = coupled unit), `LineStatus` (incl. `PARTIAL_ACTIVE`, `PARTIAL_DISRUPTION`, `TOTAL_DISRUPTION`), `WheelStatus` (FRESH → WORN_OUT). Only `Line.status` and `Vehicle.wheel_status` use `TextChoicesField`; `Vehicle.status`, `Asset.status`, `Asset.asset_type` use plain `choices=`, so the enum is not exposed as a GraphQL enum uniformly.
- **Integrity rules** are pushed into the DB rather than Python: unique constraints on `Line.code`/`display_name`, `Station.display_name`, `(station, line)`, `(line, internal_representation)`, `(vehicle, line)`, `(identification_no, vehicle_type)`, plus a *conditional* unique index on `StationLine.internal_representation` that an operator can opt out of per-row via `override_internal_representation_constraint`. `BTreeIndex` is declared on most searchable text columns. Deletes are `PROTECT` on reference edges and `CASCADE` only on `VehicleLine`.
- **Request-scoped state:** ten `DataLoader`s in `OperationContextLoaders` (`operation/schema/loaders.py`) — `vehicle_from_vehicle_type_loader`, `vehicle_type_from_line_loader`, `vehicle_from_line_loader`, `vehicle_status_count_from_vehicle_type_loader`, `vehicle_count_from_vehicle_type_loader`, `last_spotting_date_from_vehicle_loader`, `spotting_count_from_vehicle_loader`, `spottings_from_vehicle_loader`, `incident_from_vehicle_loader`, `incident_count_from_vehicle_loader`. `rosak/context.py` `copy.deepcopy`s the dict per request so caches never leak across requests. The count loaders batch by collapsing N keys into a single `aaggregate()` call with one `Count(filter=…)` annotation per key — clever, but it makes the key part of an SQL alias, and `batch_load_spotting_count_from_vehicle` aliases only on `key[0]` while the key is `(vehicle_id, Q)`, so two different date-window filters for the same vehicle in one request will collide.
- **Known rough edges:** `batch_load_vehicle_from_line` reads `keys[0][1]` and assumes every key in the batch shares the same `spotted_today` value (documented in-code); `VehicleType` scalar declares `info: str` though the model field is `description`; `Asset` / `StationLine` scalars declare plural `stations` / `lines` list fields over singular FKs; `LineAdmin` defines `list_editable` twice (the second assignment wins, dropping `status` from inline editing).
- **Schema evolution** (17 migrations, `operation/migrations/`): initial model set → `VehicleLine` M2M conversion done as a careful three-step `db0` → data-copy → `db1` sequence (`0004`–`0006`) → constraint/index hardening (`0008`, `0010`, `0011`) → status/nickname/colour additions (`0012`–`0015`) → `telegram_channel_id` + `calendar_incidents` (`0016`) → history tables (`0017`).

## 🧩 Extension Points & Hooks

- **GraphQL surface:** add a query by declaring a field on `OperationScalars`; add a filter/order class in `filters.py`/`orderings.py`. The `@strawberry_django.filter_field` pattern (`VehicleTypeFilter.line_id`, `StationFilter.location`) is the established way to add non-trivial predicates without touching models.
- **Mutations:** `OperationMutations` plus the commented `inputs.py` are a ready-made, pre-designed slot — uncommenting `LineInput`/`AssetInput`/`StationInput` and the `strawberry_django.mutations.create/update/delete` lines is the intended path to a write API, and requires no model changes.
- **DataLoaders:** `OperationContextLoaders` is a plain dict merged by key in `rosak/context.py`; new batch resolvers attach by adding one entry, and other apps can already reach them via `info.context.loaders["operation"][…]`.
- **Enums / statuses:** `LineStatus`, `VehicleStatus`, `WheelStatus` are `TextChoices`, so new members are additive. Note the coupling cost: each new `VehicleStatus` member currently needs a hand-written `vehicle_status_*_count` field on `VehicleType`.
- **Admin:** the inline classes (`StationLineTabularInline`, `VehicleLineTabularInline`, `AssetTabularInline`, `AssetMediaTabluarInline`, `StationMediaStackedInline`) are exported and already reused cross-app (`incident.admin` imports `Line`; this app imports `StationIncidentInlineAdmin` / `VehicleIncidentInlineAdmin`), making inlines the low-friction integration seam.
- **Analytics:** `common.utils.get_trends` is the single shared aggregation primitive; new trend endpoints are a matter of supplying `count_model`, `groupby_field`, `filters`, and `additional_groupby`.
- **History:** `HistoricalRecords` on `Vehicle`/`Asset` gives a queryable audit trail that nothing currently exposes — a free extension point for timeline features.

## 💡 Potential Feature Opportunities

1. **Station accessibility board — "which lifts and escalators are working here".** `Asset` already models exactly this: `asset_type` (`AssetType.LIFT` / `ESCALATOR`), `status` (`AssetStatus.IN_OPERATION` / `UNDER_MAINTENANCE`), an `officialid`, a `station` FK with `related_name="assets"`, and `medias` for photos — and the `Station` scalar already exposes `assets: List["Asset"]`. Yet the `Asset` Strawberry type in `operation/schema/scalars.py` omits `status` entirely and `AssetFilter` has no `status` field, so a client physically cannot ask whether a lift is up. Joined with `reporting.Report.asset` (already FK'd here, and `reporting.schema.scalars` already re-uses this `Asset` scalar), the same query could return "lift out of service, 4 rider reports open" — the single highest-value accessibility feature in a network where a broken lift means a wheelchair user cannot use the station at all.
   **Readiness:** `Partially ready` — the data exists, the read surface does not. Add `status: strawberry.auto` to the `Asset` scalar (`operation/schema/scalars.py`) and to `AssetFilter` (`operation/schema/filters.py`). Because `Asset.status` is a plain `CharField(choices=AssetStatus.choices)` and `Asset.asset_type` a plain `TextField(choices=AssetType.choices)` rather than `TextChoicesField`, `strawberry.auto` resolves them to `String` instead of a GraphQL enum; converting both to `django_choices_field.TextChoicesField(choices_enum=…)` in `operation/models.py` (new migration after `0017_historicalvehicle_historicalasset`) is what makes them enum-typed and consistent with `Line.status`. While in that file, fix `Asset.stations: List["Station"]` → `station: "Station"`, since the model FK is singular.

2. **Route-ordered station sequences (strip maps, "next stations", ordered line pages).** Every consumer that renders a line wants its stations in *travel* order, and `StationLine` is the only place that ordinal could live — but it has no such field. `StationLine.Meta.ordering = ["internal_representation"]` is a lexicographic sort of a 32-char code, so `Line.station_lines` returns `KJ10` before `KJ2`; any frontend showing a line diagram is either re-sorting client-side or displaying the wrong order. Fixing this unlocks strip maps, "stations between A and B", and correct station pickers in the spotting flow (`spotting.Event` holds two FKs to `Station`).
   **Readiness:** `Not ready` — a schema change is required first. `django-ordered-model` is already a project dependency and `incident/models.py` uses `OrderedModel` throughout, so the pattern is established in-repo. Implementer steps: make `StationLine` inherit `ordered_model.models.OrderedModel` with `order_with_respect_to = "line"` in `operation/models.py`, merge `class Meta(OrderedModel.Meta)` with the three existing `UniqueConstraint`s, generate a migration plus a data migration backfilling `order` from the numeric tail of `internal_representation`, switch `StationLineTabularInline` in `operation/admin.py` to `ordered_model.admin.OrderedTabularInline` (the file already imports `OrderedInlineModelAdminMixin` onto `StationAdmin`, currently a no-op), and expose `order` on the `StationLine` scalar with a `StationLineOrder` class in `operation/schema/orderings.py`. Caution: changing `Meta.ordering` silently changes the result order of every existing `Line.station_lines` query.

3. **Collapse the seven hand-written status counters into one generated `statusCounts` field.** `VehicleType` currently declares `vehicle_status_in_service_count`, `…_not_spotted_…`, `…_out_of_service_…`, `…_decommissioned_…`, `…_married_…`, `…_testing_…` and `…_unknown_…` as seven near-identical resolvers, each loading `(self.id, VehicleStatus.X)` from `vehicle_status_count_from_vehicle_type_loader`. Because that loader is already keyed on `(vehicle_type_id, status)` and batches all keys into a single `aaggregate()` with one `Count(filter=…)` per key, one resolver looping `for status in VehicleStatus` returns the entire breakdown at the same query cost. This removes the coupling flagged in *Extension Points*: adding a `VehicleStatus` member stops being a scalar edit, and fleet-composition charts stop needing a code change per status.
   **Readiness:** `Ready` — no migration, no loader change. Touch only `operation/schema/scalars.py`: add a small `@strawberry.type VehicleStatusCount` (`status`, `count`) and a `status_counts: List[VehicleStatusCount]` resolver that awaits one `.load((self.id, status))` per `VehicleStatus` member. Keep the seven existing fields with `deprecation_reason` set for one release, since the frontend reads them by name today.

4. **Fleet and asset change timeline — a "what changed this week" feed.** `HistoricalRecords()` sits on both `Vehicle` and `Asset` (tables created in migration `0017_historicalvehicle_historicalasset`), and `simple_history.middleware.HistoryRequestMiddleware` is installed in `rosak/settings.py`, so `history_user`, `history_date` and `history_type` are *already being populated* on every admin edit — a complete, attributed audit trail that no interface reads. Exposing it gives per-vehicle timelines ("this set went `TESTING` → `IN_SERVICE` on 12 March, wheels re-profiled in June") and a network-wide digest of fleet churn and lift repairs, which is precisely the institutional knowledge a community rail platform exists to preserve.
   **Readiness:** `Partially ready` — the data is being recorded but has no type and no query. Implementer steps: add `HistoricalVehicle` / `HistoricalAsset` Strawberry types in `operation/schema/scalars.py` over `models.Vehicle.history.model` / `models.Asset.history.model`, exposing `history_date`, `history_type`, `history_change_reason` and the tracked fields; add `vehicleChanges` / `assetChanges` root fields (with `after` / `before` date args and `pagination=True`) to `OperationScalars` in `operation/schema/schema.py`; and add a batching loader in `operation/schema/loaders.py` for the per-vehicle case, because `simple_history`'s `prev_record` / `diff_against()` — the natural way to render "what changed" rather than "what the row looked like" — costs one query per row otherwise. Gate `history_user` behind `rosak.permissions.IsAdmin`, mirroring how `common/schema/scalars.py` protects `firebase_id`, since it names staff accounts.

5. **Staff-authenticated GraphQL write API for reference data.** The write path is pre-designed and merely switched off: `operation/schema/inputs.py` contains a complete commented-out `LineInput` / `AssetInput` / `StationInput` set with `*PartialInput` variants, `operation/schema/mutations.py` is empty, and `OperationMutations` is a `pass`-body class *already mixed into* `rosak.schema.Mutation`. The permission primitives exist too — `rosak/permissions.py` provides `IsLoggedIn`, `IsAdmin` and `IsRecaptchaChallengePassed`, and `spotting/schema/schema.py` already combines all three on mutations. Today every new station, every lift status correction, and every fleet-status update requires Django admin access, which makes a handful of staff the bottleneck on the whole dataset; a guarded mutation surface lets trusted contributors maintain it and lets a future moderation UI live outside `/admin/`.
   **Readiness:** `Partially ready` — three concrete defects block a straight uncomment. (a) `inputs.py` does `from operation.schema.enums import AssetType`, but that module does not exist — enums live in `operation/enums.py`, so the import must be repointed or the field typed as the generated enum. (b) `StationInput` declares `internal_representation`, which is a field on `StationLine`, not `Station`; drop it or reshape the input to nest station-line rows. (c) There is no `VehicleInput` / `VehiclePartialInput` at all, even though `Vehicle.status` and `wheel_status` are the fields contributors most want to correct — write them against `operation/models.Vehicle`. Then declare `strawberry_django.mutations.create/update/delete(..., permission_classes=[IsLoggedIn, IsAdmin])` in `operation/schema/schema.py`. A natural follow-on, entirely deterministic: fire a Telegram broadcast when `Line.status` is set to `PARTIAL_DISRUPTION` / `TOTAL_DISRUPTION`, since `Line.telegram_channel_id` and the `telegram_provider` handlers are already in place.

## 💡 Potential AI Feature Opportunities

1. **Predictive fleet-health / wheel-wear scoring.** `Vehicle` already carries `wheel_status`, `in_service_since`, `notes`, a full `HistoricalVehicle` audit trail, per-vehicle `incident_count`, and a dense `spotting_trends` series. That is a labelled feature set: a model could predict the next `WheelStatus` transition or flag vehicles whose spotting cadence is decaying toward `NOT_SPOTTED`, exposed as a `Vehicle.predicted_*` field backed by a new DataLoader — no schema migration required.
2. **Anomaly detection over line-level spotting/status trends.** `Line.vehicle_spotting_trends` plus `chartography`'s `LineVehicleStatusCountHistory` give per-line, per-status daily/weekly series with zero-filling and calendar flags (`is_last_week_of_month`) already computed. Seasonal-decomposition or changepoint detection could turn `LineStatus.PARTIAL_DISRUPTION`/`TOTAL_DISRUPTION` from a manually-set field into a *suggested* status, with `Line.telegram_channel_id` and the existing `telegram_provider` handlers as the ready-made alerting channel.
3. **Natural-language geospatial/network query resolver.** `StationFilter.location` already accepts a point-plus-radius, `Station.location` is a real `PointField`, and the filter graph is fully nested (station → line → station_line). An LLM layer translating "lifts out of service within 2 km of KL Sentral on the Kelana Jaya line" into a nested `StationFilter`/`AssetFilter` argument tree would need no new resolvers — only a translation step in front of the existing schema — and `Asset.asset_type`/`status` make the lift/escalator availability case the obvious first target.
