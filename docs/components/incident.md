# Component: incident

## 📌 Purpose & Scope

- **Core Responsibility:** Owns the *disruption record* for the rail network — two structurally independent tiers: (a) a per-asset **incident ledger** (`VehicleIncident`, `StationIncident`) that annotates a single vehicle or station with dated, editorially-ordered events, and (b) a network-level **calendar incident** (`CalendarIncident`) representing a service disruption spanning a datetime range, multiple lines/stations/vehicles, with a chronology of updates, markdown detail, media evidence and a reliability `impact_factor`. It is the "what went wrong, where and when" layer sitting on top of `operation`'s reference data.
- **Domain/Layer:** Django persistence + business-logic layer (GIS-enabled via `PointField`), surfaced as a **read-only** Strawberry GraphQL API. No `views.py` content (0 bytes), no `urls.py`, no `tasks.py`, no signals. All writes go through Django admin or `common`'s upload pipeline.

## 🔌 Interface & Data Flow

### Inputs (GraphQL arguments, filters, orderings, signals)

Root query fields are contributed by `IncidentScalars` (mixed into `rosak.schema.Query`): `vehicleIncidents`, `stationIncidents`, `calendarIncidents`, `calendarIncidentsBySeverityCount`.

| Filter (`incident/schema/filters.py`) | Notable inputs |
| --- | --- |
| `IncidentAbstractFilter` | plain (undecorated) mixin: `id`, `date`, `severity`, `is_last` |
| `VehicleIncidentFilter` | mixin + nested `vehicle: VehicleFilter` (imported from `operation.schema.filters`) |
| `StationIncidentFilter` | mixin + nested `station: StationFilter` (same cross-app import) |
| `CalendarIncidentFilter` | `id`, `severity`, plus a hand-written `date` `filter_field` |

- `CalendarIncidentFilter.date` takes a `DateFilterLookup[date]` and translates `range` / `exact` / `month.exact` / `year.exact` into an **interval-overlap** `Q` (a null `end_datetime` means "still ongoing" and always matches). Two sharp edges: the range width is enforced with a bare `assert … <= timedelta(days=60)` (an `AssertionError`, i.e. a 500, not a GraphQL validation error, and silently stripped under `python -O`), and the `month` branch does `month__lte=value.month.exact + 1`, an off-by-one that assumes a 0-indexed (JS) month from the client.
- Ordering: `CalendarIncidentOrder` — `id`, `order`, `impact_factor`, `start_datetime`, `end_datetime`. The two asset-level incident lists expose **no** ordering input.
- Resolver arguments: `calendarIncidentsBySeverityCount(start_date, end_date, group_by: GroupByEnum)` where `GroupByEnum` is `DAY | MONTH`.
- **Input types / mutations: none.** `IncidentMutations` is a bare `pass` class. **This app is read-only over GraphQL.**
- **Signals: none defined**, and no `simple_history` tracking either — audit trail is limited to `TimeStampedModel`'s `created`/`modified`.

### Outputs (GraphQL types, events)

Types in `incident/schema/scalars.py`:

- `IncidentAbstractScalar` — plain `@strawberry.type` base (`id`, `date`, `severity`, `order`, `title`, `brief`, `is_last`). Note `location` is **commented out**: the GIS point is captured in admin but never exposed to clients.
- `VehicleIncident` / `StationIncident` — subclass the base, add `vehicle: Vehicle` / `station: Station` (cross-app `operation` scalars). Their `medias` M2M is also commented out.
- `CalendarIncidentScalar` — the rich type: datetime range, `severity`, `title`, `brief`, `details`, `impact_factor: float`, `long_term`, `inaccurate`, plus `lines: [Line]`, `vehicles: [Vehicle]`, `stations: [Station]`, `categories: [CalendarIncidentCategoryScalar]`, `chronologies: [CalendarIncidentChronologyScalar]`, and three resolved fields:
  - `medias` → batched through the `medias_from_calendar_incident_loader` DataLoader, lazily typed against `common.schema.scalars.MediaScalar`.
  - `has_details` → `@sync_to_async` emptiness check on `details`.
  - `last_updated` → `@sync_to_async`; **re-fetches the row**, then `.count()` + an ordered slice on `chronologies` to take `max(incident.modified, latest_chronology.modified)`. Three extra queries per node, invisible to `DjangoOptimizerExtension` — the app's main N+1 hotspot.
- `CalendarIncidentChronologyScalar` — `order`, `indicator`, `datetime`, `content`, `source_url`, and a back-reference to `CalendarIncidentScalar`.
- `CalendarIncidentGroupByDateSeverityScalar` — flat aggregate row (`severity`, `date`, `count`, `is_long_term`) for calendar heat-map rendering; `is_long_term` is `null` in `MONTH` mode.
- **Celery: emits nothing.** No task module and no entry in `rosak/celery.py`'s beat schedule — this app is purely synchronous. It is only a *target* of `common.tasks.cleanup_temporary_media_task`.

### Dependencies

- **Outbound (incident → other apps):** `operation.Vehicle` (FK, CASCADE), `operation.Station` (FK, CASCADE), `operation.Line`/`Station`/`Vehicle` (M2M from `CalendarIncident`), `common.Media` (M2M on all three incident models, `through=CalendarIncidentMedia` for the calendar tier), `generic.views.GeometricForm` (map widget), `operation.models.Line` in admin's `CalendarIncidentLineFilter`, `operation.schema.filters`/`scalars` in the GraphQL layer.
- **Inbound (other apps → incident):**
  - `operation/admin.py` imports `StationIncidentInlineAdmin` and `VehicleIncidentInlineAdmin` — the asset-level ledger is *edited from the `operation` admin pages*, not its own.
  - `operation/schema/loaders.py` imports `incident.models.VehicleIncident` for `incident_from_vehicle_loader` and `incident_count_from_vehicle_loader`, powering `Vehicle.incidents`, `Vehicle.incidentCount` and `Vehicle.canExpand`. **No equivalent exists for `StationIncident`** — station-level incidents are reachable only via the root `stationIncidents` query (a genuine API asymmetry).
  - `operation.Line` declares its *own* `calendar_incidents = ManyToManyField("incident.CalendarIncident")`, and `Line.calendarIncidents` in GraphQL reads that. See the risk note below.
  - `common/enums.py` (`TemporaryMediaType.INCIDENT_CALENDAR_INCIDENT`), `common/views.py` (`GenericUpload` at `/upload/` stashes `calendar_incident_id` in metadata), `common/tasks.py` (creates the `CalendarIncidentMedia` row after the Discord upload completes) — this is the **only non-admin write path into the app**.
  - `telegram_provider` does **not** reference `incident` at all today, despite ingesting operator channel messages.
- **Third-party:** `model_utils.TimeStampedModel`, `ordered_model` (`OrderedModel`, `OrderedModelAdmin`, `OrderedTabularInline`, `OrderedInlineModelAdminMixin`), `mdeditor` (`MDEditorWidget` for `details`), `pendulum` (interval bucketing in the aggregate resolver), `django.contrib.gis`.

## ⚙️ Internal State & Logic

**Severity model — three disjoint `TextChoices` enums in `incident/enums.py`, all stored as plain `CharField(max_length=16, choices=…)` (no DB constraint, no `TextChoicesField`):**

| Enum | Values | Applies to |
| --- | --- | --- |
| `IncidentSeverity` | `CRITICAL`, `TRIVIA`, `STATUS` | asset-level tier — mixes true severity with a non-severity "status annotation" bucket |
| `CalendarIncidentSeverity` | `MAJOR` (line-wide breakage, crashes), `MINOR` (single-vehicle), `OTHERS` | network-level tier |
| `CalendarIncidentChronologyIndicator` | `GREEN`, `RED`, `BLUE`, `GRAY` | timeline dot colour |

The two severity vocabularies are **not interchangeable**, and there is no mapping between them. `CalendarIncidentChronology.indicator`'s `help_text` documents a fifth "Loading" state that does not exist in the enum — a client-side-only value that will never validate.

**Incident vs. calendar-incident.** `IncidentAbstractModel` (`TimeStampedModel + OrderedModel`) carries `date` (a plain `DateField` — day granularity), `severity`, optional `location: PointField`, short `title`/`brief`, `is_last`, and an explicit editable `order`. `VehicleIncident` and `StationIncident` set `order_with_respect_to` to their parent, so each vehicle/station owns an independently ordered history, and `is_last` flags the row that represents the asset's *current* state. `CalendarIncident` instead models a *span* (`start_datetime`, nullable `end_datetime` = ongoing) with `long_term` (collapse to start date only in month view), `inaccurate` (display an "unverified" badge), a `Decimal(5,2)` `impact_factor`, a `TextField` `brief`, markdown `details`, and fan-out M2Ms. Its narrative lives in `CalendarIncidentChronology` rows (`related_name="chronologies"`, ordered per incident), maintained as an admin inline. **There is no FK between the two tiers** — a `VehicleIncident` cannot be linked to the `CalendarIncident` it belongs to; correlation is only implicit via shared vehicle/station and date.

**Aggregation logic (`schema/resolvers.py`).** `get_calendar_incidents_by_severity_count` is the only hand-written resolver. It first narrows to incidents overlapping the window, `aaggregate`s the earliest `start_datetime`, then builds a `pendulum` interval clamped to `min(end_date, today)` and constructs **one conditional `Count(filter=Q(…))` per bucket × severity (× long/short term in `DAY` mode)** — up to `days × 3 × 2` conditional aggregates in a single query — then reconstructs dates by string-splitting the aggregate alias on `_`. Efficient in round-trips (one query), but the generated SQL grows linearly with the requested range; the 60-day assertion in the filter is the de-facto guard, and it does not apply to this resolver.

**Batching.** `IncidentContextLoaders` holds a single `medias_from_calendar_incident_loader`, registered under key `"incident"` in `rosak/context.py` and `deepcopy`'d per request. `batch_load_medias_from_calendar_incident` walks `CalendarIncidentMedia` with `select_related("media")` and returns a **`set`** per key even though the field is typed `List[MediaScalar]` — media are silently de-duplicated and the `CalendarIncidentMedia.timestamp` ordering is discarded.

**Known integrity risks.**
- **Duplicate Line↔CalendarIncident relation.** `CalendarIncident.lines` (`related_name="incidents"`, set in migration `0013`) and `operation.Line.calendar_incidents` are two *separate* join tables. Admin's `filter_horizontal` edits the former; the GraphQL `Line.calendarIncidents` field reads the latter — so that field is expected to be permanently empty. Consolidating on `Line.incidents` (the reverse accessor) is the fix.
- **`StationIncident`'s unique constraint is missing its condition.** `VehicleIncident` guards `UniqueConstraint(fields=["is_last", "vehicle"], condition=Q(is_last=True))`; `StationIncident` declares the same constraint on `["is_last", "station"]` **without the condition**, so a station can hold at most one `is_last=False` incident in total. Any second historical incident for a station will raise `IntegrityError`.
- `order` is redeclared on the concrete models as `editable=True` with a `# Remove after beta` comment still outstanding.

**Schema evolution (13 migrations, `0001_initial` Aug 2022 → `0013` Mar 2024):** `0002`/`0003` add `is_last` and its constraints; `0004` introduces the whole calendar tier (`CalendarIncident`, `CalendarIncidentCategory`, `CalendarIncidentChronology`); `0005`–`0008` churn on `severity` choices and `brief`; `0009` adds chronology `source_url`; `0010` adds `inaccurate`; `0011` replaces the plain media M2M with the `CalendarIncidentMedia` through-model; `0013` adds `related_name="incidents"`. `0005_alter_calendarincident_severity.py` is currently **uncommitted-modified** in the working tree.

## 🧩 Extension Points & Hooks

- **The abstract triad.** `IncidentAbstractModel` + `IncidentAbstractScalar` + `IncidentAbstractFilter` is a deliberate three-layer template: adding a new incident target (e.g. `AssetIncident` for `operation.Asset` lifts/escalators) means one model subclass, one scalar subclass, one filter subclass, one field on `IncidentScalars`, and one inline in `operation/admin.py` — no changes to existing code.
- **`IncidentMutations` (empty `pass`)** is the designated, already-wired seam for the first write path; it is mixed into `rosak.schema.Mutation` today and contributes nothing.
- **`CalendarIncidentCategory`** is a free-form tag table — new taxonomies (signalling, power, rolling stock, weather, industrial action) need data rows, not migrations.
- **`IncidentContextLoaders`** dict — new batched fields plug in by adding one key; the per-request `deepcopy` in `rosak/context.py` handles isolation.
- **`impact_factor` is a reserved hook with zero consumers.** Its `help_text` specifies "scores to deduct from a full score of 100 per day, prorated by usual service hours when consolidating", but no code in the repo — `chartography` included — ever reads it. The reliability-index feature it was designed for is unbuilt; the column, the admin field, the GraphQL field and the ordering key are all already in place.
- **`CalendarIncidentChronology.source_url` + the `/upload/` → `common.tasks` → `CalendarIncidentMedia` pipeline** form a ready evidence-attachment channel (with EXIF timestamp capture) for any future citation or verification workflow.
- **`inaccurate` / `long_term` booleans** are presentation flags the frontend already honours — usable as confidence or provisional markers by automated writers without new schema.
- **`ordered_model`** gives editors manual precedence control (`move_up_down_links`) independent of chronology, useful for pinning headline incidents.

## 💡 Potential Feature Opportunities

1. **"All incidents in this disruption" — one FK to join the two tiers.** The single highest-leverage schema change in the app. Today `VehicleIncident`/`StationIncident` and the `CalendarIncident` they belong to have no relation at all, so a reader viewing a network disruption cannot see which individual trains or stations were affected, and an editor logging a vehicle fault cannot attach it to the open disruption. A nullable `calendar_incident` FK on `IncidentAbstractModel` (`on_delete=SET_NULL`, `related_name="%(class)s_set"`) gives `CalendarIncidentScalar` rollup lists and each asset-level scalar a parent link, following the existing abstract-triad pattern exactly. For a community rail platform this is the difference between a calendar of headlines and a genuinely queryable incident record — and it also makes `impact_factor` attributable to specific rolling stock.
   **Readiness:** `Not ready` — the FK does not exist; correlation today is implicit via shared vehicle/station plus `date` proximity. An implementer adds the field to `IncidentAbstractModel` in `/home/kwongtn/rosak_backend/incident/models.py` (both concrete models inherit it), generates `incident/migrations/0014_…` (nullable, so no backfill is forced), adds `calendar_incident: Optional["CalendarIncidentScalar"]` to `VehicleIncident`/`StationIncident` and the reverse `List[...]` fields to `CalendarIncidentScalar` in `incident/schema/scalars.py`, a nested filter in `incident/schema/filters.py`, and `autocomplete_fields = ("calendar_incident",)` on the inlines in `incident/admin.py` — `CalendarIncidentAdmin` already declares `search_fields`, so admin autocomplete works with no extra setup.

2. **Per-line reliability score — pure arithmetic over `impact_factor`.** `impact_factor` is a `Decimal(5,2)` on `CalendarIncident` whose `help_text` already specifies the exact formula ("Scores to deduct from full score of 100 per day. Will be prorated based on usual service hours when consolidating"), and it is fully wired end-to-end — DB column, admin form field, `CalendarIncidentScalar.impact_factor: float`, and an `impact_factor` key on `CalendarIncidentOrder` — with **zero consumers anywhere in the repo**. A new resolver alongside `get_calendar_incidents_by_severity_count` in `incident/schema/resolvers.py` can walk incidents overlapping a window, deduct each one's `impact_factor` per overlapped day from 100, and group by the affected `Line` — no model, just subtraction and a `GROUP BY`. Publishing a monthly reliability figure per line is the flagship number a community transit-watch site exists to produce.
   **Readiness:** `Partially ready` — the value and every plumbing layer already exist, but two gaps remain. (a) The "prorated by usual service hours" half of the spec has no data source: `operation.Line` carries only `official_numbering`, `code`, `display_name`, `display_color`, `status` and `telegram_channel_id` — no service-hours field — so either v1 uses whole-day denominators or a `service_start_time`/`service_end_time` pair is added to `operation/models.py`. (b) The resolver must traverse `CalendarIncident.lines` (reverse accessor `Line.incidents`, set in migration `0013`), **not** `operation.Line.calendar_incidents`, which is the dead duplicate join table admin never writes to. Files: `incident/schema/resolvers.py`, `incident/schema/schema.py` (new field on `IncidentScalars`), optionally `operation/schema/scalars.py` for a `Line.reliabilityScore` field.

3. **Public status page and a subscribable disruption feed (ICS / Atom / RSS).** `CalendarIncident` already holds everything such a feed needs: `start_datetime`, a nullable `end_datetime` that literally means "still ongoing", `severity`, `title`, markdown `details`, the `inaccurate` flag for an "unverified" badge, `long_term` for maintenance-window collapsing, and ordered `CalendarIncidentChronology` rows carrying `datetime`, `indicator`, `content` and `source_url` for successive updates. An "is it broken right now?" page plus a calendar subscription commuters can add to their phone is the highest-value read-only surface this data supports, and needs no new persistence at all.
   **Readiness:** `Partially ready` — two concrete gaps. (a) There is no way to ask for *ongoing* incidents: `CalendarIncidentFilter` exposes only `id`, `severity` and the hand-written `date` field, so a client must send a `date.range` window (hard-capped at 60 days by a bare `assert`) and filter client-side; add an `ongoing: Optional[bool]` `filter_field` mapping to `Q(end_datetime__isnull=True)` in `incident/schema/filters.py`. (b) For a real feed URL, `incident/views.py` is 0 bytes and the app has no `urls.py`; `rosak/urls.py` already `include()`s `operation.urls` and `telegram_provider.urls`, so add `incident/urls.py` with a `django.contrib.syndication.views.Feed` subclass (Atom/RSS) and a plain-text `text/calendar` view, then one `path("incident/", include("incident.urls"))` line.

4. **Put asset-level incidents on the map, with their photo evidence.** `IncidentAbstractModel.location` is a real `PointField`, already captured by editors through `VehicleIncidentLocationForm`/`StationIncidentLocationForm` (latitude/longitude inputs supplied by `generic.views.GeometricForm`), and both `VehicleIncident` and `StationIncident` carry a `medias` M2M to `common.Media`. All three are **commented out** in `incident/schema/scalars.py` (`# location` at line 19, `# medias` at lines 28 and 34), so data volunteers are already entering is invisible to every client — no "where on the line did this door fault happen" map, no photo next to the ledger entry.
   **Readiness:** `Ready` — no migration, no new infrastructure. `generic.schema.scalars.GeoPoint` already exists and `operation.schema.scalars.Station` uses precisely `location: Optional["GeoPoint"]`, so declare the same on `IncidentAbstractScalar`, and `medias: List[Annotated["MediaScalar", strawberry.lazy("common.schema.scalars")]]` on both subclasses. These are plain M2Ms with no through-model ordering to preserve, so `DjangoOptimizerExtension` prefetches them directly — unlike the calendar tier, no DataLoader is required. Single file: `incident/schema/scalars.py`.

5. **Station incident history — currently blocked by a missing constraint condition.** A station-detail page showing "past problems at this station" is the natural twin of the vehicle history the frontend already renders, but it is impossible today for two independent reasons. First, `StationIncident.Meta` declares `UniqueConstraint(fields=["is_last", "station"], name="…_unique_is_last_station")` **without** the `condition=Q(is_last=True)` that its `VehicleIncident` twin has, so at most one `is_last=False` row can exist across the entire table — the second historical incident for *any* station raises `IntegrityError`. Second, `operation/schema/loaders.py` provides `incident_from_vehicle_loader` and `incident_count_from_vehicle_loader` (powering `Vehicle.incidents`, `Vehicle.incidentCount`, `Vehicle.canExpand`) but no station equivalent, so `operation.schema.scalars.Station` has no `incidents` field at all — only the root `stationIncidents` query reaches them.
   **Readiness:** `Not ready` — fix the constraint in `incident/models.py` and ship a migration with `RemoveConstraint` + `AddConstraint` (existing `is_last=False` rows must be checked first or `AddConstraint` will fail on legacy data), then mirror `batch_load_incident_from_vehicle`/`batch_load_incident_count_from_vehicle` as station variants in `operation/schema/loaders.py`, register the new keys in the `OperationContextLoaders` dict, and add `incidents`/`incident_count` resolver fields to `Station` in `operation/schema/scalars.py`. Note the constraint fix is the hard blocker and should ship on its own — it is a latent production bug, not just a missing feature.

## 💡 Potential AI Feature Opportunities

1. **Auto-draft calendar incidents from operator announcements.** `telegram_provider` already ingests channel messages and `operation.Line` carries `telegram_channel_id`, yet nothing bridges into `incident`. An LLM extraction step could propose a `CalendarIncident` (start/end datetime, `severity`, affected `lines`/`stations`, `title`, `brief`) plus successive `CalendarIncidentChronology` rows straight from raw announcements, writing through the empty `IncidentMutations` and setting `inaccurate=True` as a built-in low-confidence / awaiting-review marker. Chronology `source_url` gives citation for free.
2. **Impact scoring and severity assistance.** With `impact_factor` present but unconsumed, a model trained on historical span duration, affected-line count, chronology length and severity could suggest an `impact_factor` at admin-save time and roll it into a per-line reliability index for `chartography` — turning a dormant column into the reliability metric it was specified as, without a migration.
3. **Semantic clustering, dedup and cross-tier linkage.** `title`/`brief`/`details`/chronology text plus the `CalendarIncidentCategory` M2M make this app embedding-ready: suggest categories automatically, detect that a newly filed incident duplicates an open one, support natural-language calendar search ("signalling failures on the Kelana Jaya line last monsoon"), and — most valuably — propose links between the disconnected tiers, inferring which `VehicleIncident`/`StationIncident` ledger rows belong to which `CalendarIncident` from shared asset and date proximity. That inferred relation is exactly the FK the schema currently lacks.
