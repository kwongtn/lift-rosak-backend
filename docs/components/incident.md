# Component: incident

## 📌 Purpose & Scope

- **Core Responsibility:** Owns the _disruption record_ for the rail network — two structurally independent tiers: (a) a per-asset **incident ledger** (`VehicleIncident`, `StationIncident`) that annotates a single vehicle or station with dated, editorially-ordered events, and (b) a network-level **calendar incident** (`CalendarIncident`) representing a service disruption spanning a datetime range, multiple lines/stations/vehicles, with a chronology of updates, markdown detail, media evidence and a reliability `impact_factor`. It is the "what went wrong, where and when" layer sitting on top of `operation`'s reference data. It also owns the crowd-sourced **feed**: `SocialMediaLink` submissions (canonical-URL dedup + votes) and `LineStatusReport` passenger-load reports, which consolidate into a per-line pulse consumed by `operation.Line`.
- **Domain/Layer:** Django persistence + business-logic layer (GIS-enabled via `PointField`), surfaced as a **read/write** Strawberry GraphQL API. `views.py` holds the X Activity API webhook receiver (`/webhooks/x-api`, the primary official-post ingestion path) and there is no `urls.py` of its own — the webhook route is registered directly in `rosak/urls.py`. No signals. Writes flow through the GraphQL mutations (community reporting + admin approval), the `/upload/` → `common` media pipeline, the webhook receiver, and the Celery tasks in `incident/tasks.py` (scheduled in `rosak/celery.py`, plus the webhook's off-beat `notify_official_post_links`).

## 🔌 Interface & Data Flow

### Inputs (GraphQL arguments, filters, orderings, signals)

Root query fields are contributed by `IncidentScalars` (mixed into `rosak.schema.Query`): `vehicleIncidents`, `stationIncidents`, `calendarIncidents`, `calendarIncidentsBySeverityCount`, `pendingCalendarIncidents` (admin queue), `socialMediaLinks` (admin queue; tri-state `hidden: Boolean` filter), `publicSocialMediaLinks` (cursor-paginated connection), `calendarIncidentCategories`, `calendarIncidentHistory` (logged-in), `lineStatusHistory`, `networkStatusHistory`, `linesStatusHistory`, `lineStatusReports`.

| Filter (`incident/schema/filters.py`) | Notable inputs                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------- |
| `IncidentAbstractFilter`              | plain (undecorated) mixin: `id`, `date`, `severity`, `is_last`                     |
| `VehicleIncidentFilter`               | mixin + nested `vehicle: VehicleFilter` (imported from `operation.schema.filters`) |
| `StationIncidentFilter`               | mixin + nested `station: StationFilter` (same cross-app import)                    |
| `CalendarIncidentFilter`              | `id`, `severity`, plus hand-written `ongoing` and `date` `filter_field`s           |

- `CalendarIncidentFilter.date` takes a `CalendarIncidentDateFilter`. `range` and `exact` use inclusive **interval-overlap** predicates: start ≤ window end AND (end ≥ window start OR no end). Open-ended incidents must still start by the window end; combine `OR: { ongoing: true }` to retain the pinned section regardless of the viewed month. `month.exact` / `year.exact` remain legacy calendar-part filters. The range width is enforced with a `GraphQLError` ("date range cannot exceed 60 days") — a proper validation error, not a bare assert. One sharp edge remains: the `month` branch does `month__lte=value.month.exact + 1`, an off-by-one that assumes a 0-indexed (JS) month from the client.
- `CalendarIncidentFilter.ongoing` maps `true`/`false` to `Q(end_datetime__isnull=…)` — a client can ask for "what's currently broken" without guessing a date window.
- Ordering: `CalendarIncidentOrder` — `id`, `order`, `impact_factor`, `start_datetime`, `end_datetime`. The two asset-level incident lists expose **no** ordering input.
- Resolver arguments: `calendarIncidentsBySeverityCount(start_date, end_date, group_by: GroupByEnum)` where `GroupByEnum` is `DAY | MONTH`; `publicSocialMediaLinks(incident_id, line_id, first, after, mine, status, current_service_day_only, last_week_only, align_page_to_day, display_today_in_last_week, collapse_threads)` — **ordered `-occurred_at DESC, id DESC`** (the event instant, not the submission time; `id` is the tie-break that makes the order total, and the keyset cursor is the `(occurred_at, id)` pair); the optional `status: SocialMediaLinkStatus` narrows the feed to one approval status (omitted, both `LIVE` and `PENDING_APPROVAL` are returned), and `currentServiceDayOnly: Boolean! = false` restricts it to links **occurring** at/after the current service day's 03:00 start (`services/line_status.py::service_day_start`, the same helper behind `lineStatusHistory` and its two siblings `networkStatusHistory(dayStartHour: Int = 3)` / `linesStatusHistory(lineIds: [ID!]!, dayStartHour: Int = 3)` — see the service-day history section below); `lastWeekOnly: Boolean! = false` restricts it to the last six **completed** calendar days, i.e. the half-open range `[local midnight six days ago, local midnight this morning)` — `occurred_at >=` via `incident/schema/resolvers.py::last_week_start` (naive-local like `service_day_start`) and `<` today 00:00 via the upper-bound counterpart `_event_window_before`, so **today is excluded by default**; the cut is plain calendar midnight, deliberately **not** the 03:00 service-day rollover; `displayTodayInLastWeek: Boolean! = false` drops the upper bound and restores the inclusive seven-day window, and is inert when `lastWeekOnly` is `false` (composable with `currentServiceDayOnly`, but only the intersection: the pair spans `[service_day_start, today 00:00)`, so it is empty from the 03:00 rollover until midnight and needs `displayTodayInLastWeek: true` for the old "current service day" meaning); `alignPageToDay: Boolean! = false` makes a page never end mid-day — after the standard `first + 1` lookahead fetch, if the lookahead row shares the page's last local calendar day **of `occurred_at`**, the lookahead and every remaining row of that day are appended (the page may exceed `first`, **no cap**: a whole day lands on one page), `endCursor` moves to that day's last row and `hasNextPage` probes for any row after it, while a lookahead on a different day leaves the page byte-identical to today's behaviour; `collapseThreads: Boolean! = false` narrows the page to link-tree **roots** (`parent IS NULL` — a plain indexed null test on a self-FK, which is cheaper than the flat `thread` column it replaced) before the count and before the cursor, so `totalCount` counts roots and each root carries its whole **subtree** through `sublinks` / `sublinkCount` — see the link-tree section below for why grouping must happen server-side and why a thread is now a tree rather than a flat group; it is silently ignored when `mine` is requested; `totalCount` stays the full filtered-set size regardless of cursor or `alignPageToDay`; **automatically ingested rows (`is_automated=True`) are excluded while they are `PENDING_APPROVAL`**, so an official announcement only becomes public once an admin approves it — community-submitted pending links still surface, unchanged, with their pending icon; **`HIDDEN` rows are excluded unconditionally** on the public branch, so an explicit `status: HIDDEN` returns an empty page rather than resurrecting them (the `mine` branch is deliberately exempt — an owner still sees their own hidden submission); `socialMediaLinks(search, category_id, completed, line_id, vehicle_id, station_id, occurred_after, occurred_before)` — the console queue, ordered `-occurred_at, -id` with inclusive (`>=`/`<=`) windows on the **same** column the sort uses. ⚠️ The last two arguments are a deliberate **breaking rename** of `created_after`/`created_before`; the old names are not aliased, so a stale client gets a GraphQL "Unknown argument" validation error rather than a silent filter on the wrong column; `calendarIncidentHistory(id, limit)`.

- **HTTP (non-GraphQL).** `GET/POST /webhooks/x-api` (name `x_api_webhook`), registered in `rosak/urls.py` inside an `apps.is_installed("incident")` block and wrapped in `csrf_exempt` — the request is authenticated by X's HMAC signature over the raw body, not by a session, and X sends no CSRF token and cannot be given one. Full contract in **Internal State & Logic** below.
- 🔴 **All nine vote mutations return `VoteMutationPayload`, not `GenericMutationReturn`.** `upvote` / `downvote` / `removeVote` / `upvoteChronology` / `downvoteChronology` / `removeChronologyVote` / `upvoteSocialMediaLink` / `downvoteSocialMediaLink` / `removeSocialMediaLinkVote` all acknowledge with `ok` **plus** the vote state the write produced: `userVote` (the caller's own −1/0/1), `voteScore`, `upvotes`, `downvotes`. The service layer's `set_*_vote` / `remove_*_vote` helpers return the same snapshot as a `VoteOutcome` dataclass, read in **one** aggregate round-trip (`Sum("value")` + filtered `Count`s; the caller's own vote is two more filtered counts rather than a second query, which `unique_together ("user", "content_type", "object_id")` makes exact). **Why the payload exists:** `ok` alone leaves the client to project the new score itself, and that projection races its own echo of the value and every other voter — the vote indicator visibly snapped back. **Why `ok` is retained:** the payload is a widening, so a client whose selection set is `{ ok }` keeps working unchanged; the retype is nonetheless a breaking change by graphql-core's definition and is named in `EXPECTED_ACCEPTED_BREAKING_CHANGES` (with a dedicated `_CHANGED_TYPE` anti-rot shape) rather than aliased. `_vote_payload` in `interactions.py` is the single place a `VoteOutcome` becomes a payload — all nine share one shape so the client's one control has one code path.
- `submitFeedLink(input: FeedLinkInput)` returns a `FeedLinkPayload` (`ok`, `link`, `isDuplicate`, `duplicateOfId`, `userVote`) — the feed path goes straight to `LIVE` for any logged-in user, dedups on the canonical URL and auto-upvotes the existing row on a duplicate. `submitLineStatusReport(input: LineStatusReportInput)` returns `GenericMutationReturn` and creates one standalone `LineStatusReport`. `updateSocialMediaLink` is `IsLoggedIn` (the service layer enforces ownership: admin edits land `LIVE`, a submitter's edit is forced back to `PENDING_APPROVAL`). **It is replace-not-patch**: the service assigns `url` and `title` unconditionally and calls `.set()` on all four tag M2Ms, so every caller must re-send the full payload — including `occurredAt`, whose explicit `null` means *reset to the submission time*, not "leave alone". `groupSocialMediaLinks(linkIds: [ID!]!, parentId: ID = null): GenericMutationReturn!`, `ungroupSocialMediaLinks(linkIds: [ID!]!): GenericMutationReturn!` and `reorderSocialMediaLinks(linkIds: [ID!]!, parentId: Maybe<ID>): GenericMutationReturn!` are dedicated **id-only** mutations precisely so a grouping action never has to travel through that input; `group` returns the **root of the affected conversation** in `id` so the client refetches exactly that row. ⚠️ `parentId` is a deliberate **un-aliased** rename of the previous `threadId` (as are the scalar's `parentId` / `sublinkCount` / `sublinks`), so a stale client gets a loud "Unknown argument/field" rather than silently receiving the old one-level grouping; the rename is pinned by `EXPECTED_ACCEPTED_BREAKING_CHANGES` in `rosak/tests/test_schema_snapshot.py`. `reorderSocialMediaLinks` takes a `Maybe` on `parentId` while `group` takes a plain nullable `ID`, because the two arguments have genuinely different states — see the link-tree section below.

- **Service-level permission matrix** (the GraphQL `IsLoggedIn` gate is the floor; finer rules live in `incident/services/`):

| Operation | Non-admin | Admin |
| --------- | --------- | ----- |
| Edit a LIVE incident | any logged-in → creates a DRAFT revision (`parent_incident`), one-open-draft rule rejects a second actor's draft with the spec message; OCC `expected_version` fires on every path | in-place |
| Edit DRAFT / own PENDING_APPROVAL | author → in-place | in-place |
| Delete incident | author only when `DRAFT` or `PENDING_APPROVAL` | any |
| Delete chronology | author when the chronology or its parent incident is `DRAFT`/`PENDING_APPROVAL` | any |
| Request chronology deletion | author-or-admin, LIVE chronologies only → `PENDING_DELETION` | — |
| Approve / reject chronology deletion | — | soft-deletes / reverts to LIVE |

- **Signals: none defined.** Audit trail is `django-simple-history` (`HistoricalRecords(cascade_delete_history=False)` on `CalendarIncident` and `CalendarIncidentChronology`) plus `TimeStampedModel`'s `created`/`modified`.

### Outputs (GraphQL types, events)

Types in `incident/schema/scalars.py`:

- `IncidentAbstractScalar` — plain `@strawberry.type` base (`id`, `date`, `severity`, `order`, `title`, `brief`, `is_last`). Note `location` is **commented out**: the GIS point is captured in admin but never exposed to clients.
- `VehicleIncident` / `StationIncident` — subclass the base, add `vehicle: Vehicle` / `station: Station` (cross-app `operation` scalars). Their `medias` M2M is also commented out.
- `CalendarIncidentScalar` — the rich type: datetime range, `severity`, `status` (`CalendarIncidentStatus`), `title`, `brief`, `details`, `impact_factor: float`, `version` (OCC counter), `long_term`, `inaccurate`, `user` (the `created_by` author, `Optional[UserScalar]`), plus `lines: [Line]`, `vehicles: [Vehicle]`, `stations: [Station]`, `categories: [CalendarIncidentCategoryScalar]`, `chronologies: [CalendarIncidentChronologyScalar]`, and resolved fields:
  - `medias` → batched through the `medias_from_calendar_incident_loader` DataLoader, lazily typed against `common.schema.scalars.MediaScalar`.
  - `vote_score` / `vote_breakdown` / `user_vote` → batched through the `vote_scores` / `vote_breakdown` / `user_vote_value` DataLoaders (generic `common.Vote` via ContentType).
  - `links(first: Int = 10, after: String)` → a `SocialMediaLinkConnection` of per-incident submitted links, newest **occurrence** first (`occurred_at DESC, id DESC` — an incident whose newest report describes last Tuesday sorts that link first), keyset-cursor format identical to the root `publicSocialMediaLinks` resolver so a nested cursor can be handed to the root query for continuation pages. Page one is served by the `incident_links` DataLoader (one query for a feed of cards); continuation pages query directly (per-parent cursors cannot be batched). `totalCount` is the incident's full link count, unaffected by `after` (a separate `acount()` before the page branch).
  - `has_details` → `@sync_to_async` emptiness check on `details`.
  - `last_updated` → `@sync_to_async`; **re-fetches the row**, then `.count()` + an ordered slice on `chronologies` to take `max(incident.modified, latest_chronology.modified)`. Three extra queries per node, invisible to `DjangoOptimizerExtension` — the app's main N+1 hotspot.
- `CalendarIncidentChronologyScalar` — `id`, `order`, `status` (`CalendarIncidentStatus`, independent of the parent), `indicator`, `datetime`, `content`, `source_url`, a back-reference to `CalendarIncidentScalar`, and the same three vote fields (`vote_score` / `vote_breakdown` / `user_vote`) as the incident scalar.
- `CalendarIncidentHistoryEntryScalar` — one diffed `django-simple-history` record: `timestamp` (`history_date`, UTC), `actor` (nullable display identity, `None` for system/anonymous), `change_type` (`"created"` / `"updated"` / `"deleted"`), `changed_fields` (model field names from `diff_against`, internal history fields excluded). Served by `calendarIncidentHistory(id, limit=50)`, latest-first, `IsLoggedIn`.
- `SocialMediaLinkScalar` — `id`, `url`, `normalizedUrl` (tracking-stripped canonical form, computed on save), `title`, `description`, `status` (`SocialMediaLinkStatus`: `LIVE` / `PENDING_APPROVAL` / `HIDDEN`), `created` (submission time — the moderation provenance column), **`occurredAt: DateTime!`** (the event time; non-null and naive local, see the section below), `completed`, `completed_at`, `is_automated` → **`isAutomated: Boolean!`** (true only for rows written by official-post ingestion — the "Official" capture badge; false for every hand-submitted link, legacy rows included), `completed_by` (resolved display name — nickname or `firebase_id[:8]` shortId), `user`, `categories`, `lines`, `vehicles`, `stations`, the five hierarchy fields (**`parentId: ID`**, **`isThreadRoot: Boolean!`**, **`position: Int!`**, **`sublinkCount: Int!`**, **`sublinks: [SocialMediaLinkScalar!]!`** — the last recursive, see the link-tree section below), and `voteScore` / `userVote` (batched through the `vote_scores` / `user_vote_value` loaders). `SocialMediaLinkEdge` / `SocialMediaLinkPageInfo` / `SocialMediaLinkConnection` wrap it for cursor pagination; the connection also carries `totalCount: Int!` (whole filtered set — including the automated-pending exclusion below — `after`-independent; computed with a separate `queryset.acount()` before the cursor filter, so every call costs one extra count query, and the empty anonymous-`mine` page reports `0`); `FeedLinkPayload` is the `submitFeedLink` return type (`ok`, `link`, `isDuplicate`, `duplicateOfId`, `userVote`).
- `LineStatusReportScalar` — a single `LineStatusReport` read row: `id`, `status` (`PassengerStatus`), `delayMinutes`, `notes`, `created`, `user`, and `stations: [Station!]!` (the report's station tags, `[]` when unattached), served cursor-paginated by `lineStatusReports(lineId, first, after)`.
- `CalendarIncidentGroupByDateSeverityScalar` — flat aggregate row (`severity`, `date`, `count`, `is_long_term`) for calendar heat-map rendering; `is_long_term` is `null` in `MONTH` mode.
- **Celery (`incident/tasks.py`, registered in `rosak/celery.py`'s beat schedule):** `purge_soft_deleted_incidents` (hard-deletes safedelete-soft-deleted incidents past 90 days, `crontab(hour="3", minute="0")`), `purge_rejected_incidents` (hard-deletes `REJECTED` incidents unchanged for 30 days, `crontab(hour="3", minute="30")`) and `ingest_official_posts` (pulls the tracked official X accounts into `SocialMediaLink`, `crontab(minute="*/5")` with `{"expires": 240, "time_limit": 180}` — `expires` sits under the 5-minute period so a wedged run is never re-dispatched on top of itself). The ingestion task **ships inert**: it returns `{"skipped": "disabled"}` unless `OFFICIAL_POST_INGESTION_ENABLED` and `{"skipped": "no_token"}` without `X_API_BEARER_TOKEN`, so the beat entry is safe to deploy before the API tier is provisioned. It never calls `self.retry` and never sleeps — a per-handle `OfficialPostFetchError` is logged and the remaining handles still run, so one bad handle cannot stall the tick. **Phase 2 — the admin notification:** after each handle's `ingest_posts`, one message per entry in `summary.created_ids` goes to `settings.TELEGRAM_ADMIN_CHAT_ID` (the whole pass is skipped when that setting is blank, and re-scrapes announce nothing because a skipped/duplicate post has no id in `created_ids`). The message carries the handle, the post's own time, the **verbatim** `description` body, a permalink and a `{settings.FRONTEND_BASE_URL}/console/insiden/links` deep link, truncated so the *escaped* text stays inside Telegram's 4096-character limit, and every dynamic value is `html.escape`d — `raw_payload` is never rendered. It is sent through `telegram_provider.utils.send_message(..., return_log=True)`, whose returned audit log is joined to the new row via `TelegramSocialMediaLinkLog`, which is what makes the message resolvable by the existing `/approve` handler (a no-op on an already-`LIVE` row). The copy states the post is published and links to the console to *review*, not approve. Notification failure is contained per link (warn + continue): a dead-lettered or raising send costs the announcement, not the ingest — the row is already `LIVE` and visible in the feed. A per-handle `notified` counter is reported in the result dict and the structured log line (it is deliberately **not** in `INGEST_COUNTERS`, so it does not roll up into the task's top-level totals). The app is also a _target_ of `common.tasks.cleanup_temporary_media_task`.
- **Management commands (`incident/management/commands/`):**
  - `ingest_official_posts.py` — the manual backfill for the same ingestion path — `--handle` (repeatable), `--since` / `--until` (whole UTC days, mutually exclusive with the `since_id` fast path), `--limit`, `--fixture` and `--dry-run`. A fetch or ingest failure becomes a `CommandError` (non-zero exit); `--fixture` is rejected when a date window is given, and a multi-handle run is rejected as ambiguous when the handle came from settings rather than `--handle`.
  - `x_webhook.py` — the operator's lever for the webhook lifecycle, because a URL that merely exists receives nothing: X only pushes to a **registered** webhook that has answered a CRC challenge, and only for accounts with an **activity subscription** pointing at it. `register URL` (POST `/2/webhooks`), `list`, `delete ID`, `revalidate ID` (PUT, re-triggers CRC) and `subscribe HANDLE...` (one `post.create` subscription per handle, `@` stripped). Registration requires public **HTTPS with no port**, reachable from X's servers; a failure surfaces as the API's own `CrcValidationFailed` / `UrlValidationFailed` error `title`, which is the only part of the upstream body this command quotes — a `CommandError` message gets pasted into chats, so it carries the status code and that title and nothing else. `--webhook-id` is optional for `subscribe`: omitted, the registered webhooks are listed and there must be **exactly one**, because guessing between several would attach subscriptions to the wrong endpoint and stay silent until events stop arriving. Handle→user-id resolution reuses the ingestion service's own registry path — `resolve_account(handle, create=True)` (which auto-registers an unknown handle under `Unassigned`), then `ensure_user_profile`, the one live lookup — imported **inside** `_user_id` so the seam is patchable at its source, so a subscription can never be created against a different id than ingestion polls for. Authorised by `X_API_BEARER_TOKEN`, which must be **App-only** and is unrelated to the signing secrets — those stay server-side and are never sent to X from here. The token is read from settings, used only in an `Authorization` header, and never printed.
  - `export_official_posts.py` — the **read** side (spec Phase 3): exports every `is_automated=True` row as a JSONL or CSV archive — `--handle` (repeatable, `@` tolerated), `--since` / `--until` (inclusive UTC days over `posted_at`), `--format jsonl|csv`, `--output PATH|-`, `--include-raw`, `--dry-run`, `--push-to-hub REPO_ID`. The columns are the HuggingFace dataset schema in a fixed order (`post_id`, `posted_at` = the stored column's ISO-8601 form, `handle`, `text` = the verbatim `description`, `permalink`, plus `raw_payload` under `--include-raw`), ordered `posted_at, post_id, id` so two exports of unchanged rows are byte-identical. Rows stream out of `.only(...).iterator(chunk_size=500)` — a cursor, never a full-table list — and `--push-to-hub` is the one documented exception (`Dataset.from_dict` wants the whole set), lazy-importing `datasets` so no dependency is added, reading `HF_TOKEN` from the environment (never printed) and always pushing `private=True`. `--output -` sends the summary line to **stderr** so the data stream stays pipeable; `--dry-run` reports the exact count and writes nothing.

  - `telegram_provider` references `incident` **only** through the `TelegramSocialMediaLinkLog` FK (migration `0005`) and the `approve` handler that resolves it — it ingests no incident data. The dependency runs `incident → telegram_provider` for the notification, so the edge is one-way.
- **Third-party:** `model_utils.TimeStampedModel`, `ordered_model` (`OrderedModel`, `OrderedModelAdmin`, `OrderedTabularInline`, `OrderedInlineModelAdminMixin`), `mdeditor` (`MDEditorWidget` for `details`), `pendulum` (interval bucketing in the aggregate resolver), `django.contrib.gis`, `django-safedelete` (soft-delete + purge), `django-simple-history` (audit trail), `django-choices-field` (`TextChoicesField` for status enums), and **`django-tree-queries` >= 0.26.1** (the link tree: `OrderableTreeNode` / `TreeNodeForeignKey`; requires `"tree_queries"` in `INSTALLED_APPS` or it raises `tree_queries.E001`). ## ⚙️ Internal State & Logic

**Severity + status enums in `incident/enums.py`, all stored as `TextChoicesField` (or plain `CharField(max_length=16, choices=…)` for the legacy severity fields):**

| Enum | Values | Applies to |
| ---- | ------ | ---------- |
| `IncidentSeverity` | `CRITICAL`, `TRIVIA`, `STATUS` | asset-level tier — mixes true severity with a non-severity "status annotation" bucket |
| `CalendarIncidentSeverity` | `MAJOR` (line-wide breakage, crashes), `MINOR` (single-vehicle), `OTHERS` | network-level tier |
| `CalendarIncidentChronologyIndicator` | `GREEN`, `RED`, `BLUE`, `GRAY` | timeline dot colour |
| `CalendarIncidentStatus` | `DRAFT`, `PENDING_APPROVAL`, `LIVE`, `REJECTED`, `PENDING_DELETION` | shared by incident + chronology status fields; `PENDING_DELETION` is only ever set on chronologies (mark-for-delete flow) |
| `SocialMediaLinkStatus` | `LIVE`, `PENDING_APPROVAL`, `HIDDEN` | link lifecycle — deliberately not reusing the incident enum. `HIDDEN` is a **moderation decision**, not a lifecycle stage: the row is never returned by the public feed (not by default, not via an explicit `status: HIDDEN` filter), the console still lists it so an admin can un-hide it, and the owner still sees it under `mine` |
| `IngestPlatform` | `X` | source platform of an automatically ingested post on `SocialMediaLink`; one member by design — a second platform is a new member plus its own fetch function, never a speculative placeholder |
| `PassengerStatus` | `NORMAL`, `BUSY`, `CROWDED`, `EXTREMELY_CROWDED`, `BACKLOGGED`, `DELAYED`, `DISRUPTED` | crowd-reported passenger load on a `LineStatusReport`; declaration order doubles as the consolidation severity rank (`NORMAL` least → `DISRUPTED` most) |

The two severity vocabularies are **not interchangeable**, and there is no mapping between them. `CalendarIncidentChronology.indicator`'s `help_text` documents a fifth "Loading" state that does not exist in the enum — a client-side-only value that will never validate.

**Incident vs. calendar-incident.** `IncidentAbstractModel` (`TimeStampedModel + OrderedModel`) carries `date` (a plain `DateField` — day granularity), `severity`, optional `location: PointField`, short `title`/`brief`, `is_last`, and an explicit editable `order`. `VehicleIncident` and `StationIncident` set `order_with_respect_to` to their parent, so each vehicle/station owns an independently ordered history, and `is_last` flags the row that represents the asset's _current_ state. `CalendarIncident` instead models a _span_ (`start_datetime`, nullable `end_datetime` = ongoing) with `long_term` (collapse to start date only in month view), `inaccurate` (display an "unverified" badge), a `Decimal(5,2)` `impact_factor`, a `TextField` `brief`, markdown `details`, fan-out M2Ms, a `status` lifecycle, a `version` OCC counter, and a nullable `parent_incident` FK for the draft-revision flow. Its narrative lives in `CalendarIncidentChronology` rows (`related_name="chronologies"`, ordered per incident), each with its own independent `status`. **There is no FK between the two tiers** — a `VehicleIncident` cannot be linked to the `CalendarIncident` it belongs to; correlation is only implicit via shared vehicle/station and date.

**Feed links and the passenger pulse (`services/feed_links.py`, `services/line_status.py`, `services/urls.py`).** `SocialMediaLink` is the community feed item: `normalized_url` is recomputed on every `save()` from `canonicalize_url` (tracking params such as `fbclid`/`gclid`/`igshid`/`si`/`utm_*` stripped, host lowercased, fragment and trailing slash dropped) and cross-row dedup is enforced in `submit_feed_link` (global canonical match → auto-upvote the existing row; otherwise create `LIVE`), **not** by a DB constraint. It is also the target table of automated ingestion (below), which is why it now also carries a nullable `socmed_account` FK plus `post_id`, `posted_at`, `is_automated` and the untouched `raw_payload` — all `null`/default for community-submitted links, and **not exposed on `SocialMediaLinkScalar` yet** except `is_automated` (`isAutomated`), which is the only one of them a client needs — `posted_at` in particular stays **read-only provider provenance**: ingestion writes it alongside `occurred_at` from the same `RawPost.posted_at`, and `manage.py export_official_posts` reads it because an archive wants the provider's own value. `LineStatusReport` is a single passenger-load observation on a line (`status`, optional `delay_minutes` / `notes` / `stations`, optional `link`); `consolidate` reduces the last 15 minutes of reports to one `PassengerStatus` by weighted majority — a report linked to a social entry is weighted `1 + max(net_vote, 0)`, an unlinked report `1`, ties broken by recency then enum rank — and carries the full per-status count dict alongside the winner, which `load_line_pulses` batches per line in 3 flat queries for `operation.Line` (`passengerStatusCounts`). `load_line_status_history` backs `lineStatusHistory(lineId, dayStartHour)`: a line with at least one report that service day gets the full 24 hourly buckets (03:00 → 02:00, empty hours zero-filled), while a line with no report returns `[]` — the client's "No data" state. Each bucket carries `hourStart` / `hourEnd` / `count` (the hour's total) / `dominantStatus` plus `statusCounts` (`[PassengerStatusCount!]!` — the existing `operation.schema.scalars.PassengerStatusCount` reused rather than an incident-local parallel type: the per-status tally in enum order with zero counts omitted, summing to `count`; `[]` for an empty hour) for the frontend's stacked bars. `fetch_page_title` is a best-effort `httpx` `<title>` scrape that collapses every failure to `""`.

**The three service-day history queries (`services/line_status.py`).** `lineStatusHistory`, `networkStatusHistory` and `linesStatusHistory` are three *views* of one read, not three implementations: `_service_day_entries(line_ids, day_start_hour=, now=)` is the single private helper that validates `dayStartHour`, computes `service_day_start` and issues **one** `LineStatusReport` query, returning `(now, day_start, rows)` where each row pairs a report with its `line_id`. `line_ids=None` means *every* line, a non-empty sequence means `line_id__in`, and an **empty sequence returns before the query** — so `linesStatusHistory(lineIds: [])` is a zero-query call. All three then bucket through `bucket_hourly`, so they share the identical 24-hour contract and cannot drift on it.

| Query | Service | Scope | Returned when there is data | Returned when there is none |
| ----- | ------- | ----- | ---------------------------- | ----------------------------- |
| `lineStatusHistory(lineId: ID!, dayStartHour: Int = 3): [LineStatusHourBucket!]!` | `load_line_status_history` | one line | 24 buckets | `[]` |
| `networkStatusHistory(dayStartHour: Int = 3): [LineStatusHourBucket!]!` | `load_network_status_history` | **all lines, one grouped read** | 24 buckets | `[]` |
| `linesStatusHistory(lineIds: [ID!]!, dayStartHour: Int = 3): [LineStatusHistory!]!` | `load_lines_status_history` | N lines, **one query** | one `LineStatusHistory` per requested id, each with 24 buckets | the same entries, each line with `buckets: []` |

- **`networkStatusHistory` is a network aggregate, not a per-line figure.** With no line filter, an hour's `count` / `dominantStatus` / `statusCounts` tally **every** line's reports in that hour, so a chart of it answers "how is the network doing", not "how is line X doing". A client that wants one line must ask `lineStatusHistory` (or pick that line out of `linesStatusHistory`) — reading `networkStatusHistory` as a per-line series would silently draw other lines' reports under that line's name.
- **`linesStatusHistory` returns one entry per requested id, in the requested order**, with the SAME per-line invariant as `lineStatusHistory` (24 buckets or `[]`). The entry existing does **not** mean the line reported anything: `buckets == []` *is* the "no data" state. Duplicate ids collapse to one entry (first occurrence wins). `lineIds` is length-capped at `MAX_LINES_PER_HISTORY_REQUEST = 64` — a `LineStatusValidationError` (surfaced as a `GraphQLError`), so a client bug naming an unbounded id list cannot turn into a service-day scan; an unparseable id is a validation error too, not a 500. The cap is *not* a query-count guard: the read is one query at any count.
- All three are **public** (no `permission_classes`), like `lineStatusHistory`, and all three map `HourBucket` through one private `_hour_bucket()` in `schema/resolvers.py` — the single place the `PassengerStatus` enum mapping and the `statusCounts` ordering (declaration order, zeros omitted) live, so the three fields cannot disagree about the breakdown a stacked chart is drawn from.
- ⚠️ The network read filters on `created` alone, and the table's index is `(line, created)`, so it is a sequential scan of the service day's rows rather than an index seek. That is the right trade at current volume (one query beats a loop over lines, which is exactly what this query exists to avoid) but it is the thing to revisit if the report table grows by orders of magnitude — add a `created`-leading index first, do not split the read.

**X Activity API webhook receive (`views.py` + `services/x_webhooks.py`).** The **primary** ingestion path; the 5-minute poll (`OFFICIAL_POST_POLLING_ENABLED`, default off) is the fallback. One endpoint serves both of X's contracts, and it is a plain synchronous Django view rather than DRF — there is no authentication, no serializer and no content negotiation, only an HMAC over the raw bytes and a fast 200. Everything cryptographic and everything that touches the database lives in the service; `views.py` is transport only (validate, delegate, acknowledge).

| Request  | Response                                                                                                                                                              |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`    | 200 `{"response_token": "sha256=…"}`; 400 when `crc_token` is missing/blank; 503 when no signing secret is configured (operator-fixable, so not worth an X retry) |
| `POST`   | 200 `{"status": "ok", "events", "ingested", "skipped", "unresolved"}`; 400 non-JSON / not an object / rejected payload; 403 absent-or-wrong signature; 503 no secret or no system author |
| anything | 405 with `Allow: GET, POST`                                                                                                                                              |

Four choices are the load-bearing ones. (a) **The signature covers raw bytes.** `request.body` is read once and handed to `verify_webhook_signature(headers, raw_body)`; the parsed JSON is never re-serialized to recompute a digest, because that silently breaks the moment X changes its key order. Both candidate header/secret pairs in `SIGNATURE_CANDIDATES` (`X-Twitter-Webhooks-Signature-OAuth2` × `X_API_OAUTH2_CLIENT_SECRET`, and legacy `X-Twitter-Webhooks-Signature` × `X_API_SECRET_KEY`) are accepted, but a candidate is only tried when its secret is *configured* — comparing against an empty secret would accept a signature anyone can compute. Comparison is `hmac.compare_digest` over UTF-8 bytes on both sides, so a non-ASCII header cannot turn a 403 into a 500. (b) **The CRC is signed with the preferred secret only** (`X_API_OAUTH2_CLIENT_SECRET` when set), because that is the one X verifies the answer against; the legacy header is *not* tried for CRC, so `crc_response_token` matching a different construction than X expects is the first thing to check when registration returns `CrcValidationFailed`. (c) **Acknowledgement is the design constraint.** X retries anything outside 2xx and expects an answer within 10 seconds, so the DB write is inline (it is a handful of `get_or_create`s) and the Telegram notification is handed to the `notify_official_post_links` Celery task — a broker outage is logged and still answered 200, because the row is already committed and approvable from the console. `OfficialPostIngestError` (missing system author) is the one case that returns 503, so X may redeliver rather than the post being silently dropped. (d) **Two non-errors are acknowledged, not refused**: the master switch `OFFICIAL_POST_INGESTION_ENABLED=false` answers `{"status": "ignored", "reason": "ingestion disabled"}`, and a non-`post.create` event (e.g. `post.delete`) answers 200 having done nothing — a switch that is off, or an event we will never act on, is not X's fault, and erroring would only earn a retry storm.

**Official-post ingestion (`services/official_posts.py`).** Pulls the `SocMedAccount` registry accounts — the DB, seeded by migration `0029`, is the single source of truth; `OFFICIAL_POST_HANDLES` no longer exists — from the X API and lands them as `SocialMediaLink` rows authored by the `system:official-ingest` service user. Three deliberate choices bound the blast radius. (a) **Bounded, single-pass paging**: `fetch_user_posts` walks `next_token` backwards with a hard `_MAX_PAGES = 10` ceiling, so a handle whose timeline is re-scraped from scratch cannot fan out into hundreds of requests; `since_id=latest_post_id(account)` is the cheap path used by the periodic task. (b) **Two failure vocabularies**: `OfficialPostFetchError` (transport / token / rate limit, message sanitised so a bearer token can never reach a log line) is caught per handle and the tick continues, while `OfficialPostIngestError` from `get_system_author()` propagates — a missing service user is a deployment fault, not a per-handle hiccup. (c) **Idempotency is structural**: the partial `UniqueConstraint` on `(socmed_account, post_id)` is a DB-level backstop, and the service re-reads on `IntegrityError` rather than taking an advisory lock. A created row is `LIVE` — official posts are auto-published (auto-approved) by policy, so no admin action sits between the operator's announcement and the public feed; migration `0032` backfills the rows the old policy left `PENDING_APPROVAL` (automated pending → `LIVE`, `HIDDEN` never touched), and the pre-create existence checks mean a re-ingest never resurrects an admin-hidden official row. `ingest_posts(posts, *, author, dry_run=False)` resolves each post's account via `resolve_account(platform, handle=..., create=True)` — an unknown handle auto-registers under `Unassigned`, never an API call — returns an `IngestSummary(fetched, created, skipped, duplicate_urls, created_ids=())` and takes an additive keyword-only `dry_run: bool = False` that counts would-be creations inside the same code path and writes nothing. `load_fixture_posts(path, *, handle=None)` is the injectable offline source: `--fixture` plus `--dry-run` gives a network-free import rehearsal, and the shipped JSON fixtures under `incident/fixtures/` are what the test suite replays. **One decode point.** X delivers post text with `&amp;` / `&lt;` / `&gt;` / `&quot;` / `&#39;` and numeric references still encoded, so `tweet_to_raw_post` — the single mapping into `RawPost` shared by the poll, the fixture loader *and* the webhook parser — runs `html.unescape` (stdlib) on the text exactly once. `RawPost.text`, and therefore `SocialMediaLink.title` (truncated to `TITLE_MAX_LENGTH` *after* decoding) and `description`, are verbatim-after-decoding; `RawPost.raw` is left exactly as the provider sent it, so `raw_payload` keeps the encoded original for export fidelity. Never decode a second time: `&amp;amp;` is an *escaped entity*, and a second pass would store a bare `&`. A plain `&` is left alone, which is what the fixture replay asserts.

**The account registry (`models.py`: `Agency`, `SocMedAccount`).** The DB replaces `settings.OFFICIAL_POST_HANDLES` (which no longer exists) as the single source of truth for which social accounts the pipeline tracks. `SocMedAccount` is unique on `(platform, handle)` and on non-empty `(platform, user_id)` — an empty `user_id` is the explicit "not yet resolved" state, sharable by many rows. `is_enabled` (default `True`) gates the **polling task only**: `ingest_official_posts` iterates enabled X accounts ordered by handle, so flipping one row on/off changes what the 5-minute poll fetches without a settings change (the webhook is unaffected — it resolves by the delivery's own author id). Every ingest path converges on `resolve_account(platform, *, handle, user_id, raw_payload, display_name, create)`: lookup **by `user_id` first** (strongest key — a webhook carries the id while the handle may have changed), then by `handle`; a hit cheaply back-fills a missing `user_id` and refreshes `display_name`/`raw_payload`/`resolved_at` when the caller holds the provider's full user object; a miss with `create=True` *and* a known handle auto-registers under the `Unassigned` agency with an empty `user_id` — **never an API call**. `resolve_account` touches no network. The **only** live lookup is `ensure_user_profile(account)` — a no-op when `user_id` is set, otherwise one `GET /2/users/by/username/{handle}` (persisting the same shape as the baked `0029` seed payloads: `user_id`, `display_name`, the whole `data` object as `raw_payload`, `resolved_at`). `sync_account_profiles()` is the bounded sweep over registry rows with a missing `user_id`, catching per-account `OfficialPostFetchError` and continuing — the one API path the webhook's `_resolve_account` fallback and the `x_webhook subscribe` command both rely on. Migration `0029` seeds the two agencies and `askrapidkl`/`myrapidkl` with their full user objects baked in (so staging/prod cost no API call) and moves `SocialMediaLink` onto a nullable `socmed_account` FK with a partial unique `(socmed_account, post_id)`; `link.socmed_account.handle` / `.platform` are now the read paths.

**Official-post export (`management/commands/export_official_posts.py`).** The read side of the same pipeline, and the only surface that *republishes* what ingestion stored. It selects `is_automated=True` (a community link is never part of the operator's archive, however much it looks like one), narrows by `--handle` / a UTC-day `--since`/`--until` window over `posted_at`, and writes the HuggingFace dataset schema — `post_id`, `posted_at`, `handle`, `text` (the verbatim `description`), `permalink`, plus `raw_payload` under `--include-raw`. Three properties are deliberate. (a) **Bounded memory**: rows arrive through `.only(...).iterator(chunk_size=500)`, i.e. a server-side cursor, and `raw_payload` is only added to the SELECT when it is actually exported. The single exception is `--push-to-hub`, because `Dataset.from_dict` takes the whole record set; that path materialises it once and reuses the list for the file write. (b) **Byte-stable output**: the column order is fixed and the sort key is `posted_at, post_id, id` — `id` is the extra tiebreak, because both leading keys are nullable and "same input → same output" needs a *total* order. (c) **No new dependency and no leaked secret**: `datasets` is lazy-imported inside the flag's own path (a missing package is an actionable `CommandError`, not a traceback, and `pyproject.toml` is unchanged), the token comes from `os.environ["HF_TOKEN"]` and is handed straight to `push_to_hub` without ever being printed, and `private=True` is unconditional because tweet content redistributed on the Hub is outside X's terms. Note that the exported `posted_at` is the stored column verbatim, and with `USE_TZ = False` that is naive **local** wall time (see `MISTAKES.md`) — the instant is right, the offset is missing, and the `--since`/`--until` bounds stay aware so the *window* is still a true UTC day.

**Webhook account attribution (`services/x_webhooks.py::_resolve_account`).** A delivery does not always name the account, and guessing is the one thing this path must never do — a permalink built from the wrong handle is a permanent public lie, while a dropped post is still recoverable by the polling fallback. Three rules, in order. (1) `includes.users[].username` matched on `payload.author_id` is the **only** attribution source: it arrives inside the signed body, so it cannot be forged without the signing secret, and it costs no network call. **The expansion lives on the event object — `data.includes` (`ActivityStreamResponse.data.includes`, per X's own OpenAPI schema) — not at the top level.** `_expansion_containers` searches `data` first and falls back to a top-level `includes` only for a differently-shaped delivery, so a stale top-level entry can never shadow the real one. Getting this wrong is silent: the registry fallback then runs, fails, and every post is counted `unresolved` (see `MISTAKES.md`). (2) Otherwise `_resolve_account` looks the account up **by `user_id` only** (`author_id` or the filter's `user_id`) in `SocMedAccount`; on a miss it runs the bounded `sync_account_profiles()` sweep once (the only API path, over registry rows with a missing user id) and retries the lookup. `author_id` deliberately **wins over** `filter.user_id`: a reply by another account carries the tracked account in the filter but a different author, and preferring the filter would misattribute it. Step (1) hands the full `includes.users` object to `resolve_account(..., create=True)`, which auto-registers an unknown author under `Unassigned` (empty `user_id` until `ensure_user_profile` resolves it) — no API call, and the delivery back-fills the row's `display_name` / `raw_payload` / `resolved_at`. (3) Still no match → counted as `unresolved`, warned about, dropped. Replies, quotes and reposts are all `post.create` and are all ingested, matching the polling path's `exclude_retweets=False`. The deprecated AAA `tweet_create_events` shape (no `data` envelope, `for_user_id` instead) is parsed defensively for the same reason.

**The webhook notification (`tasks.py::notify_official_post_links`).** Off-beat, dispatched by the view. It reuses `_notify_created_links` with the `WEBHOOK_HANDLE_LABEL = "webhook"` label rather than re-implementing a line of it, so the message text, the escaping, the truncation and the `TelegramSocialMediaLinkLog` join row (what makes reply-`/approve` work) are identical on both paths, and the `TELEGRAM_ADMIN_CHAT_ID`-blank guard is inherited rather than duplicated.

**Environment / settings matrix for the webhook.**

| Setting                           | Required for                | Effect of leaving it unset                                                                                                                   |
| --------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `X_API_OAUTH2_CLIENT_SECRET`      | CRC + delivery verification | Preferred when the app has one — X verifies the CRC answer against **this** secret. Obtain it from the developer portal (the app's OAuth 2.0 client) and configure the same value on X. |
| `X_API_SECRET_KEY`                | delivery verification       | Legacy OAuth 1.0 consumer secret ("API Secret Key"). Sufficient alone for a POST-verified app; a CRC-only config needs the OAuth 2.0 secret, or a re-register against whichever secret is configured. |
| `X_API_BEARER_TOKEN`              | `x_webhook` command         | Must be **App-only**; without it `register`/`subscribe` cannot run, though the receiver itself needs no bearer.                                    |
| `OFFICIAL_POST_INGESTION_ENABLED` | actual writes               | `false` → every delivery is acknowledged `{"status": "ignored"}`; nothing is written and X is not made to retry.                                  |
| `OFFICIAL_POST_POLLING_ENABLED`   | polling only                | Off by design — the webhook is the primary path.                                                                                             |
| `TELEGRAM_ADMIN_CHAT_ID`          | notifications               | Rows still ingest; nobody is told, and the log line says so.                                                                                 |

Troubleshooting order when a registration returns `CrcValidationFailed`: (1) is the endpoint reachable from the public internet over HTTPS with **no port** — X's fetcher will not follow a redirect; (2) does `GET ?crc_token=…` answer 200 in under 10 s; (3) is the configured secret the one X is signing with (prefer `X_API_OAUTH2_CLIENT_SECRET`) — the single most common cause, because a CRC signed with the legacy secret is rejected outright; (4) was the app restarted after the secret changed, since the values are read at import. `UrlValidationFailed` is the earlier gate: the URL itself is unacceptable.

**The approval gate — a defensive net (`schema/resolvers.py::get_public_social_media_links`).** The public feed excludes exactly `is_automated=True, status=PENDING_APPROVAL` — one `exclude()`, applied after the `status` filter and *before* the `totalCount` computation, so the count and the page always agree with what is published. Official ingestion **auto-publishes**: `ingest_posts` writes `LIVE`, so this exclusion catches only a legacy/imported automated row still parked in the old approval state — it is a safety net, not the publish path, and it guarantees an official post can never be public while unapproved even if one arrives from another writer. It is deliberately scoped to `is_automated` rather than to the status alone: a *community* link awaiting approval keeps today's behaviour and still appears with its pending icon, because hiding pending rows wholesale would silently hide hand-submitted reports too. The console queue (`socialMediaLinks`) and the mutation layer are untouched, so `status` still round-trips. The moderation surface is the console (`{settings.FRONTEND_BASE_URL}/console/insiden/links`, the URL the Telegram notification links to for *review*) and, for any legacy row still pending, replying `/approve` to the notification, which resolves through `TelegramSocialMediaLinkLog` and flips the row to `LIVE`; `/approve` on an already-`LIVE` row is a no-op that answers "Link is not awaiting approval." The same rule exists as a per-row predicate, `services/social_link_visibility.py::is_publicly_visible`, which is the single source of truth and is what the scalar's thread fields import; the two `.exclude()` calls here are its queryset-level twin and are deliberately **not** replaced by it (see the thread section above).

**The moderation gate — `HIDDEN` (`enums.py` + the same resolver).** `SocialMediaLinkStatus.HIDDEN` is the third member and the only one that is *not* a lifecycle stage: it records that an admin decided the row must not be seen. Three properties, each deliberate. (a) **It is a public-feed exclusion, not a lifecycle.** The resolver adds `queryset.exclude(status=HIDDEN)` *after* the optional `status` narrowing, so the exclusion defeats resurrection — asking for `status: HIDDEN` returns an empty page with `totalCount: 0` instead of handing back exactly what moderation removed. It is placed before the count for the same reason as the automated-pending gate: page and `totalCount` must agree. (b) **It applies to community rows too**, not just ingested ones — a hand-submitted link can be just as unwanted as a mis-scraped announcement, and the status is a moderation verdict rather than an ingestion fact. (c) **The `mine` branch is exempt** (`if not mine_requested:`). "My links" is the owner's own submission list, not a public feed, so someone whose submission was hidden can still see it and ask an admin about it; nobody else can. Correspondingly, `get_social_media_links` (the console queue) lists **all statuses by default** — `HIDDEN` included — because an admin has to be able to *find* a hidden row to un-hide it; its tri-state `hidden: Boolean` arg narrows that set without changing the default (omitted = all statuses, `true` = only `HIDDEN`, `false` = exclude `HIDDEN`), which powers the console's show/hide-hidden-entries filter. An admin update may set `HIDDEN` through `updateSocialMediaLink` (the enum arrives over the wire as `"HIDDEN"`); a non-admin edit is still forced back to `PENDING_APPROVAL`, so hiding stays an admin decision a submitter can neither set nor keep. Telegram `/approve` on a hidden row is a no-op path — it only acts on `PENDING_APPROVAL` rows and answers "Link is not awaiting approval."

**The event datetime — `SocialMediaLink.occurred_at` (`models.py`, `services/social_links.py`, `services/feed_links.py`, `services/official_posts.py`).** A submitted link carries **two** instants and they are not interchangeable. `created` is *when someone reported it* — the provenance column moderation reasons about ("is this fresh?"). `occurred_at` is *when the thing happened* — the instant the card renders and **every** ordering, window, day-grouping header and keyset cursor in the app is built on. Before this field existed a post published at 09:00 and reported at 09:40 displayed and sorted as 09:40, and a hand-typed event time was impossible.

- **NOT NULL, deliberately.** Keyset pagination orders by `-occurred_at, -id` and needs a *total* order; a nullable column would force `Coalesce` into every filter and `.order_by()`, and would sort NULLs **last** (the Postgres default) on a DESC scan instead of first. The index `socialmedialink_occurred_idx` is `("-occurred_at", "-id")` — `id` must be in it because it is the tie-break that makes the order total (`occurred_at` is non-null but not unique; an admin can group posts sharing a minute).
- **`posted_at` survives as read-only provider provenance.** Nothing may read-modify-write it. `export_official_posts` deliberately stays on that column: an archive's purpose is provider fidelity, and swapping it for `occurred_at` would change the meaning of every previously published export. On the automated path both are written from the single `RawPost.posted_at` inside `ingest_posts` — the *only* writer of `SocialMediaLink` on that path (beat tick, manual command, webhook all funnel through it), so the pair cannot drift.
- **Two different tri-states, read the call site before reusing the field.** `SocialMediaLinkWrite.occurred_at` is `datetime | None | _Unset`: on *update*, `UNSET` = leave alone / a datetime = set / **explicit `None` = reset to `link.created`** ("this happened when it was reported"), the documented escape hatch since the column cannot hold null; on *submit* the kwarg is omitted entirely so the model default fires (passing `None` would violate NOT NULL). `FeedLinkInput.occurred_at` is a flat two-state `Maybe` — that path only ever INSERTs, so "omitted" and "explicit null" have exactly one meaning — and a duplicate canonical URL short-circuits to the pre-existing row **without** touching its `occurred_at`, because the feed dedups on canonical URL and a re-submission is a second report *of the same event*.
- **Timezone.** With `USE_TZ = False` + `TIME_ZONE = "Asia/Kuala_Lumpur"` every stored datetime is naive **local** wall time, so `occurredAt` serialises with no offset and must never be `make_aware`/`astimezone`'d. Migration `0030`'s backfill is a **single SQL `Coalesce("posted_at", "created")`** for exactly that reason: a per-row Python loop would round-trip each value through the field adapter and shift every row by +08:00, invisibly at the UI's minute precision. See `MISTAKES.md` (2026-09-26 and 2026-09-30).

**The link tree — `SocialMediaLink.parent` / `position` (`models.py`, `services/social_link_threads.py`, `services/social_link_visibility.py`).** Related links form a **conversation**, and a conversation is an **ordered nested tree**, not a flat group. `SocialMediaLink` inherits `tree_queries.OrderableTreeNode`: `parent` is a `TreeNodeForeignKey("self", null=True, related_name="children", on_delete=SET_NULL)` and the library contributes `position` (the sibling sequence) plus `Meta.ordering = ["position"]`. A **root** is simply a row with `parent_id IS NULL`. Nothing about `tree_path` is stored — it is a recursive-CTE annotation recomputed per query, so the whole shape change is two columns plus a data pass (no redundant path column, no in-memory tree, no signal on every `save()`). Migration **`0031_socialmedialink_tree_parent_and_more.py`** runs `AddField(parent)` → `AddField(position)` → `AlterModelOptions` → a `RunPython` that converts any old `thread` groups and backfills `position` → `RemoveField(thread)`, in that order, because the backfill must read the final `parent_id` and `thread` must still exist when it does. Both halves of that `RunPython` finish with `SET CONSTRAINTS ALL IMMEDIATE`: `parent` and `thread` are `DEFERRABLE INITIALLY DEFERRED` FKs, so the re-parenting writes queue constraint-trigger events that only fire at COMMIT, and PostgreSQL refuses the following `RemoveField` DDL while they are pending (`ObjectInUse`). That abort is invisible on a never-threaded database — the dev DB had none — and real: it left staging at `0030` until the flush was added. It is reversible: Django replays the list backwards, so `thread` is re-added before the reverse `RunPython` can reconstruct it from `parent`, and `position` is zeroed (no pre-0031 column maps onto it). **The conversion is defensive code, not a data rescue** — the dev database held 44 links and **zero** group members, so the `thread_id` loop matches nothing there; it is written anyway because a data migration runs on every apply, not only the deploy it was authored against.

Five properties are load-bearing, and all five are enforced above the database:

- **No cycles, and the check is in `save()`, not `clean()`.** The library's loop protection lives in `TreeNode.clean()`, which only `full_clean()` calls — so a plain `link.parent = other; link.save()` writes a cycle *silently*, and the recursive CTE anchors on `parent_id IS NULL`, meaning the row is then unreachable from every tree query while `ancestors()` on it raises `DoesNotExist` (a 500, not an empty list). `SocialMediaLink.save()` therefore runs `_guard_tree_cycle` before delegating to `super()` and raises `ValidationError`, skipping the check when `update_fields` cannot name the FK — which means matching **both** of its spellings, because Django accepts a field's `name` or its `attname` and matches on either, so `save(update_fields=["parent_id"])` writes the `parent` column and must not slip past on the `"parent"`-only test. `bulk_create`/`bulk_update` bypass `save()`, so the service re-checks before any write and a rejected call writes nothing.
- **Depth <= `MAX_THREAD_DEPTH = 3`** (a root is depth 0, so four levels: root → sublink → sub-sublink → leaf). It is a **write-side** guard, not a read-side one: the read side is bounded by what the loader fetched, so a client may select `sublinks` deeper than we store and the extra levels simply come back empty. Clamping on read would invent rows. The bound is on the *resulting* depth and counts the subtrees that travel with the moved links, so re-parenting a deep branch under a shallow parent is rejected even when the parent alone looks fine.
- **`position` is assigned explicitly, never inferred.** The library's `save()` appends at `max(siblings) + 10` via a non-atomic read-then-write, **re-parenting never recomputes `position` at all**, and `bulk_create` bypasses it entirely — so a moved link would land at an arbitrary point and could collide with a sibling, making `ORDER BY position` non-deterministic. `_reindex_siblings` renumbers the whole affected sibling set to `10, 20, 30, …` on every structural write (arrivals first, then stayers in `(position, pk)`, with the vacated slot closed when a row leaves). Migration `0031` ranks with the same `× 10` stride, partitioned by `parent_id`, ordered by `(occurred_at, id)` — `occurred_at` for the chronological story, `id` because two links can share an instant and `RowNumber` over a non-total order hands ties arbitrary numbers.
- **Permission, all-or-nothing.** An admin may group, ungroup and reorder any links; a submitter only their own — checked per link on the whole selection **and on the named target parent**, rejecting the call as a unit. Deliberately checked on the *named* link rather than the conversation's root: a submitter who owns a sublink of a tree an admin created can deepen it, which is integrity and not confidentiality (no status changes, nothing unhidden, and they already see the rows they are editing). That trade disappears the moment submitters may nest under a conversation they did not contribute to — then the root has to be checked too.
- **`is_publicly_visible(link)` is the single source of truth** for the two moderation gates (`services/social_link_visibility.py`). The public feed keeps its queryset-level `.exclude()` pair as a deliberate **twin** — a per-row Python filter would not shrink `totalCount` or the fetched page, so page and count would stop agreeing — while the scalar applies the per-row predicate in exactly **one** function, `scalars.py::_publicly_visible_subtree`. Change the rule in the predicate first.

`on_delete=SET_NULL` is the matching non-destructive trade, and the **opposite** of the library's default (the inherited FK is hardcoded `CASCADE`): deleting a link **promotes** its sublinks to roots instead of cascade-deleting a group nobody asked to delete. It works because the library finds the tree by the field *name* `parent` and its CTE hardcodes `parent_id`, and it never inspects `on_delete` — so changing only `on_delete` is safe while **renaming the field would break the tree**. Pinned by `TreeDeletePromotionTests`, which asserts the subtree survives *and* stays reachable from its new root.

**The three mutations, and what each one actually does.**

| Mutation | Semantics |
| -------- | --------- |
| `groupSocialMediaLinks(linkIds, parentId: ID = null)` | **`parentId: null` STARTS A NEW CONVERSATION** — it does not make separate roots. The root is elected as the selected link with the smallest `(occurred_at, id)`, and every other selected link becomes its **direct child**, ordered by the same key. Supplying a `parentId` **nests the selection as direct children of that link**, root or sublink alike, one level deeper rather than being hoisted to the top — that is the behaviour nesting exists for, and it is why the argument is not called a thread id. Returns the **root of the affected conversation** in `id`; on the append path that is the target's own root, resolved only to be returned, never imposed on the write. |
| `ungroupSocialMediaLinks(linkIds)` | Clears `parent` on **exactly** the named links, promoting them to roots. **Deliberately not a cascade**: a link's own sublinks stay parented to it, so the branch simply continues under a representative that is now itself a root, and every intermediate state is a legal tree. A cascade would have to guess a new parent for an arbitrary subtree — a thread-topology decision the caller did not make. Ungrouping does **not** renumber the promoted roots, so two roots can legitimately share a `position`; `reorderSocialMediaLinks(parentId: null, …)` renumbers the whole root set and clears the tie. |
| `reorderSocialMediaLinks(linkIds, parentId: Maybe<ID>)` | A **permutation of one existing sibling set**, not a move: every id must already be a child of `parentId` (of `null`, when `parentId` is null), and anything else is rejected with a message pointing at `groupSocialMediaLinks`. The named order becomes `10, 20, 30, …` and un-named siblings keep their relative order after them. `parentId: null` reorders the **roots** — a real use (which link leads a conversation), not a degenerate one. |

`reorder` needs a `Maybe` on `parentId` while `group` does not, and the difference is the point. In `group`, omitted and explicit `null` mean the same thing — "no target, elect a root" — so a plain `ID = null` is the honest signature and a `Maybe` would advertise a third state that does not exist. In `reorder` they are **genuinely different requests**: an explicit `parentId: null` means "reorder the roots", while an omitted `parentId` names no sibling set at all and is rejected, because a plain nullable argument would silently answer the second with the first and reorder every root in the system. `reorder` exists because `position` is a stored, user-visible sequence and nothing else in the API can set it — `group` only ever appends a selection in `occurred_at` order, so the console could not put a link first, and a stored sequence nobody can set is not a feature. `position` is read-only over the wire: there is **no input** for it anywhere in the schema, on purpose, so a hand-numbered value cannot enter the store through the API.

**`sublinkCount` and `sublinks` are two reads of one fetch**, so the badge cannot disagree with the list it labels. `batch_load_sublink_subtrees` returns the node's whole subtree at any depth as a flat, depth-first list (`_depth_first` / `_sibling_groups` bucket on `parent_id` and sort by `position`, because `position` is a *sibling* order and a flat mixed-level queryset cannot express it in SQL); `sublinks` then filters `parent_id == self.id` out of that list and `sublinkCount` is its length. One loader call, one query per subtree rather than one per level, and the loader is deep-copied per request so a page asking for both fields on the same row pays the single query once.

⚠️ **`isThreadRoot` is a root marker, not a "has sublinks" marker, and it is true for an ordinary ungrouped link too.** `parentId is None` describes a link nothing points at, which is exactly as true of a lone link on the feed (a conversation of one) as of a real root — so it must never decide whether to draw the "N links" chip or the expand chevron. The only correct affordance test is **`sublinkCount > 0`** (`sublinks.length > 0`), which is false for a lone link and true for a root that has children.

⚠️ **`position` has four traps.** It is **sibling-scoped** — only comparable between two links with the same `parentId`, and since every root is one sibling set, `position` 10 under root A has nothing to do with `position` 10 under root B, so it is never a global tie-break and never a stable identity (`id` is; `(position, id)` is the order inside one sibling set). It is **gap-spaced (`10, 20, 30, …`), not an index** — `position` 40 does not mean "the fourth", and a client rendering an ordinal from it is wrong. It is **not guaranteed unique** — the service renumbers a whole set on every write, a promoted root can tie, and `0` is the column's own default, so it is what a row written outside `save()` carries. And it is the **only** ordering in the schema that is not `occurredAt DESC, id DESC`: the feed, the console queue and an incident's `links` all order on the event instant, and only `sublinks` follows `position`, so sorting a mixed list by it interleaves unrelated conversations.

⚠️ **A hidden middle node suppresses its visible descendants too.** `_publicly_visible_subtree` applies two rules in order: the shared predicate, and then *a descendant of a row that rule removed is removed too*. A hidden middle node stays in the tree, so its visible children are in the loader's rows — but no client can reach them through `sublinks`, because the node they hang off is not in the list the client walks. Counting them while the nesting cannot show them is exactly the badge/list disagreement this design exists to make impossible, and it would appear the first time an admin hid a node with children. The pass relies on the loader's depth-first ordering (a row's parent is judged before the row itself is reached), which is why the loader sorts the way it does.

**Why the feed paginates over roots (`collapseThreads`) rather than grouping client-side.** Under `occurred_at` ordering a conversation's descendants are **not adjacent** — an admin can nest a 09:00 post under an 11:00 post, and between them sit whatever else happened, including sublinks of *other* conversations. A flat page is therefore not a superset of whole conversations: a descendant's root may not even be on the page, so no post-processing of one page can reconstruct the grouping. Paginating roots and nesting the subtree is the only shape in which "every conversation that starts here is fully shown" is true — and with nesting, "fully shown" also means **every level** of it, which is why the read side fetches a whole subtree in one query rather than a level at a time. The accepted coupling: **a conversation is public iff its root is public**, which is why the gates are queryset-level and see the root row — hiding a root hides its whole subtree on a collapsed surface. The console surfaces `sublinkCount` so an admin can see what a moderation decision will take with it before making it, and `mine` is never collapsed (a personal list).

⚠️ **The time windows widen to the whole subtree; moderation stays root-only, and the asymmetry is deliberate.** `currentServiceDayOnly` / `lastWeekOnly` admit a collapsed card if the root **or any of its descendants, at any depth** occurred at/after the bound (`_event_window`), and the `lastWeekOnly` **upper** bound is subtree-aware in the same way (`_event_window_before`: a card is excluded when the root **or any descendant at any depth** occurred at/after today's midnight), while visibility and `status` are still decided on the root alone. Both choices fail safe for their own question: a window asks "what happened in this window" and a conversation is in it if any part of it was, whereas a moderation gate asks "may this be shown" and the cautious answer for a shared object is that hiding any representative removes the whole group. Conflating them would either leak a hidden descendant into a day-grouped feed or drop a just-reported link from today's activity. Nesting is what makes the split non-negotiable: the distance between the row that is moderated and the row that happened is no longer bounded by one hop, so no single shared rule could serve both questions.

This is **not** a rare corner, and it is the trap to know before touching the window flags: grouping elects the *earliest* link as root so conversations read oldest-first, so descendants are LATER than the root by construction — meaning any conversation that opened before the window and got a follow-up inside it has a root outside the window and a descendant inside it, at depth 1 or at depth 2+. Resolved on the root, the whole conversation vanished from the day's feed and with it the follow-up, because the collapsed surface renders the root. Making `occurredAt` **editable** added the mirror case: an admin can now move a descendant *earlier* than its root, so "the root is the earliest event" stopped being an invariant. The accepted cost of the fix is cosmetic — a root admitted only via a descendant renders with the root's *older* `occurredAt`, so a "today" feed can show a card stamped before today. Re-grouping the conversation over the whole set re-elects the earliest link and fixes the stamp.

**Behaviour note — `lastWeekOnly` closes at today 00:00 by default.** The effective range is `[six days ago 00:00, today 00:00)`, so a "previous days" view never shows the day in progress; `displayTodayInLastWeek: true` restores the inclusive seven-day window, the exclusion is applied **before** `totalCount` (so the count reports what the page can show), and it is ignored entirely when `lastWeekOnly` is `false`.

**Two implementation traps in the window subquery** (`schema/resolvers.py::_in_window_subtree_roots`, which is what replaced the previous correlated `EXISTS`). A correlated subquery would have to re-run the recursion **per candidate root** (a `Recursive Union` nested inside `EXISTS(SubPlan)`, i.e. a full table scan as the CTE anchor, once per row), so the subquery is deliberately **un-correlated** and folded in as `pk__in` — one walk, hashed, probed by the outer scan. And the library's documented performance lever `tree_filter`/`tree_exclude` is **rejected**: it restricts the base table *before* the recursion, so filtering to the in-window rows deletes an out-of-window root from the CTE, the recursion cannot reach below it, each orphan becomes a root of its own truncated tree, and `tree_path[1]` returns the descendant instead of the conversation's root — the widening then silently stops working. The subquery is therefore unfiltered by design (no status, no moderation excludes, no `incident_id`): the price is that the walk covers the table rather than the page, bounded by the table and paid only when a window flag and `collapse_threads` are both on. See `MISTAKES.md` (2026-10-01) for the `__tree` identifier coupling and the `.distinct()`-not-`.order_by()` rule.

**Draft-revision flow (`services/incidents.py`).** A non-admin edit of a non-DRAFT incident creates a DRAFT revision (`parent_incident=incident`, `created_by` = the **editing actor**, not the original author). The one-open-draft rule rejects a second actor's edit while a draft is open ("An unapproved edit draft already exists for this incident. Please allow the draft to approve before proceeding."); the same actor's re-edit resumes their own draft in place. Admin approval of a revision (`approve_incident`) merges fields, M2Ms, chronologies and medias into the parent atomically, then hard-deletes the draft. Admin edits apply in place (Option A); an author editing their own `PENDING_APPROVAL` row also applies in place (spec C1). `delete_incident` resolves pending children first — open draft revisions and `PENDING_APPROVAL`/`PENDING_DELETION` chronologies are soft-deleted so no orphaned pending child survives a parent deletion (safedelete's `SOFT_DELETE` does not cascade by design).

**Aggregation logic (`schema/resolvers.py`).** `get_calendar_incidents_by_severity_count` is the only hand-written aggregate resolver. It first narrows to incidents overlapping the window, `aaggregate`s the earliest `start_datetime`, then builds a `pendulum` interval clamped to `min(end_date, today)` and constructs **one conditional `Count(filter=Q(…))` per bucket × severity (× long/short term in `DAY` mode)** — up to `days × 3 × 2` conditional aggregates in a single query — then reconstructs dates by string-splitting the aggregate alias on `_`. Efficient in round-trips (one query), but the generated SQL grows linearly with the requested range; the 60-day `GraphQLError` in the filter is the de-facto guard, and it does not apply to this resolver.

**Batching.** `IncidentContextLoaders` holds six loaders, registered under key `"incident"` in `rosak/context.py` and `deepcopy`'d per request: `medias_from_calendar_incident_loader` (walks `CalendarIncidentMedia` with `select_related("media")`, returns a **`set`** per key even though the field is typed `List[MediaScalar]` — media are silently de-duplicated and the `CalendarIncidentMedia.timestamp` ordering is discarded), `vote_scores` / `vote_breakdown` / `user_vote_value` (generic `common.Vote` counts per ContentType), and `incident_links` (batches the first page of per-incident link connections, `first+1` rows per incident to compute `has_next_page`; ordered `-occurred_at, -id`), plus **`sublink_subtrees`** — keyed by link id, returning that link's whole **publicly-visible-ready** subtree at any depth as a FLAT list in depth-first, siblings-in-`position` order, and **never visibility-filtered** (that is the data layer; the moderation rule lives once in `services/social_link_visibility.py`). It costs **one existence probe for the whole batch plus one `descendants()` CTE per key that has children**, so a page of N rows costs `1 + (rows with children)` queries — never one per tree level — and the answer is assembled **positionally** from `keys` so a duplicate key is answered at its own position. With deliberately **no** sibling count loader: `sublinkCount` and `sublinks` are two reads of this one cached call, which makes the badge structurally incapable of disagreeing with the list it labels. `rosak/context.py` registers the whole dict, so a new key needs no change there.

## 🧩 Extension Points & Hooks

- **The abstract triad.** `IncidentAbstractModel` + `IncidentAbstractScalar` + `IncidentAbstractFilter` is a deliberate three-layer template: adding a new incident target (e.g. `AssetIncident` for `operation.Asset` lifts/escalators) means one model subclass, one scalar subclass, one filter subclass, one field on `IncidentScalars`, and one inline in `operation/admin.py` — no changes to existing code.
- **`IncidentMutations`** is the wired write seam — it composes `IncidentCrudMutations`, `ChronologyMutations`, `VoteMutations`, `SocialMediaLinkMutations` and `ExtractionMutations` into `rosak.schema.Mutation`. New write paths add a mixin here.
- **`services/social_link_threads.py` is the hierarchy seam.** Everything about *what a conversation is* (no cycles, `MAX_THREAD_DEPTH`, root election by `(occurred_at, id)`, explicit `position` renumbering) and *who may nest* (admin any / submitter own, checked on the selection **and** the named target parent, all-or-nothing) lives in one `transaction.atomic()` block per entry point — `group_social_media_links`, `ungroup_social_media_links`, `reorder_social_media_links`. A new hierarchy affordance — auto-suggest, bulk regroup, move-to-neighbour — is a new entry point onto those blocks, never a new ad-hoc `UPDATE`, and it must assign `position` explicitly (see the link-tree section). Likewise `services/social_link_visibility.py::is_publicly_visible` is the one place the public-visibility rule may be changed, and any new moderation gate must call it rather than re-deriving the pair of `.exclude()`s; on the read side the rule is applied in exactly one function, `scalars.py::_publicly_visible_subtree`.
- **`CalendarIncidentCategory`** is a free-form tag table — new taxonomies (signalling, power, rolling stock, weather, industrial action) need data rows, not migrations. It also backs `SocialMediaLink.categories`.
- **`IncidentContextLoaders`** dict — new batched fields plug in by adding one key; the per-request `deepcopy` in `rosak/context.py` handles isolation.
- **Status enums as lifecycle hooks.** `CalendarIncidentStatus` (with `PENDING_DELETION` reserved for the chronology mark-for-delete flow) and `SocialMediaLinkStatus` are the approval-lifecycle vocabulary; new states are enum additions plus the matching service gate. `PassengerStatus` is likewise additive — a new member appends to the enum and its consolidation rank.
- **`SIGNATURE_CANDIDATES` is the signed-request verification seam.** A tuple of `(header name, settings attribute)` pairs, tried in order and each gated on its secret actually being configured — adding X's next signing scheme is one tuple entry plus one env var, with no change to the view or the ingest path. The CRC answer, by contrast, deliberately uses only the *first* configured candidate (`_preferred_signing_secret`), because X verifies the CRC against exactly one secret.
- **`EVENT_POST_CREATE` + `WebhookIngestResult` are the event seam.** Subscribing to more `*.create` / `*.delete` types means teaching `_create_items` the new envelope; every unrecognised type is already acknowledged and ignored, so nothing breaks in the meantime. The counters enforce `ingested + skipped + unresolved == events`, so a redelivery that creates nothing is visible as `ingested=0` rather than as silence.
- **`_expansion_containers` is the envelope-location seam.** It returns the objects an `includes` expansion may hang off, most-current first, so both the Activity API's `data.includes` and a top-level `includes` resolve with one precedence rule instead of a second ad-hoc lookup. A future X envelope that nests the event one level deeper is a one-line change here — and the ordering is load-bearing: earlier entries win, so a stale copy can never override the authoritative one.
- **Pulse calibration knobs.** The consolidation window (`WINDOW_MINUTES=15`), the minimum report count (`MIN_REPORTS=1`), the service-day start/length (`DAY_START_HOUR=3`, `HOURS_IN_SERVICE_DAY=24`) and the pulse-link cap (`_MAX_PULSE_LINKS=5`) are module constants in `incident/services/line_status.py`; `canonicalize_url`'s `TRACKING_PARAMS` set is the one place to teach the feed a new tracking parameter.
- **`impact_factor` is a reserved hook with zero consumers.** Its `help_text` specifies "scores to deduct from a full score of 100 per day, prorated by usual service hours when consolidating", but no code in the repo — `chartography` included — ever reads it. The reliability-index feature it was designed for is unbuilt; the column, the admin field, the GraphQL field and the ordering key are all already in place.
- **`CalendarIncidentChronology.source_url` + the `/upload/` → `common.tasks` → `CalendarIncidentMedia` pipeline** form a ready evidence-attachment channel (with EXIF timestamp capture) for any future citation or verification workflow.
- **`inaccurate` / `long_term` booleans** are presentation flags the frontend already honours — usable as confidence or provisional markers by automated writers without new schema.
- **`ordered_model`** gives editors manual precedence control (`move_up_down_links`) independent of chronology, useful for pinning headline incidents.

## 💡 Potential Feature Opportunities

1. **"All incidents in this disruption" — one FK to join the two tiers.** The single highest-leverage schema change in the app. Today `VehicleIncident`/`StationIncident` and the `CalendarIncident` they belong to have no relation at all, so a reader viewing a network disruption cannot see which individual trains or stations were affected, and an editor logging a vehicle fault cannot attach it to the open disruption. A nullable `calendar_incident` FK on `IncidentAbstractModel` (`on_delete=SET_NULL`, `related_name="%(class)s_set"`) gives `CalendarIncidentScalar` rollup lists and each asset-level scalar a parent link, following the existing abstract-triad pattern exactly. For a community rail platform this is the difference between a calendar of headlines and a genuinely queryable incident record — and it also makes `impact_factor` attributable to specific rolling stock.
   **Readiness:** `Not ready` — the FK does not exist; correlation today is implicit via shared vehicle/station plus `date` proximity. An implementer adds the field to `IncidentAbstractModel` in `/home/kwongtn/rosak_backend/incident/models.py` (both concrete models inherit it), generates the next free `incident/migrations/00NN_…` (**`0032`**, since `0031` replaced `thread` with the `parent` tree; nullable, so no backfill is forced), adds `calendar_incident: Optional["CalendarIncidentScalar"]` to `VehicleIncident`/`StationIncident` and the reverse `List[...]` fields to `CalendarIncidentScalar` in `incident/schema/scalars.py`, a nested filter in `incident/schema/filters.py`, and `autocomplete_fields = ("calendar_incident",)` on the inlines in `incident/admin.py` — `CalendarIncidentAdmin` already declares `search_fields`, so admin autocomplete works with no extra setup.

2. **Per-line reliability score — pure arithmetic over `impact_factor`.** `impact_factor` is a `Decimal(5,2)` on `CalendarIncident` whose `help_text` already specifies the exact formula ("Scores to deduct from full score of 100 per day. Publishing a monthly reliability figure per line is the flagship number a community transit-watch site exists to produce.

(a) The "prorated by usual service hours" half of the spec has no data source: `operation.Line` carries only `official_numbering`, `code`, `display_name`, `display_color`, `status` and `telegram_channel_id` — no service-hours field — so either v1 uses whole-day denominators or a `service_start_time`/`service_end_time` pair is added to `operation/models.py`. (b) The resolver must traverse `CalendarIncident.lines` (reverse accessor `Line.incidents`, set in migration `0013`), **not** `operation.Line.calendar_incidents`, which is the dead duplicate join table admin never writes to. ## 💡 Potential AI Feature Opportunities

1. **Auto-draft calendar incidents from operator announcements.** `telegram_provider` already ingests channel messages and `operation.Line` carries `telegram_channel_id`, yet nothing bridges into `incident`. An LLM extraction step could propose a `CalendarIncident` (start/end datetime, `severity`, affected `lines`/`stations`, `title`, `brief`) plus successive `CalendarIncidentChronology` rows straight from raw announcements, writing through the now-wired `IncidentMutations` (the `extractDataFromUrl` mutation already demonstrates the pattern) and setting `inaccurate=True` as a built-in low-confidence / awaiting-review marker. Chronology `source_url` gives citation for free.
2. **Impact scoring and severity assistance.** With `impact_factor` present but unconsumed, a model trained on historical span duration, affected-line count, chronology length and severity could suggest an `impact_factor` at admin-save time and roll it into a per-line reliability index for `chartography` — turning a dormant column into the reliability metric it was specified as, without a migration.
3. **Semantic clustering, dedup and cross-tier linkage.** `title`/`brief`/`details`/chronology text plus the `CalendarIncidentCategory` M2M make this app embedding-ready: suggest categories automatically, detect that a newly filed incident duplicates an open one, support natural-language calendar search ("signalling failures on the Kelana Jaya line last monsoon"), and — most valuably — propose links between the disconnected tiers, inferring which `VehicleIncident`/`StationIncident` ledger rows belong to which `CalendarIncident` from shared asset and date proximity. That inferred relation is exactly the FK the schema currently lacks.
