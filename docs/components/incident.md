# Component: incident

## 📌 Purpose & Scope

- **Core Responsibility:** Owns the _disruption record_ for the rail network — two structurally independent tiers: (a) a per-asset **incident ledger** (`VehicleIncident`, `StationIncident`) that annotates a single vehicle or station with dated, editorially-ordered events, and (b) a network-level **calendar incident** (`CalendarIncident`) representing a service disruption spanning a datetime range, multiple lines/stations/vehicles, with a chronology of updates, markdown detail, media evidence and a reliability `impact_factor`. It is the "what went wrong, where and when" layer sitting on top of `operation`'s reference data. It also owns the crowd-sourced **feed**: `SocialMediaLink` submissions (canonical-URL dedup + votes) and `LineStatusReport` passenger-load reports, which consolidate into a per-line pulse consumed by `operation.Line`.
- **Domain/Layer:** Django persistence + business-logic layer (GIS-enabled via `PointField`), surfaced as a **read/write** Strawberry GraphQL API. `views.py` holds the X Activity API webhook receiver (`/webhooks/x-api`, the primary official-post ingestion path) and there is no `urls.py` of its own — the webhook route is registered directly in `rosak/urls.py`. No signals. Writes flow through the GraphQL mutations (community reporting + admin approval), the `/upload/` → `common` media pipeline, the webhook receiver, and the Celery tasks in `incident/tasks.py` (scheduled in `rosak/celery.py`, plus the webhook's off-beat `notify_official_post_links`).

## 🔌 Interface & Data Flow

### Inputs (GraphQL arguments, filters, orderings, signals)

Root query fields are contributed by `IncidentScalars` (mixed into `rosak.schema.Query`): `vehicleIncidents`, `stationIncidents`, `calendarIncidents`, `calendarIncidentsBySeverityCount`, `pendingCalendarIncidents` (admin queue), `socialMediaLinks` (admin queue), `publicSocialMediaLinks` (cursor-paginated connection), `calendarIncidentCategories`, `calendarIncidentHistory` (logged-in), `lineStatusHistory`, `lineStatusReports`.

| Filter (`incident/schema/filters.py`) | Notable inputs                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------- |
| `IncidentAbstractFilter`              | plain (undecorated) mixin: `id`, `date`, `severity`, `is_last`                     |
| `VehicleIncidentFilter`               | mixin + nested `vehicle: VehicleFilter` (imported from `operation.schema.filters`) |
| `StationIncidentFilter`               | mixin + nested `station: StationFilter` (same cross-app import)                    |
| `CalendarIncidentFilter`              | `id`, `severity`, plus hand-written `ongoing` and `date` `filter_field`s           |

- `CalendarIncidentFilter.date` takes a `CalendarIncidentDateFilter`. `range` and `exact` use inclusive **interval-overlap** predicates: start ≤ window end AND (end ≥ window start OR no end). Open-ended incidents must still start by the window end; combine `OR: { ongoing: true }` to retain the pinned section regardless of the viewed month. `month.exact` / `year.exact` remain legacy calendar-part filters. The range width is enforced with a `GraphQLError` ("date range cannot exceed 60 days") — a proper validation error, not a bare assert. One sharp edge remains: the `month` branch does `month__lte=value.month.exact + 1`, an off-by-one that assumes a 0-indexed (JS) month from the client.
- `CalendarIncidentFilter.ongoing` maps `true`/`false` to `Q(end_datetime__isnull=…)` — a client can ask for "what's currently broken" without guessing a date window.
- Ordering: `CalendarIncidentOrder` — `id`, `order`, `impact_factor`, `start_datetime`, `end_datetime`. The two asset-level incident lists expose **no** ordering input.
- Resolver arguments: `calendarIncidentsBySeverityCount(start_date, end_date, group_by: GroupByEnum)` where `GroupByEnum` is `DAY | MONTH`; `publicSocialMediaLinks(incident_id, line_id, first, after, mine, status, current_service_day_only)` — the optional `status: SocialMediaLinkStatus` narrows the feed to one approval status (omitted, both `LIVE` and `PENDING_APPROVAL` are returned), and `currentServiceDayOnly: Boolean! = false` restricts it to links created at/after the current service day's 03:00 start (`services/line_status.py::service_day_start`, the same helper behind `lineStatusHistory`); **automatically ingested rows (`is_automated=True`) are excluded while they are `PENDING_APPROVAL`**, so an official announcement only becomes public once an admin approves it — community-submitted pending links still surface, unchanged, with their pending icon; **`HIDDEN` rows are excluded unconditionally** on the public branch, so an explicit `status: HIDDEN` returns an empty page rather than resurrecting them (the `mine` branch is deliberately exempt — an owner still sees their own hidden submission); `socialMediaLinks(search, category_id, completed, line_id, vehicle_id, station_id, created_after, created_before)`; `calendarIncidentHistory(id, limit)`.

- **HTTP (non-GraphQL).** `GET/POST /webhooks/x-api` (name `x_api_webhook`), registered in `rosak/urls.py` inside an `apps.is_installed("incident")` block and wrapped in `csrf_exempt` — the request is authenticated by X's HMAC signature over the raw body, not by a session, and X sends no CSRF token and cannot be given one. Full contract in **Internal State & Logic** below.
- `submitFeedLink(input: FeedLinkInput)` returns a `FeedLinkPayload` (`ok`, `link`, `isDuplicate`, `duplicateOfId`, `userVote`) — the feed path goes straight to `LIVE` for any logged-in user, dedups on the canonical URL and auto-upvotes the existing row on a duplicate. `submitLineStatusReport(input: LineStatusReportInput)` returns `GenericMutationReturn` and creates one standalone `LineStatusReport`. `updateSocialMediaLink` is `IsLoggedIn` (the service layer enforces ownership: admin edits land `LIVE`, a submitter's edit is forced back to `PENDING_APPROVAL`).

- **Service-level permission matrix** (the GraphQL `IsLoggedIn` gate is the floor; finer rules live in `incident/services/`):

| Operation | Non-admin | Admin |
| --------- | --------- | ----- |
| Edit a LIVE incident | any logged-in → creates a DRAFT revision (`parent_incident`), one-open-draft rule rejects a second actor's draft with the spec message; OCC `expected_version` fires on every path | in-place |
| Edit DRAFT / own PENDING_APPROVAL | author → in-place | in-place |
| Delete incident | author only when `DRAFT` or `PENDING_APPROVAL` | any |
| Delete chronology | author when the chronology or its parent incident is `DRAFT`/`PENDING_APPROVAL` | any |
| Request chronology deletion | author-or-admin, LIVE chronologies only → `PENDING_DELETION` | — |
| Approve / reject chronology deletion | — | soft-deletes / reverts to LIVE |

- **Signals: none defined.** Audit trail is `django-simple-history` (`HistoricalRecords(cascade_delete_history=False)` on `CalendarIncident` and `CalendarIncidentChronology`) plus `TimeStampedModel`'s `created`/`modified`.

### Outputs (GraphQL types, events)

Types in `incident/schema/scalars.py`:

- `IncidentAbstractScalar` — plain `@strawberry.type` base (`id`, `date`, `severity`, `order`, `title`, `brief`, `is_last`). Note `location` is **commented out**: the GIS point is captured in admin but never exposed to clients.
- `VehicleIncident` / `StationIncident` — subclass the base, add `vehicle: Vehicle` / `station: Station` (cross-app `operation` scalars). Their `medias` M2M is also commented out.
- `CalendarIncidentScalar` — the rich type: datetime range, `severity`, `status` (`CalendarIncidentStatus`), `title`, `brief`, `details`, `impact_factor: float`, `version` (OCC counter), `long_term`, `inaccurate`, `user` (the `created_by` author, `Optional[UserScalar]`), plus `lines: [Line]`, `vehicles: [Vehicle]`, `stations: [Station]`, `categories: [CalendarIncidentCategoryScalar]`, `chronologies: [CalendarIncidentChronologyScalar]`, and resolved fields:
  - `medias` → batched through the `medias_from_calendar_incident_loader` DataLoader, lazily typed against `common.schema.scalars.MediaScalar`.
  - `vote_score` / `vote_breakdown` / `user_vote` → batched through the `vote_scores` / `vote_breakdown` / `user_vote_value` DataLoaders (generic `common.Vote` via ContentType).
  - `links(first: Int = 10, after: String)` → a `SocialMediaLinkConnection` of per-incident submitted links, newest first (`created DESC, id DESC`), keyset-cursor format identical to the root `publicSocialMediaLinks` resolver so a nested cursor can be handed to the root query for continuation pages. Page one is served by the `incident_links` DataLoader (one query for a feed of cards); continuation pages query directly (per-parent cursors cannot be batched). `totalCount` is the incident's full link count, unaffected by `after` (a separate `acount()` before the page branch).
  - `has_details` → `@sync_to_async` emptiness check on `details`.
  - `last_updated` → `@sync_to_async`; **re-fetches the row**, then `.count()` + an ordered slice on `chronologies` to take `max(incident.modified, latest_chronology.modified)`. Three extra queries per node, invisible to `DjangoOptimizerExtension` — the app's main N+1 hotspot.
- `CalendarIncidentChronologyScalar` — `id`, `order`, `status` (`CalendarIncidentStatus`, independent of the parent), `indicator`, `datetime`, `content`, `source_url`, a back-reference to `CalendarIncidentScalar`, and the same three vote fields (`vote_score` / `vote_breakdown` / `user_vote`) as the incident scalar.
- `CalendarIncidentHistoryEntryScalar` — one diffed `django-simple-history` record: `timestamp` (`history_date`, UTC), `actor` (nullable display identity, `None` for system/anonymous), `change_type` (`"created"` / `"updated"` / `"deleted"`), `changed_fields` (model field names from `diff_against`, internal history fields excluded). Served by `calendarIncidentHistory(id, limit=50)`, latest-first, `IsLoggedIn`.
- `SocialMediaLinkScalar` — `id`, `url`, `normalizedUrl` (tracking-stripped canonical form, computed on save), `title`, `description`, `status` (`SocialMediaLinkStatus`: `LIVE` / `PENDING_APPROVAL` / `HIDDEN`), `created`, `completed`, `completed_at`, `is_automated` → **`isAutomated: Boolean!`** (true only for rows written by official-post ingestion — the "Official" capture badge; false for every hand-submitted link, legacy rows included), `completed_by` (resolved display name — nickname or `firebase_id[:8]` shortId), `user`, `categories`, `lines`, `vehicles`, `stations`, and `voteScore` / `userVote` (batched through the `vote_scores` / `user_vote_value` loaders). `SocialMediaLinkEdge` / `SocialMediaLinkPageInfo` / `SocialMediaLinkConnection` wrap it for cursor pagination; the connection also carries `totalCount: Int!` (whole filtered set — including the automated-pending exclusion below — `after`-independent; computed with a separate `queryset.acount()` before the cursor filter, so every call costs one extra count query, and the empty anonymous-`mine` page reports `0`); `FeedLinkPayload` is the `submitFeedLink` return type (`ok`, `link`, `isDuplicate`, `duplicateOfId`, `userVote`).
- `LineStatusReportScalar` — a single `LineStatusReport` read row: `id`, `status` (`PassengerStatus`), `delayMinutes`, `notes`, `created`, `user`, and `stations: [Station!]!` (the report's station tags, `[]` when unattached), served cursor-paginated by `lineStatusReports(lineId, first, after)`.
- `CalendarIncidentGroupByDateSeverityScalar` — flat aggregate row (`severity`, `date`, `count`, `is_long_term`) for calendar heat-map rendering; `is_long_term` is `null` in `MONTH` mode.
- **Celery (`incident/tasks.py`, registered in `rosak/celery.py`'s beat schedule):** `purge_soft_deleted_incidents` (hard-deletes safedelete-soft-deleted incidents past 90 days, `crontab(hour="3", minute="0")`), `purge_rejected_incidents` (hard-deletes `REJECTED` incidents unchanged for 30 days, `crontab(hour="3", minute="30")`) and `ingest_official_posts` (pulls the tracked official X accounts into `SocialMediaLink`, `crontab(minute="*/5")` with `{"expires": 240, "time_limit": 180}` — `expires` sits under the 5-minute period so a wedged run is never re-dispatched on top of itself). The ingestion task **ships inert**: it returns `{"skipped": "disabled"}` unless `OFFICIAL_POST_INGESTION_ENABLED` and `{"skipped": "no_token"}` without `X_API_BEARER_TOKEN`, so the beat entry is safe to deploy before the API tier is provisioned. It never calls `self.retry` and never sleeps — a per-handle `OfficialPostFetchError` is logged and the remaining handles still run, so one bad handle cannot stall the tick. **Phase 2 — the admin notification:** after each handle's `ingest_posts`, one message per entry in `summary.created_ids` goes to `settings.TELEGRAM_ADMIN_CHAT_ID` (the whole pass is skipped when that setting is blank, and re-scrapes announce nothing because a skipped/duplicate post has no id in `created_ids`). The message carries the handle, the post's own time, the **verbatim** `description` body, a permalink and a `{settings.FRONTEND_BASE_URL}/console/insiden/links` deep link, truncated so the *escaped* text stays inside Telegram's 4096-character limit, and every dynamic value is `html.escape`d — `raw_payload` is never rendered. It is sent through `telegram_provider.utils.send_message(..., return_log=True)`, whose returned audit log is joined to the new row via `TelegramSocialMediaLinkLog`, which is what makes the message reply-approvable through the existing `/approve` handler. Notification failure is contained per link (warn + continue): a dead-lettered or raising send costs the announcement, not the ingest, and the row still lands `PENDING_APPROVAL` for console approval. A per-handle `notified` counter is reported in the result dict and the structured log line (it is deliberately **not** in `INGEST_COUNTERS`, so it does not roll up into the task's top-level totals). The app is also a _target_ of `common.tasks.cleanup_temporary_media_task`.
- **Management commands (`incident/management/commands/`):**
  - `ingest_official_posts.py` — the manual backfill for the same ingestion path — `--handle` (repeatable), `--since` / `--until` (whole UTC days, mutually exclusive with the `since_id` fast path), `--limit`, `--fixture` and `--dry-run`. A fetch or ingest failure becomes a `CommandError` (non-zero exit); `--fixture` is rejected when a date window is given, and a multi-handle run is rejected as ambiguous when the handle came from settings rather than `--handle`.
  - `x_webhook.py` — the operator's lever for the webhook lifecycle, because a URL that merely exists receives nothing: X only pushes to a **registered** webhook that has answered a CRC challenge, and only for accounts with an **activity subscription** pointing at it. `register URL` (POST `/2/webhooks`), `list`, `delete ID`, `revalidate ID` (PUT, re-triggers CRC) and `subscribe HANDLE...` (one `post.create` subscription per handle, `@` stripped). Registration requires public **HTTPS with no port**, reachable from X's servers; a failure surfaces as the API's own `CrcValidationFailed` / `UrlValidationFailed` error `title`, which is the only part of the upstream body this command quotes — a `CommandError` message gets pasted into chats, so it carries the status code and that title and nothing else. `--webhook-id` is optional for `subscribe`: omitted, the registered webhooks are listed and there must be **exactly one**, because guessing between several would attach subscriptions to the wrong endpoint and stay silent until events stop arriving. Handle→user-id resolution reuses `official_posts._resolve_user_id` (imported **inside** `_user_id`, so the seam is patchable at its source), so a subscription can never be created against a different id than ingestion polls for. Authorised by `X_API_BEARER_TOKEN`, which must be **App-only** and is unrelated to the signing secrets — those stay server-side and are never sent to X from here. The token is read from settings, used only in an `Authorization` header, and never printed.
  - `export_official_posts.py` — the **read** side (spec Phase 3): exports every `is_automated=True` row as a JSONL or CSV archive — `--handle` (repeatable, `@` tolerated), `--since` / `--until` (inclusive UTC days over `posted_at`), `--format jsonl|csv`, `--output PATH|-`, `--include-raw`, `--dry-run`, `--push-to-hub REPO_ID`. The columns are the HuggingFace dataset schema in a fixed order (`post_id`, `posted_at` = the stored column's ISO-8601 form, `handle`, `text` = the verbatim `description`, `permalink`, plus `raw_payload` under `--include-raw`), ordered `posted_at, post_id, id` so two exports of unchanged rows are byte-identical. Rows stream out of `.only(...).iterator(chunk_size=500)` — a cursor, never a full-table list — and `--push-to-hub` is the one documented exception (`Dataset.from_dict` wants the whole set), lazy-importing `datasets` so no dependency is added, reading `HF_TOKEN` from the environment (never printed) and always pushing `private=True`. `--output -` sends the summary line to **stderr** so the data stream stays pipeable; `--dry-run` reports the exact count and writes nothing.

## ⚙️ Internal State & Logic

**Severity + status enums in `incident/enums.py`, all stored as `TextChoicesField` (or plain `CharField(max_length=16, choices=…)` for the legacy severity fields):**

| Enum | Values | Applies to |
| ---- | ------ | ---------- |
| `IncidentSeverity` | `CRITICAL`, `TRIVIA`, `STATUS` | asset-level tier — mixes true severity with a non-severity "status annotation" bucket |
| `CalendarIncidentSeverity` | `MAJOR` (line-wide breakage, crashes), `MINOR` (single-vehicle), `OTHERS` | network-level tier |
| `CalendarIncidentChronologyIndicator` | `GREEN`, `RED`, `BLUE`, `GRAY` | timeline dot colour |
| `CalendarIncidentStatus` | `DRAFT`, `PENDING_APPROVAL`, `LIVE`, `REJECTED`, `PENDING_DELETION` | shared by incident + chronology status fields; `PENDING_DELETION` is only ever set on chronologies (mark-for-delete flow) |
| `SocialMediaLinkStatus` | `LIVE`, `PENDING_APPROVAL`, `HIDDEN` | link lifecycle — deliberately not reusing the incident enum. `HIDDEN` is a **moderation decision**, not a lifecycle stage: the row is never returned by the public feed (not by default, not via an explicit `status: HIDDEN` filter), the console still lists it so an admin can un-hide it, and the owner still sees it under `mine` |
| `IngestPlatform` | `X` | source platform of an automatically ingested post on `SocialMediaLink`; one member by design — a second platform is a new member plus its own fetch function, never a speculative placeholder |
| `PassengerStatus` | `NORMAL`, `BUSY`, `CROWDED`, `EXTREMELY_CROWDED`, `BACKLOGGED`, `DELAYED`, `DISRUPTED` | crowd-reported passenger load on a `LineStatusReport`; declaration order doubles as the consolidation severity rank (`NORMAL` least → `DISRUPTED` most) |

The two severity vocabularies are **not interchangeable**, and there is no mapping between them. `CalendarIncidentChronology.indicator`'s `help_text` documents a fifth "Loading" state that does not exist in the enum — a client-side-only value that will never validate.

**Incident vs. calendar-incident.** `IncidentAbstractModel` (`TimeStampedModel + OrderedModel`) carries `date` (a plain `DateField` — day granularity), `severity`, optional `location: PointField`, short `title`/`brief`, `is_last`, and an explicit editable `order`. `VehicleIncident` and `StationIncident` set `order_with_respect_to` to their parent, so each vehicle/station owns an independently ordered history, and `is_last` flags the row that represents the asset's _current_ state. `CalendarIncident` instead models a _span_ (`start_datetime`, nullable `end_datetime` = ongoing) with `long_term` (collapse to start date only in month view), `inaccurate` (display an "unverified" badge), a `Decimal(5,2)` `impact_factor`, a `TextField` `brief`, markdown `details`, fan-out M2Ms, a `status` lifecycle, a `version` OCC counter, and a nullable `parent_incident` FK for the draft-revision flow. Its narrative lives in `CalendarIncidentChronology` rows (`related_name="chronologies"`, ordered per incident), each with its own independent `status`. **There is no FK between the two tiers** — a `VehicleIncident` cannot be linked to the `CalendarIncident` it belongs to; correlation is only implicit via shared vehicle/station and date.

**Feed links and the passenger pulse (`services/feed_links.py`, `services/line_status.py`, `services/urls.py`).** `SocialMediaLink` is the community feed item: `normalized_url` is recomputed on every `save()` from `canonicalize_url` (tracking params such as `fbclid`/`gclid`/`igshid`/`si`/`utm_*` stripped, host lowercased, fragment and trailing slash dropped) and cross-row dedup is enforced in `submit_feed_link` (global canonical match → auto-upvote the existing row; otherwise create `LIVE`), **not** by a DB constraint. It is also the target table of automated ingestion (below), which is why it now also carries a nullable `platform` + `post_id` pair, `posted_at`, `is_automated`, `source_handle` and the untouched `raw_payload` — all `null`/default for community-submitted links, and **not exposed on `SocialMediaLinkScalar` yet** except `is_automated` (`isAutomated`), which is the only one of them a client needs. `LineStatusReport` is a single passenger-load observation on a line (`status`, optional `delay_minutes` / `notes` / `stations`, optional `link`); `consolidate` reduces the last 15 minutes of reports to one `PassengerStatus` by weighted majority — a report linked to a social entry is weighted `1 + max(net_vote, 0)`, an unlinked report `1`, ties broken by recency then enum rank — and carries the full per-status count dict alongside the winner, which `load_line_pulses` batches per line in 3 flat queries for `operation.Line` (`passengerStatusCounts`). `load_line_status_history` backs `lineStatusHistory(lineId, dayStartHour)`: a line with at least one report that service day gets the full 24 hourly buckets (03:00 → 02:00, empty hours zero-filled), while a line with no report returns `[]` — the client's "No data" state. Each bucket carries `hourStart` / `hourEnd` / `count` (the hour's total) / `dominantStatus` plus `statusCounts` (`[PassengerStatusCount!]!` — the existing `operation.schema.scalars.PassengerStatusCount` reused rather than an incident-local parallel type: the per-status tally in enum order with zero counts omitted, summing to `count`; `[]` for an empty hour) for the frontend's stacked bars. `fetch_page_title` is a best-effort `httpx` `<title>` scrape that collapses every failure to `""`.

**X Activity API webhook receive (`views.py` + `services/x_webhooks.py`).** The **primary** ingestion path; the 5-minute poll (`OFFICIAL_POST_POLLING_ENABLED`, default off) is the fallback. One endpoint serves both of X's contracts, and it is a plain synchronous Django view rather than DRF — there is no authentication, no serializer and no content negotiation, only an HMAC over the raw bytes and a fast 200. Everything cryptographic and everything that touches the database lives in the service; `views.py` is transport only (validate, delegate, acknowledge).

| Request  | Response                                                                                                                                                              |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`    | 200 `{"response_token": "sha256=…"}`; 400 when `crc_token` is missing/blank; 503 when no signing secret is configured (operator-fixable, so not worth an X retry) |
| `POST`   | 200 `{"status": "ok", "events", "ingested", "skipped", "unresolved"}`; 400 non-JSON / not an object / rejected payload; 403 absent-or-wrong signature; 503 no secret or no system author |
| anything | 405 with `Allow: GET, POST`                                                                                                                                              |

Four choices are the load-bearing ones. (a) **The signature covers raw bytes.** `request.body` is read once and handed to `verify_webhook_signature(headers, raw_body)`; the parsed JSON is never re-serialized to recompute a digest, because that silently breaks the moment X changes its key order. Both candidate header/secret pairs in `SIGNATURE_CANDIDATES` (`X-Twitter-Webhooks-Signature-OAuth2` × `X_API_OAUTH2_CLIENT_SECRET`, and legacy `X-Twitter-Webhooks-Signature` × `X_API_SECRET_KEY`) are accepted, but a candidate is only tried when its secret is *configured* — comparing against an empty secret would accept a signature anyone can compute. Comparison is `hmac.compare_digest` over UTF-8 bytes on both sides, so a non-ASCII header cannot turn a 403 into a 500. (b) **The CRC is signed with the preferred secret only** (`X_API_OAUTH2_CLIENT_SECRET` when set), because that is the one X verifies the answer against; the legacy header is *not* tried for CRC, so `crc_response_token` matching a different construction than X expects is the first thing to check when registration returns `CrcValidationFailed`. (c) **Acknowledgement is the design constraint.** X retries anything outside 2xx and expects an answer within 10 seconds, so the DB write is inline (it is a handful of `get_or_create`s) and the Telegram notification is handed to the `notify_official_post_links` Celery task — a broker outage is logged and still answered 200, because the row is already committed and approvable from the console. `OfficialPostIngestError` (missing system author) is the one case that returns 503, so X may redeliver rather than the post being silently dropped. (d) **Two non-errors are acknowledged, not refused**: the master switch `OFFICIAL_POST_INGESTION_ENABLED=false` answers `{"status": "ignored", "reason": "ingestion disabled"}`, and a non-`post.create` event (e.g. `post.delete`) answers 200 having done nothing — a switch that is off, or an event we will never act on, is not X's fault, and erroring would only earn a retry storm.

**Official-post ingestion (`services/official_posts.py`).** Pulls the handles in `OFFICIAL_POST_HANDLES` from the X API and lands them as `SocialMediaLink` rows authored by the `system:official-ingest` service user. Three deliberate choices bound the blast radius. (a) **Bounded, single-pass paging**: `fetch_user_posts` walks `next_token` backwards with a hard `_MAX_PAGES = 10` ceiling, so a handle whose timeline is re-scraped from scratch cannot fan out into hundreds of requests; `since_id=latest_post_id(handle)` is the cheap path used by the periodic task. (b) **Two failure vocabularies**: `OfficialPostFetchError` (transport / token / rate limit, message sanitised so a bearer token can never reach a log line) is caught per handle and the tick continues, while `OfficialPostIngestError` from `get_system_author()` propagates — a missing service user is a deployment fault, not a per-handle hiccup. (c) **Idempotency is structural**: the partial `UniqueConstraint` on `(platform, post_id)` is a DB-level backstop, and the service re-reads on `IntegrityError` rather than taking an advisory lock. `ingest_posts` returns an `IngestSummary(fetched, created, skipped, duplicate_urls, created_ids=())` and takes an additive keyword-only `dry_run: bool = False` that counts would-be creations inside the same code path and writes nothing. `load_fixture_posts(path, *, handle=None)` is the injectable offline source: `--fixture` plus `--dry-run` gives a network-free import rehearsal, and the shipped JSON fixtures under `incident/fixtures/` are what the test suite replays.**Official-post export (`management/commands/export_official_posts.py`).** The read side of the same pipeline, and the only surface that *republishes* what ingestion stored. It selects `is_automated=True` (a community link is never part of the operator's archive, however much it looks like one), narrows by `--handle` / a UTC-day `--since`/`--until` window over `posted_at`, and writes the HuggingFace dataset schema — `post_id`, `posted_at`, `handle`, `text` (the verbatim `description`), `permalink`, plus `raw_payload` under `--include-raw`. Three properties are deliberate. (a) **Bounded memory**: rows arrive through `.only(...).iterator(chunk_size=500)`, i.e. a server-side cursor, and `raw_payload` is only added to the SELECT when it is actually exported. The single exception is `--push-to-hub`, because `Dataset.from_dict` takes the whole record set; that path materialises it once and reuses the list for the file write. (b) **Byte-stable output**: the column order is fixed and the sort key is `posted_at, post_id, id` — `id` is the extra tiebreak, because both leading keys are nullable and "same input → same output" needs a *total* order. (c) **No new dependency and no leaked secret**: `datasets` is lazy-imported inside the flag's own path (a missing package is an actionable `CommandError`, not a traceback, and `pyproject.toml` is unchanged), the token comes from `os.environ["HF_TOKEN"]` and is handed straight to `push_to_hub` without ever being printed, and `private=True` is unconditional because tweet content redistributed on the Hub is outside X's terms. Note that the exported `posted_at` is the stored column verbatim, and with `USE_TZ = False` that is naive **local** wall time (see `MISTAKES.md`) — the instant is right, the offset is missing, and the `--since`/`--until` bounds stay aware so the *window* is still a true UTC day.

**Webhook handle attribution (`services/x_webhooks.py::_resolve_handle`).** A delivery does not always name the account, and guessing is the one thing this path must never do — a permalink built from the wrong handle is a permanent public lie, while a dropped post is still recoverable by the polling fallback. Three rules, in order. (1) `includes.users[].username` matched on `payload.author_id` is the **only** attribution source: it arrives inside the signed body, so it cannot be forged without the signing secret, and it costs no network call. **The expansion lives on the event object — `data.includes` (`ActivityStreamResponse.data.includes`, per X's own OpenAPI schema) — not at the top level.** `_expansion_containers` searches `data` first and falls back to a top-level `includes` only for a differently-shaped delivery, so a stale top-level entry can never shadow the real one. Getting this wrong is silent: the reverse lookup then runs, fails offline, and every post is counted `unresolved` (see `MISTAKES.md`). (2) Otherwise `resolve_handle_for_user_id(author_id or filter.user_id)` walks `OFFICIAL_POST_HANDLES` and compares against each handle's cached X id. `author_id` deliberately **wins over** `filter.user_id`: a reply by another account carries the tracked account in the filter but a different author, and preferring the filter would misattribute it. (3) No match → counted as `unresolved`, warned about, dropped. A per-handle `OfficialPostFetchError` inside the reverse lookup is caught and logged per handle so one bad lookup does not abort the others, and **only positive matches are cached** — a miss is never written, so widening `OFFICIAL_POST_HANDLES` later needs no cache flush. Replies, quotes and reposts are all `post.create` and are all ingested, matching the polling path's `exclude_retweets=False`. The deprecated AAA `tweet_create_events` shape (no `data` envelope, `for_user_id` instead) is parsed defensively for the same reason.

**The webhook notification (`tasks.py::notify_official_post_links`).** Off-beat, dispatched by the view. It reuses `_notify_created_links` with the `WEBHOOK_HANDLE_LABEL = "webhook"` label rather than re-implementing a line of it, so the message text, the escaping, the truncation and the `TelegramSocialMediaLinkLog` join row (what makes reply-`/approve` work) are identical on both paths, and the `TELEGRAM_ADMIN_CHAT_ID`-blank guard is inherited rather than duplicated.

**Environment / settings matrix for the webhook.**

| Setting                           | Required for                | Effect of leaving it unset                                                                                                                   |
| --------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `X_API_OAUTH2_CLIENT_SECRET`      | CRC + delivery verification | Preferred when the app has one — X verifies the CRC answer against **this** secret. Obtain it from the developer portal (the app's OAuth 2.0 client) and configure the same value on X. |
| `X_API_SECRET_KEY`                | delivery verification       | Legacy OAuth 1.0 consumer secret ("API Secret Key"). Sufficient alone for a POST-verified app; a CRC-only config needs the OAuth 2.0 secret, or a re-register against whichever secret is configured. |
| `X_API_BEARER_TOKEN`              | `x_webhook` command         | Must be **App-only**; without it `register`/`subscribe` cannot run, though the receiver itself needs no bearer.                                    |
| `OFFICIAL_POST_INGESTION_ENABLED` | actual writes               | `false` → every delivery is acknowledged `{"status": "ignored"}`; nothing is written and X is not made to retry.                                  |
| `OFFICIAL_POST_POLLING_ENABLED`   | polling only                | Off by design — the webhook is the primary path.                                                                                             |
| `TELEGRAM_ADMIN_CHAT_ID`          | notifications               | Rows still ingest; nobody is told, and the log line says so.                                                                                 |

Troubleshooting order when a registration returns `CrcValidationFailed`: (1) is the endpoint reachable from the public internet over HTTPS with **no port** — X's fetcher will not follow a redirect; (2) does `GET ?crc_token=…` answer 200 in under 10 s; (3) is the configured secret the one X is signing with (prefer `X_API_OAUTH2_CLIENT_SECRET`) — the single most common cause, because a CRC signed with the legacy secret is rejected outright; (4) was the app restarted after the secret changed, since the values are read at import. `UrlValidationFailed` is the earlier gate: the URL itself is unacceptable.

**The approval gate (`schema/resolvers.py::get_public_social_media_links`).** Automatically ingested posts land `PENDING_APPROVAL` by design, so the public feed excludes exactly `is_automated=True, status=PENDING_APPROVAL` — one `exclude()`, applied after the `status` filter and *before* the `totalCount` computation, so the count and the page always agree with what is published. It is deliberately scoped to `is_automated` rather than to the status alone: a *community* link awaiting approval keeps today's behaviour and still appears with its pending icon, because hiding pending rows wholesale would silently hide hand-submitted reports too. The admin queue (`socialMediaLinks`) and the mutation layer are untouched, so `status` still round-trips. The moderation surface is the console (`{settings.FRONTEND_BASE_URL}/console/insiden/links`, the URL the Telegram notification links to) plus replying `/approve` to the notification, which resolves through `TelegramSocialMediaLinkLog` and flips the row to `LIVE`.

**The moderation gate — `HIDDEN` (`enums.py` + the same resolver).** `SocialMediaLinkStatus.HIDDEN` is the third member and the only one that is *not* a lifecycle stage: it records that an admin decided the row must not be seen. Three properties, each deliberate. (a) **It is a public-feed exclusion, not a lifecycle.** The resolver adds `queryset.exclude(status=HIDDEN)` *after* the optional `status` narrowing, so the exclusion defeats resurrection — asking for `status: HIDDEN` returns an empty page with `totalCount: 0` instead of handing back exactly what moderation removed. It is placed before the count for the same reason as the automated-pending gate: page and `totalCount` must agree. (b) **It applies to community rows too**, not just ingested ones — a hand-submitted link can be just as unwanted as a mis-scraped announcement, and the status is a moderation verdict rather than an ingestion fact. (c) **The `mine` branch is exempt** (`if not mine_requested:`). "My links" is the owner's own submission list, not a public feed, so someone whose submission was hidden can still see it and ask an admin about it; nobody else can. Correspondingly, `get_social_media_links` (the console queue) is left unfiltered, because an admin has to be able to *find* a hidden row to un-hide it. An admin update may set `HIDDEN` through `updateSocialMediaLink` (the enum arrives over the wire as `"HIDDEN"`); a non-admin edit is still forced back to `PENDING_APPROVAL`, so hiding stays an admin decision a submitter can neither set nor keep. Telegram `/approve` on a hidden row is a no-op path — it only acts on `PENDING_APPROVAL` rows and answers "Link is not awaiting approval."

**Draft-revision flow (`services/incidents.py`).** A non-admin edit of a non-DRAFT incident creates a DRAFT revision (`parent_incident=incident`, `created_by` = the **editing actor**, not the original author). The one-open-draft rule rejects a second actor's edit while a draft is open ("An unapproved edit draft already exists for this incident. Please allow the draft to approve before proceeding."); the same actor's re-edit resumes their own draft in place. Admin approval of a revision (`approve_incident`) merges fields, M2Ms, chronologies and medias into the parent atomically, then hard-deletes the draft. Admin edits apply in place (Option A); an author editing their own `PENDING_APPROVAL` row also applies in place (spec C1). `delete_incident` resolves pending children first — open draft revisions and `PENDING_APPROVAL`/`PENDING_DELETION` chronologies are soft-deleted so no orphaned pending child survives a parent deletion (safedelete's `SOFT_DELETE` does not cascade by design).

**Aggregation logic (`schema/resolvers.py`).** `get_calendar_incidents_by_severity_count` is the only hand-written aggregate resolver. It first narrows to incidents overlapping the window, `aaggregate`s the earliest `start_datetime`, then builds a `pendulum` interval clamped to `min(end_date, today)` and constructs **one conditional `Count(filter=Q(…))` per bucket × severity (× long/short term in `DAY` mode)** — up to `days × 3 × 2` conditional aggregates in a single query — then reconstructs dates by string-splitting the aggregate alias on `_`. Efficient in round-trips (one query), but the generated SQL grows linearly with the requested range; the 60-day `GraphQLError` in the filter is the de-facto guard, and it does not apply to this resolver.

**Batching.** `IncidentContextLoaders` holds five loaders, registered under key `"incident"` in `rosak/context.py` and `deepcopy`'d per request: `medias_from_calendar_incident_loader` (walks `CalendarIncidentMedia` with `select_related("media")`, returns a **`set`** per key even though the field is typed `List[MediaScalar]` — media are silently de-duplicated and the `CalendarIncidentMedia.timestamp` ordering is discarded), `vote_scores` / `vote_breakdown` / `user_vote_value` (generic `common.Vote` counts per ContentType), and `incident_links` (batches the first page of per-incident link connections, `first+1` rows per incident to compute `has_next_page`).

**Known integrity risks.**

- **Duplicate Line↔CalendarIncident relation.** `CalendarIncident.lines` (`related_name="incidents"`, set in migration `0013`) and `operation.Line.calendar_incidents` are two _separate_ join tables. Admin's `filter_horizontal` edits the former; the GraphQL `Line.calendarIncidents` field reads the latter — so that field is expected to be permanently empty. Consolidating on `Line.incidents` (the reverse accessor) is the fix.
- `order` is redeclared on the concrete models as `editable=True` with a `# Remove after beta` comment still outstanding.

**Schema evolution (28 migrations, `0001_initial` Aug 2022 → `0028` 2026):** `0002`/`0003` add `is_last` and its constraints; `0004` introduces the whole calendar tier (`CalendarIncident`, `CalendarIncidentCategory`, `CalendarIncidentChronology`); `0005`–`0008` churn on `severity` choices and `brief`; `0009`/`0012` add and adjust chronology `source_url`; `0010` adds `inaccurate`; `0011` replaces the plain media M2M with the `CalendarIncidentMedia` through-model; `0013` adds `related_name="incidents"`; `0014` adds `SocialMediaLink`; `0015`/`0016` add safedelete `deleted` fields; `0017` converts status fields to `TextChoicesField`; `0018`/`0019` wire `SocialMediaLink.user`/`completed_by`; `0020` adds `CalendarIncident.created_by`; `0021` fixes the `StationIncident` unique constraint (adds the missing `condition=Q(is_last=True)`); `0022` adds link `description` + `status`; `0023` adds `PENDING_DELETION` to the shared status enum; `0024` adds `SocialMediaLink.normalized_url` (with a reversible batched backfill) and the `LineStatusReport` model; `0025` re-backfills `normalized_url` for rows the first backfill missed (reversible via `RunPython.noop`); `0026` adds the `incident_li_line_id_828375_idx` composite index on `LineStatusReport(line, created)`; `0027` adds the official-post ingestion fields (`platform`, `post_id`, `posted_at`, `is_automated`, `source_handle`, `raw_payload`) with the partial unique constraint on `(platform, post_id)`, and seeds the `system:official-ingest` service user that `get_system_author()` resolves; `0028` is choices-only — it adds `hidden` to the `status` choices (no data migration, no column change).

## 🧩 Extension Points & Hooks

- **The abstract triad.** `IncidentAbstractModel` + `IncidentAbstractScalar` + `IncidentAbstractFilter` is a deliberate three-layer template: adding a new incident target (e.g. `AssetIncident` for `operation.Asset` lifts/escalators) means one model subclass, one scalar subclass, one filter subclass, one field on `IncidentScalars`, and one inline in `operation/admin.py` — no changes to existing code.
- **`IncidentMutations`** is the wired write seam — it composes `IncidentCrudMutations`, `ChronologyMutations`, `VoteMutations`, `SocialMediaLinkMutations` and `ExtractionMutations` into `rosak.schema.Mutation`. New write paths add a mixin here.
- **`CalendarIncidentCategory`** is a free-form tag table — new taxonomies (signalling, power, rolling stock, weather, industrial action) need data rows, not migrations. It also backs `SocialMediaLink.categories`.
- **`IncidentContextLoaders`** dict — new batched fields plug in by adding one key; the per-request `deepcopy` in `rosak/context.py` handles isolation.
- **Status enums as lifecycle hooks.** `CalendarIncidentStatus` (with `PENDING_DELETION` reserved for the chronology mark-for-delete flow) and `SocialMediaLinkStatus` are the approval-lifecycle vocabulary; new states are enum additions plus the matching service gate. `PassengerStatus` is likewise additive — a new member appends to the enum and its consolidation rank.
- **`SIGNATURE_CANDIDATES` is the signed-request verification seam.** A tuple of `(header name, settings attribute)` pairs, tried in order and each gated on its secret actually being configured — adding X's next signing scheme is one tuple entry plus one env var, with no change to the view or the ingest path. The CRC answer, by contrast, deliberately uses only the *first* configured candidate (`_preferred_signing_secret`), because X verifies the CRC against exactly one secret.
- **`EVENT_POST_CREATE` + `WebhookIngestResult` are the event seam.** Subscribing to more `*.create` / `*.delete` types means teaching `_create_items` the new envelope; every unrecognised type is already acknowledged and ignored, so nothing breaks in the meantime. The counters enforce `ingested + skipped + unresolved == events`, so a redelivery that creates nothing is visible as `ingested=0` rather than as silence.
- **`_expansion_containers` is the envelope-location seam.** It returns the objects an `includes` expansion may hang off, most-current first, so both the Activity API's `data.includes` and a top-level `includes` resolve with one precedence rule instead of a second ad-hoc lookup. A future X envelope that nests the event one level deeper is a one-line change here — and the ordering is load-bearing: earlier entries win, so a stale copy can never override the authoritative one.
- **Pulse calibration knobs.** The consolidation window (`WINDOW_MINUTES=15`), the minimum report count (`MIN_REPORTS=1`), the service-day start/length (`DAY_START_HOUR=3`, `HOURS_IN_SERVICE_DAY=24`) and the pulse-link cap (`_MAX_PULSE_LINKS=5`) are module constants in `incident/services/line_status.py`; `canonicalize_url`'s `TRACKING_PARAMS` set is the one place to teach the feed a new tracking parameter.
- **`impact_factor` is a reserved hook with zero consumers.** Its `help_text` specifies "scores to deduct from a full score of 100 per day, prorated by usual service hours when consolidating", but no code in the repo — `chartography` included — ever reads it. The reliability-index feature it was designed for is unbuilt; the column, the admin field, the GraphQL field and the ordering key are all already in place.
- **`CalendarIncidentChronology.source_url` + the `/upload/` → `common.tasks` → `CalendarIncidentMedia` pipeline** form a ready evidence-attachment channel (with EXIF timestamp capture) for any future citation or verification workflow.
- **`inaccurate` / `long_term` booleans** are presentation flags the frontend already honours — usable as confidence or provisional markers by automated writers without new schema.
- **`ordered_model`** gives editors manual precedence control (`move_up_down_links`) independent of chronology, useful for pinning headline incidents.

## 💡 Potential Feature Opportunities

A nullable `calendar_incident` FK on `IncidentAbstractModel` (`on_delete=SET_NULL`, `related_name="%(class)s_set"`) gives `CalendarIncidentScalar` rollup lists and each asset-level scalar a parent link, following the existing abstract-triad pattern exactly. For a community rail platform this is the difference between a calendar of headlines and a genuinely queryable incident record — and it also makes `impact_factor` attributable to specific rolling stock.
   **Readiness:** `Not ready` — the FK does not exist; correlation today is implicit via shared vehicle/station plus `date` proximity. An implementer adds the field to `IncidentAbstractModel` in `/home/kwongtn/rosak_backend/incident/models.py` (both concrete models inherit it), generates `incident/migrations/0024_…` (nullable, so no backfill is forced), adds `calendar_incident: Optional["CalendarIncidentScalar"]` to `VehicleIncident`/`StationIncident` and the reverse `List[...]` fields to `CalendarIncidentScalar` in `incident/schema/scalars.py`, a nested filter in `incident/schema/filters.py`, and `autocomplete_fields = ("calendar_incident",)` on the inlines in `incident/admin.py` — `CalendarIncidentAdmin` already declares `search_fields`, so admin autocomplete works with no extra setup.
