# Component: incident

## 📌 Purpose & Scope

- **Core Responsibility:** Owns the _disruption record_ for the rail network — two structurally independent tiers: (a) a per-asset **incident ledger** (`VehicleIncident`, `StationIncident`) that annotates a single vehicle or station with dated, editorially-ordered events, and (b) a network-level **calendar incident** (`CalendarIncident`) representing a service disruption spanning a datetime range, multiple lines/stations/vehicles, with a chronology of updates, markdown detail, media evidence and a reliability `impact_factor`. It is the "what went wrong, where and when" layer sitting on top of `operation`'s reference data.
- **Domain/Layer:** Django persistence + business-logic layer (GIS-enabled via `PointField`), surfaced as a **read/write** Strawberry GraphQL API. No `views.py` content (0 bytes), no `urls.py`, no signals. Writes flow through the GraphQL mutations (community reporting + admin approval), the `/upload/` → `common` media pipeline, and two Celery purge tasks (`incident/tasks.py`, scheduled in `rosak/celery.py`).

## 🔌 Interface & Data Flow

### Inputs (GraphQL arguments, filters, orderings, signals)

Root query fields are contributed by `IncidentScalars` (mixed into `rosak.schema.Query`): `vehicleIncidents`, `stationIncidents`, `calendarIncidents`, `calendarIncidentsBySeverityCount`, `pendingCalendarIncidents` (admin queue), `socialMediaLinks` (admin queue), `publicSocialMediaLinks` (cursor-paginated connection), `calendarIncidentCategories`, `calendarIncidentHistory` (logged-in).

| Filter (`incident/schema/filters.py`) | Notable inputs                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------- |
| `IncidentAbstractFilter`              | plain (undecorated) mixin: `id`, `date`, `severity`, `is_last`                     |
| `VehicleIncidentFilter`               | mixin + nested `vehicle: VehicleFilter` (imported from `operation.schema.filters`) |
| `StationIncidentFilter`               | mixin + nested `station: StationFilter` (same cross-app import)                    |
| `CalendarIncidentFilter`              | `id`, `severity`, plus hand-written `ongoing` and `date` `filter_field`s           |

- `CalendarIncidentFilter.date` takes a `DateFilterLookup[date]` and translates `range` / `exact` / `month.exact` / `year.exact` into an **interval-overlap** `Q` (a null `end_datetime` means "still ongoing" and always matches). The range width is enforced with a `GraphQLError` ("date range cannot exceed 60 days") — a proper validation error, not a bare assert. One sharp edge remains: the `month` branch does `month__lte=value.month.exact + 1`, an off-by-one that assumes a 0-indexed (JS) month from the client.
- `CalendarIncidentFilter.ongoing` maps `true`/`false` to `Q(end_datetime__isnull=…)` — a client can ask for "what's currently broken" without guessing a date window.
- Ordering: `CalendarIncidentOrder` — `id`, `order`, `impact_factor`, `start_datetime`, `end_datetime`. The two asset-level incident lists expose **no** ordering input.
- Resolver arguments: `calendarIncidentsBySeverityCount(start_date, end_date, group_by: GroupByEnum)` where `GroupByEnum` is `DAY | MONTH`; `publicSocialMediaLinks(incident_id, line_id, first, after, mine)`; `socialMediaLinks(search, category_id, completed, line_id, vehicle_id, station_id, created_after, created_before)`; `calendarIncidentHistory(id, limit)`.
- **Mutations** — `IncidentMutations` composes five mixins (all in `incident/schema/mutations/`):

| Mixin | Mutations | Permission |
| ----- | --------- | ---------- |
| `IncidentCrudMutations` (`incidents.py`) | `createCalendarIncident`, `updateCalendarIncident`, `submitCalendarIncident`, `deleteCalendarIncident` | `IsLoggedIn` |
| | `approveCalendarIncident`, `rejectCalendarIncident` | `IsAdmin` |
| `ChronologyMutations` (`chronologies.py`) | `createChronology`, `updateChronology`, `reorderChronology`, `deleteChronology`, `requestChronologyDeletion` | `IsLoggedIn` |
| | `approveChronology`, `approveChronologyDeletion`, `rejectChronologyDeletion` | `IsAdmin` |
| `VoteMutations` (`interactions.py`) | `upvote`, `downvote`, `removeVote`, `upvoteChronology`, `downvoteChronology`, `removeChronologyVote` | `IsLoggedIn` |
| `SocialMediaLinkMutations` (`interactions.py`) | `submitSocialMediaLink` | `IsLoggedIn` |
| | `markSocialMediaLinkCompleted`, `updateSocialMediaLink` | `IsAdmin` |
| `ExtractionMutations` (`interactions.py`) | `extractDataFromUrl` | `IsLoggedIn` |

- **Service-level permission matrix** (the GraphQL `IsLoggedIn` gate is the floor; finer rules live in `incident/services/`):

| Operation | Non-admin | Admin |
| --------- | --------- | ----- |
| Edit a LIVE incident | any logged-in → creates a DRAFT revision (`parent_incident`), one-open-draft rule rejects a second actor's draft with the spec message; OCC `expected_version` fires on every path | in-place |
| Edit DRAFT / own PENDING_APPROVAL | author → in-place | in-place |
| Delete incident | author only when `DRAFT` or `PENDING_APPROVAL` | any |
| Delete chronology | author when the chronology or its parent incident is `DRAFT`/`PENDING_APPROVAL` | any |
| Request chronology deletion | author-or-admin, LIVE chronologies only → `PENDING_DELETION` | — |
| Approve / reject chronology deletion | — | soft-deletes / reverts to LIVE |

- **Signals: none defined.** Audit trail is `django-simple-history` (`HistoricalRecords(cascade_delete_history=False)` on `CalendarIncident` and `CalendarIncidentChronology`) plus `TimeStampedModel`'s `created`/`modified`.

### Outputs (GraphQL types, events)

Types in `incident/schema/scalars.py`:

- `IncidentAbstractScalar` — plain `@strawberry.type` base (`id`, `date`, `severity`, `order`, `title`, `brief`, `is_last`). Note `location` is **commented out**: the GIS point is captured in admin but never exposed to clients.
- `VehicleIncident` / `StationIncident` — subclass the base, add `vehicle: Vehicle` / `station: Station` (cross-app `operation` scalars). Their `medias` M2M is also commented out.
- `CalendarIncidentScalar` — the rich type: datetime range, `severity`, `status` (`CalendarIncidentStatus`), `title`, `brief`, `details`, `impact_factor: float`, `version` (OCC counter), `long_term`, `inaccurate`, `user` (the `created_by` author, `Optional[UserScalar]`), plus `lines: [Line]`, `vehicles: [Vehicle]`, `stations: [Station]`, `categories: [CalendarIncidentCategoryScalar]`, `chronologies: [CalendarIncidentChronologyScalar]`, and resolved fields:
  - `medias` → batched through the `medias_from_calendar_incident_loader` DataLoader, lazily typed against `common.schema.scalars.MediaScalar`.
  - `vote_score` / `vote_breakdown` / `user_vote` → batched through the `vote_scores` / `vote_breakdown` / `user_vote_value` DataLoaders (generic `common.Vote` via ContentType).
  - `links(first: Int = 10, after: String)` → a `SocialMediaLinkConnection` of per-incident submitted links, newest first (`created DESC, id DESC`), keyset-cursor format identical to the root `publicSocialMediaLinks` resolver so a nested cursor can be handed to the root query for continuation pages. Page one is served by the `incident_links` DataLoader (one query for a feed of cards); continuation pages query directly (per-parent cursors cannot be batched).
  - `has_details` → `@sync_to_async` emptiness check on `details`.
  - `last_updated` → `@sync_to_async`; **re-fetches the row**, then `.count()` + an ordered slice on `chronologies` to take `max(incident.modified, latest_chronology.modified)`. Three extra queries per node, invisible to `DjangoOptimizerExtension` — the app's main N+1 hotspot.
- `CalendarIncidentChronologyScalar` — `id`, `order`, `status` (`CalendarIncidentStatus`, independent of the parent), `indicator`, `datetime`, `content`, `source_url`, a back-reference to `CalendarIncidentScalar`, and the same three vote fields (`vote_score` / `vote_breakdown` / `user_vote`) as the incident scalar.
- `CalendarIncidentHistoryEntryScalar` — one diffed `django-simple-history` record: `timestamp` (`history_date`, UTC), `actor` (nullable display identity, `None` for system/anonymous), `change_type` (`"created"` / `"updated"` / `"deleted"`), `changed_fields` (model field names from `diff_against`, internal history fields excluded). Served by `calendarIncidentHistory(id, limit=50)`, latest-first, `IsLoggedIn`.
- `SocialMediaLinkScalar` — `id`, `url`, `title`, `description`, `status` (`SocialMediaLinkStatus`: `LIVE` / `PENDING_APPROVAL`), `created`, `completed`, `completed_at`, `completed_by` (resolved display name — nickname or `firebase_id[:8]` shortId), `user`, `categories`, `lines`, `vehicles`, `stations`. `SocialMediaLinkEdge` / `SocialMediaLinkPageInfo` / `SocialMediaLinkConnection` wrap it for cursor pagination.
- `CalendarIncidentGroupByDateSeverityScalar` — flat aggregate row (`severity`, `date`, `count`, `is_long_term`) for calendar heat-map rendering; `is_long_term` is `null` in `MONTH` mode.
- **Celery (`incident/tasks.py`, registered in `rosak/celery.py`'s beat schedule):** `purge_soft_deleted_incidents` (hard-deletes safedelete-soft-deleted incidents past 90 days, `crontab(hour="3", minute="0")`) and `purge_rejected_incidents` (hard-deletes `REJECTED` incidents unchanged for 30 days, `crontab(hour="3", minute="30")`). The app is also a _target_ of `common.tasks.cleanup_temporary_media_task`.

## ⚙️ Internal State & Logic

**Severity + status enums in `incident/enums.py`, all stored as `TextChoicesField` (or plain `CharField(max_length=16, choices=…)` for the legacy severity fields):**

| Enum | Values | Applies to |
| ---- | ------ | ---------- |
| `IncidentSeverity` | `CRITICAL`, `TRIVIA`, `STATUS` | asset-level tier — mixes true severity with a non-severity "status annotation" bucket |
| `CalendarIncidentSeverity` | `MAJOR` (line-wide breakage, crashes), `MINOR` (single-vehicle), `OTHERS` | network-level tier |
| `CalendarIncidentChronologyIndicator` | `GREEN`, `RED`, `BLUE`, `GRAY` | timeline dot colour |
| `CalendarIncidentStatus` | `DRAFT`, `PENDING_APPROVAL`, `LIVE`, `REJECTED`, `PENDING_DELETION` | shared by incident + chronology status fields; `PENDING_DELETION` is only ever set on chronologies (mark-for-delete flow) |
| `SocialMediaLinkStatus` | `LIVE`, `PENDING_APPROVAL` | link lifecycle — a strict 2-state subset, deliberately not reusing the incident enum |

The two severity vocabularies are **not interchangeable**, and there is no mapping between them. `CalendarIncidentChronology.indicator`'s `help_text` documents a fifth "Loading" state that does not exist in the enum — a client-side-only value that will never validate.

**Incident vs. calendar-incident.** `IncidentAbstractModel` (`TimeStampedModel + OrderedModel`) carries `date` (a plain `DateField` — day granularity), `severity`, optional `location: PointField`, short `title`/`brief`, `is_last`, and an explicit editable `order`. `VehicleIncident` and `StationIncident` set `order_with_respect_to` to their parent, so each vehicle/station owns an independently ordered history, and `is_last` flags the row that represents the asset's _current_ state. `CalendarIncident` instead models a _span_ (`start_datetime`, nullable `end_datetime` = ongoing) with `long_term` (collapse to start date only in month view), `inaccurate` (display an "unverified" badge), a `Decimal(5,2)` `impact_factor`, a `TextField` `brief`, markdown `details`, fan-out M2Ms, a `status` lifecycle, a `version` OCC counter, and a nullable `parent_incident` FK for the draft-revision flow. Its narrative lives in `CalendarIncidentChronology` rows (`related_name="chronologies"`, ordered per incident), each with its own independent `status`. **There is no FK between the two tiers** — a `VehicleIncident` cannot be linked to the `CalendarIncident` it belongs to; correlation is only implicit via shared vehicle/station and date.

**Draft-revision flow (`services/incidents.py`).** A non-admin edit of a non-DRAFT incident creates a DRAFT revision (`parent_incident=incident`, `created_by` = the **editing actor**, not the original author). The one-open-draft rule rejects a second actor's edit while a draft is open ("An unapproved edit draft already exists for this incident. Please allow the draft to approve before proceeding."); the same actor's re-edit resumes their own draft in place. Admin approval of a revision (`approve_incident`) merges fields, M2Ms, chronologies and medias into the parent atomically, then hard-deletes the draft. Admin edits apply in place (Option A); an author editing their own `PENDING_APPROVAL` row also applies in place (spec C1). `delete_incident` resolves pending children first — open draft revisions and `PENDING_APPROVAL`/`PENDING_DELETION` chronologies are soft-deleted so no orphaned pending child survives a parent deletion (safedelete's `SOFT_DELETE` does not cascade by design).

**Aggregation logic (`schema/resolvers.py`).** `get_calendar_incidents_by_severity_count` is the only hand-written aggregate resolver. It first narrows to incidents overlapping the window, `aaggregate`s the earliest `start_datetime`, then builds a `pendulum` interval clamped to `min(end_date, today)` and constructs **one conditional `Count(filter=Q(…))` per bucket × severity (× long/short term in `DAY` mode)** — up to `days × 3 × 2` conditional aggregates in a single query — then reconstructs dates by string-splitting the aggregate alias on `_`. Efficient in round-trips (one query), but the generated SQL grows linearly with the requested range; the 60-day `GraphQLError` in the filter is the de-facto guard, and it does not apply to this resolver.

**Batching.** `IncidentContextLoaders` holds five loaders, registered under key `"incident"` in `rosak/context.py` and `deepcopy`'d per request: `medias_from_calendar_incident_loader` (walks `CalendarIncidentMedia` with `select_related("media")`, returns a **`set`** per key even though the field is typed `List[MediaScalar]` — media are silently de-duplicated and the `CalendarIncidentMedia.timestamp` ordering is discarded), `vote_scores` / `vote_breakdown` / `user_vote_value` (generic `common.Vote` counts per ContentType), and `incident_links` (batches the first page of per-incident link connections, `first+1` rows per incident to compute `has_next_page`).

**Known integrity risks.**

- **Duplicate Line↔CalendarIncident relation.** `CalendarIncident.lines` (`related_name="incidents"`, set in migration `0013`) and `operation.Line.calendar_incidents` are two _separate_ join tables. Admin's `filter_horizontal` edits the former; the GraphQL `Line.calendarIncidents` field reads the latter — so that field is expected to be permanently empty. Consolidating on `Line.incidents` (the reverse accessor) is the fix.
- `order` is redeclared on the concrete models as `editable=True` with a `# Remove after beta` comment still outstanding.

**Schema evolution (23 migrations, `0001_initial` Aug 2022 → `0023` 2026):** `0002`/`0003` add `is_last` and its constraints; `0004` introduces the whole calendar tier (`CalendarIncident`, `CalendarIncidentCategory`, `CalendarIncidentChronology`); `0005`–`0008` churn on `severity` choices and `brief`; `0009`/`0012` add and adjust chronology `source_url`; `0010` adds `inaccurate`; `0011` replaces the plain media M2M with the `CalendarIncidentMedia` through-model; `0013` adds `related_name="incidents"`; `0014` adds `SocialMediaLink`; `0015`/`0016` add safedelete `deleted` fields; `0017` converts status fields to `TextChoicesField`; `0018`/`0019` wire `SocialMediaLink.user`/`completed_by`; `0020` adds `CalendarIncident.created_by`; `0021` fixes the `StationIncident` unique constraint (adds the missing `condition=Q(is_last=True)`); `0022` adds link `description` + `status`; `0023` adds `PENDING_DELETION` to the shared status enum.

## 🧩 Extension Points & Hooks

- **The abstract triad.** `IncidentAbstractModel` + `IncidentAbstractScalar` + `IncidentAbstractFilter` is a deliberate three-layer template: adding a new incident target (e.g. `AssetIncident` for `operation.Asset` lifts/escalators) means one model subclass, one scalar subclass, one filter subclass, one field on `IncidentScalars`, and one inline in `operation/admin.py` — no changes to existing code.
- **`IncidentMutations`** is the wired write seam — it composes `IncidentCrudMutations`, `ChronologyMutations`, `VoteMutations`, `SocialMediaLinkMutations` and `ExtractionMutations` into `rosak.schema.Mutation`. New write paths add a mixin here.
- **`CalendarIncidentCategory`** is a free-form tag table — new taxonomies (signalling, power, rolling stock, weather, industrial action) need data rows, not migrations. It also backs `SocialMediaLink.categories`.
- **`IncidentContextLoaders`** dict — new batched fields plug in by adding one key; the per-request `deepcopy` in `rosak/context.py` handles isolation.
- **Status enums as lifecycle hooks.** `CalendarIncidentStatus` (with `PENDING_DELETION` reserved for the chronology mark-for-delete flow) and `SocialMediaLinkStatus` are the approval-lifecycle vocabulary; new states are enum additions plus the matching service gate.
- **`impact_factor` is a reserved hook with zero consumers.** Its `help_text` specifies "scores to deduct from a full score of 100 per day, prorated by usual service hours when consolidating", but no code in the repo — `chartography` included — ever reads it. The reliability-index feature it was designed for is unbuilt; the column, the admin field, the GraphQL field and the ordering key are all already in place.
- **`CalendarIncidentChronology.source_url` + the `/upload/` → `common.tasks` → `CalendarIncidentMedia` pipeline** form a ready evidence-attachment channel (with EXIF timestamp capture) for any future citation or verification workflow.
- **`inaccurate` / `long_term` booleans** are presentation flags the frontend already honours — usable as confidence or provisional markers by automated writers without new schema.
- **`ordered_model`** gives editors manual precedence control (`move_up_down_links`) independent of chronology, useful for pinning headline incidents.

## 💡 Potential Feature Opportunities

1. **"All incidents in this disruption" — one FK to join the two tiers.** The single highest-leverage schema change in the app. Today `VehicleIncident`/`StationIncident` and the `CalendarIncident` they belong to have no relation at all, so a reader viewing a network disruption cannot see which individual trains or stations were affected, and an editor logging a vehicle fault cannot attach it to the open disruption. A nullable `calendar_incident` FK on `IncidentAbstractModel` (`on_delete=SET_NULL`, `related_name="%(class)s_set"`) gives `CalendarIncidentScalar` rollup lists and each asset-level scalar a parent link, following the existing abstract-triad pattern exactly. For a community rail platform this is the difference between a calendar of headlines and a genuinely queryable incident record — and it also makes `impact_factor` attributable to specific rolling stock.
   **Readiness:** `Not ready` — the FK does not exist; correlation today is implicit via shared vehicle/station plus `date` proximity. An implementer adds the field to `IncidentAbstractModel` in `/home/kwongtn/rosak_backend/incident/models.py` (both concrete models inherit it), generates `incident/migrations/0024_…` (nullable, so no backfill is forced), adds `calendar_incident: Optional["CalendarIncidentScalar"]` to `VehicleIncident`/`StationIncident` and the reverse `List[...]` fields to `CalendarIncidentScalar` in `incident/schema/scalars.py`, a nested filter in `incident/schema/filters.py`, and `autocomplete_fields = ("calendar_incident",)` on the inlines in `incident/admin.py` — `CalendarIncidentAdmin` already declares `search_fields`, so admin autocomplete works with no extra setup.

2. **Per-line reliability score — pure arithmetic over `impact_factor`.** `impact_factor` is a `Decimal(5,2)` on `CalendarIncident` whose `help_text` already specifies the exact formula ("Scores to deduct from full score of 100 per day. Will be prorated based on usual service hours when consolidating"), and it is fully wired end-to-end — DB column, admin form field, `CalendarIncidentScalar.impact_factor: float`, and an `impact_factor` key on `CalendarIncidentOrder` — with **zero consumers anywhere in the repo**. A new resolver alongside `get_calendar_incidents_by_severity_count` in `incident/schema/resolvers.py` can walk incidents overlapping a window, deduct each one's `impact_factor` per overlapped day from 100, and group by the affected `Line` — no model, just subtraction and a `GROUP BY`. Publishing a monthly reliability figure per line is the flagship number a community transit-watch site exists to produce.
   **Readiness:** `Partially ready` — the value and every plumbing layer already exist, but two gaps remain. (a) The "prorated by usual service hours" half of the spec has no data source: `operation.Line` carries only `official_numbering`, `code`, `display_name`, `display_color`, `status` and `telegram_channel_id` — no service-hours field — so either v1 uses whole-day denominators or a `service_start_time`/`service_end_time` pair is added to `operation/models.py`. (b) The resolver must traverse `CalendarIncident.lines` (reverse accessor `Line.incidents`, set in migration `0013`), **not** `operation.Line.calendar_incidents`, which is the dead duplicate join table admin never writes to. Files: `incident/schema/resolvers.py`, `incident/schema/schema.py` (new field on `IncidentScalars`), optionally `operation/schema/scalars.py` for a `Line.reliabilityScore` field.

3. **Public status page and a subscribable disruption feed (ICS / Atom / RSS).** `CalendarIncident` already holds everything such a feed needs: `start_datetime`, a nullable `end_datetime` that literally means "still ongoing", `severity`, `title`, markdown `details`, the `inaccurate` flag for an "unverified" badge, `long_term` for maintenance-window collapsing, and ordered `CalendarIncidentChronology` rows carrying `datetime`, `indicator`, `content` and `source_url` for successive updates. An "is it broken right now?" page plus a calendar subscription commuters can add to their phone is the highest-value read-only surface this data supports, and needs no new persistence at all.
   **Readiness:** `Partially ready` — the `ongoing` filter now exists (`CalendarIncidentFilter.ongoing` → `Q(end_datetime__isnull=True)`), so a client can ask for currently-broken incidents directly. The remaining gap is a real feed URL: `incident/views.py` is 0 bytes and the app has no `urls.py`; `rosak/urls.py` already `include()`s `operation.urls` and `telegram_provider.urls`, so add `incident/urls.py` with a `django.contrib.syndication.views.Feed` subclass (Atom/RSS) and a plain-text `text/calendar` view, then one `path("incident/", include("incident.urls"))` line.

4. **Put asset-level incidents on the map, with their photo evidence.** `IncidentAbstractModel.location` is a real `PointField`, already captured by editors through `VehicleIncidentLocationForm`/`StationIncidentLocationForm` (latitude/longitude inputs supplied by `generic.views.GeometricForm`), and both `VehicleIncident` and `StationIncident` carry a `medias` M2M to `common.Media`. All three are **commented out** in `incident/schema/scalars.py` (`# location` at line 34, `# medias` at lines 43 and 49), so data volunteers are already entering is invisible to every client — no "where on the line did this door fault happen" map, no photo next to the ledger entry.
   **Readiness:** `Ready` — no migration, no new infrastructure. `generic.schema.scalars.GeoPoint` already exists and `operation.schema.scalars.Station` uses precisely `location: Optional["GeoPoint"]`, so declare the same on `IncidentAbstractScalar`, and `medias: List[Annotated["MediaScalar", strawberry.lazy("common.schema.scalars")]]` on both subclasses. These are plain M2Ms with no through-model ordering to preserve, so `DjangoOptimizerExtension` prefetches them directly — unlike the calendar tier, no DataLoader is required. Single file: `incident/schema/scalars.py`.

5. **Station incident history — loaders needed.** A station-detail page showing "past problems at this station" is the natural twin of the vehicle history the frontend already renders. The `StationIncident` UniqueConstraint now includes `condition=Q(is_last=True)` (fixed in migration `0021`), matching its `VehicleIncident` twin. The remaining work is adding station-equivalent loaders: `operation/schema/loaders.py` provides `incident_from_vehicle_loader` and `incident_count_from_vehicle_loader` (powering `Vehicle.incidents`, `Vehicle.incidentCount`, `Vehicle.canExpand`) but no station equivalent, so `operation.schema.scalars.Station` has no `incidents` field at all — only the root `stationIncidents` query reaches them.
   **Readiness:** `Partially ready` — constraint fixed. Mirror `batch_load_incident_from_vehicle`/`batch_load_incident_count_from_vehicle` as station variants in `operation/schema/loaders.py`, register the new keys in the `OperationContextLoaders` dict, and add `incidents`/`incident_count` resolver fields to `Station` in `operation/schema/scalars.py`.

## 💡 Potential AI Feature Opportunities

1. **Auto-draft calendar incidents from operator announcements.** `telegram_provider` already ingests channel messages and `operation.Line` carries `telegram_channel_id`, yet nothing bridges into `incident`. An LLM extraction step could propose a `CalendarIncident` (start/end datetime, `severity`, affected `lines`/`stations`, `title`, `brief`) plus successive `CalendarIncidentChronology` rows straight from raw announcements, writing through the now-wired `IncidentMutations` (the `extractDataFromUrl` mutation already demonstrates the pattern) and setting `inaccurate=True` as a built-in low-confidence / awaiting-review marker. Chronology `source_url` gives citation for free.
2. **Impact scoring and severity assistance.** With `impact_factor` present but unconsumed, a model trained on historical span duration, affected-line count, chronology length and severity could suggest an `impact_factor` at admin-save time and roll it into a per-line reliability index for `chartography` — turning a dormant column into the reliability metric it was specified as, without a migration.
