# Component: reporting

## 📌 Purpose & Scope

- **Core Responsibility:** Crowd-sourced fault reporting on **station assets** (escalators and lifts — `operation.AssetType` contains only `ESCALATOR`/`LIFT`), plus the lifecycle around such a report: community corroboration via voting, and closure via an operator/moderator resolution note. It is the "something at this station is broken" channel.
- **Distinction from sibling apps:**
  - `spotting` — user-submitted *vehicle sightings* (`spotting.Event` → `operation.Vehicle`, origin/destination stations, wheel/vehicle status). High-volume, observational, no resolution lifecycle.
  - `incident` — *curated/editorial* incident records (`VehicleIncident`, `CalendarIncident`) authored by maintainers, ordered and severity-graded, with chronology entries. Not user-submitted, no votes.
  - `reporting` — user-submitted *defect reports against fixed infrastructure assets*, and the only app in the repo modelling **votes** and **resolutions**, i.e. a moderation/triage workflow rather than a log.
- **Domain/Layer:** Django business-logic / persistence app (registered in `rosak/settings.py` `INSTALLED_APPS`), with a Strawberry GraphQL type layer that is currently **scaffolded but not wired into the public schema**.
- **Maturity:** Effectively dormant. Models, migration and Django admin are complete and live; the entire GraphQL query/mutation/filter/input surface is commented out. Treat this as a designed-but-unreleased feature, not production traffic.

## 🔌 Interface & Data Flow

### Inputs / Props / Signals

- **GraphQL arguments/inputs: none currently reachable.** `ReportingScalars` and `ReportingMutations` (`reporting/schema/schema.py`) are empty `@strawberry.type` stubs whose fields are commented out. The intended, fully drafted-but-disabled surface is:
  - Filters (`reporting/schema/filters.py`, all commented): `ReportFilter` (`id`, `asset_ids: [ID]`, `reporter_ids: [ID]`, `types: [ReportType]`), `ResolutionFilter` (`id`), `VoteFilter` (`id`, `report_id`, `user_id`, `is_upvote`).
  - Inputs (`reporting/schema/inputs.py`, all commented): `ReportInput` / `ReportPartialInput` (`asset_id`, `reporter_id`, `description`, `type`), `ResolutionInput` / `ResolutionPartialInput` (`report_ids: [str]`, `user_id`, `notes`), `VoteInput` (`report_id`, `user_id`, `is_upvote`).
  - Latent bug to fix before re-enabling: `ReportFilter.filter_types` filters on `report_type__in`, but the model field is named `type`.
- **Enum input:** `reporting.enums.ReportType` (`TextChoices`): `COSMETIC_BREAKDOWN`, `FUNCTIONAL_BREAKDOWN`, `RESOLUTION`. `RESOLUTION` sitting on the same enum as the two defect kinds means a "report" doubles as "report that this got fixed" — an alternative path to the `Resolution` model rather than a defect class.
- **Orderings:** none defined (no `strawberry_django.order`, no model `Meta.ordering`).
- **Django signals:** none registered — no `signals.py`, no `AppConfig.ready()` override in `reporting/apps.py`.
- **Admin (the only live write path today):** `ReportAdmin` (inlines `ReportMedia`, `Vote`), `ResolutionAdmin` (inline `ReportResolution`), `VoteAdmin` — `reporting/admin.py`.

### Outputs / Events / API Responses

- **GraphQL types defined** in `reporting/schema/scalars.py` (declared, but unreachable because no root field returns them):
  - `Report` — `id`, `asset: Asset`, `description`, `type` (auto → `ReportType` enum). `reporter` is commented out (no `common.User` GraphQL type is imported here).
  - `Resolution` — `id`, `reports: [Report]`, `notes`. `user` commented out.
  - `Vote` — `id`, `is_upvote`, `report: Report`. `user` commented out.
- **Celery tasks:** none. No `reporting/tasks.py`; `rosak/celery.py`'s `beat_schedule` has no `reporting.*` entry (only `common`, `telegram_provider`, `chartography`, `spotting`). No Telegram/notification fan-out on new reports, unlike `spotting`.
- **HTTP endpoints:** none. `reporting/views.py` is empty and there is no `reporting/urls.py`, so nothing is mounted in `rosak/urls.py` (contrast `operation/` and `telegram_provider/`, which are). All intended access is via the single `/graphql/` endpoint.
- **Signals fired:** none.

### Dependencies

- **Cross-app FKs — outbound (reporting → others):**
  - `Report.asset → operation.Asset` (PROTECT, nullable/optional)
  - `Report.reporter → common.User` (PROTECT, required)
  - `Report.medias ↔ common.Media` (M2M through `reporting.ReportMedia`)
  - `Resolution.user → common.User` (PROTECT)
  - `Vote.user → common.User` (PROTECT)
  - Migration `0001_initial` depends on `common.0001_initial` and `operation.0001_initial`.
- **Cross-app Python imports — outbound:** only `operation.schema.scalars.Asset` in `reporting/schema/scalars.py`. All model relations use lazy string references, so `common` is a runtime (not import-time) dependency. `tach.yml` records `reporting: depends_on: [operation]` — accurate for imports, understating the `common` coupling.
- **Inbound (others → reporting):** exactly one — `rosak/schema.py` imports `ReportingMutations, ReportingScalars` and mixes them into the root `Query`/`Mutation`. **No other app imports `reporting`**, and no other app FKs into `Report`/`Resolution`/`Vote`; `tach.yml` confirms `reporting` appears only in `rosak`'s `depends_on`. The app is a clean leaf — it can be extended or re-enabled with near-zero blast radius.
- **Third-party:** `django-model-utils` (`TimeStampedModel`, `UUIDModel`, `SoftDeletableModel`), `strawberry-graphql-django`, Django admin.

## ⚙️ Internal State & Logic

- **Models (`reporting/models.py`):** `Report`, `ReportMedia` (M2M through), `Resolution`, `ReportResolution` (M2M through), `Vote`. Five models, one migration (`0001_initial`, 2022-07-09) — the schema has never evolved, reinforcing that the feature was parked.
- **Mixin stack:** `Report` and `Resolution` are `TimeStampedModel + UUIDModel + SoftDeletableModel` — UUID PKs (so IDs are safe to expose publicly, which is why the GraphQL types declare `id: str`), `created`/`modified` audit columns, and soft delete via `is_removed`, so a `SoftDeletableManager` hides removed rows by default and moderation deletions stay recoverable. `Vote` is `TimeStampedModel` only — integer PK, hard delete, no tombstone.
- **Business logic:** essentially none. The one piece of behaviour is `Vote.is_downvote`, a Python `@property` returning `not self.is_upvote` — not annotated or exposed to GraphQL, so it cannot be filtered or ordered on at the DB level.
- **Notable integrity gaps** (scaffolding-shaped, all worth closing before launch):
  - No `UniqueConstraint` on `Vote(report, user)` — nothing prevents ballot stuffing via repeated mutation calls. Compare `operation.AssetMedia`, which *does* declare uniqueness on its through table.
  - No unique constraints on `ReportMedia` or `ReportResolution` either (duplicate attachments/links possible).
  - `Report.type` is an unbounded `TextField` with `choices`, so DB-level values are unconstrained; there is no denormalised vote tally or resolved flag, so "is this resolved?" and "what's its score?" are joins/aggregates at read time.
  - `on_delete=PROTECT` throughout means an asset, user or media cannot be deleted while any report references it — deletion must go through the soft-delete path.
- **Query optimisation:** `DjangoOptimizerExtension` is enabled globally in `rosak/schema.py`, so once fields are exposed, `Report.asset` / `Resolution.reports` resolve with automatic select/prefetch — no manual dataloaders needed.

## 🧩 Extension Points & Hooks

- **The primary hook is uncommenting.** Re-enabling the app means restoring the field declarations in `ReportingScalars` / `ReportingMutations`; the root `Query`/`Mutation` already inherit from them, so `rosak/schema.py` needs no change.
- **`reporting/schema/mutations.py` is an empty file** — the intended home for hand-written resolvers (vote toggling, permission checks, resolution workflows) as opposed to the auto-generated `strawberry_django.mutations.create/update/delete` used in the commented stubs.
- **`ReportType`** is the cheapest widening point: new defect categories are additive `TextChoices` members with no migration risk (`type` is already a `TextField`).
- **Through-model tables** (`ReportMedia`, `ReportResolution`) are the natural place to hang per-link metadata (caption, ordering, who attached it, resolution role) without altering `Report`.
- **`AppConfig.ready()` in `reporting/apps.py`** is the standard place to attach `post_save` signals — e.g. fan out a Telegram alert on `FUNCTIONAL_BREAKDOWN`, or recompute a vote tally — following the pattern `telegram_provider/apps.py` uses.
- **Celery** is autodiscovering (`app.autodiscover_tasks()`), so a new `reporting/tasks.py` is picked up with no registration; scheduled work only needs a `beat_schedule` entry in `rosak/celery.py`, mirroring `spotting.tasks.report_spotting_today`.
- **Soft delete** already provides an "unremove" path; a staff-only GraphQL field using the unfiltered manager would expose a moderation review queue with no schema change.

## 💡 Potential Feature Opportunities

*Baseline reality for every item below: none of this app is user-visible today. `Report`, `Vote` and `Resolution` exist as tables and Django-admin screens only — the entire GraphQL surface is commented out, so no client can read or write them. Items 1–2 are about making the app reachable at all; items 3–5 presuppose that.*

1. **Ship the drafted report submission and browse surface.** The whole premise of the app — a rider filing "escalator B at this station is dead", others seeing it — is fully designed and completely unreachable. `ReportingScalars` / `ReportingMutations` in `reporting/schema/schema.py` are empty `pass` stubs, and `reporting/schema/filters.py` and `inputs.py` are 100% comments. Restoring the `reports` / `resolutions` / `votes` fields and the `create_report` / `update_reports` mutations would make `Report`, `Vote` and `Resolution` client-visible for the first time since the 2022 initial migration. This is the precondition for everything else in this section, and it is cheap: `rosak/schema.py`'s root `Query` / `Mutation` already inherit both mixins, so no file outside `reporting/` has to change to expose the fields.
   **Readiness:** `Partially ready` — the drafted code does not currently import, so uncommenting alone will not boot. Three concrete blockers: (a) `reporting/schema/filters.py:7` and `reporting/schema/inputs.py:7` both do `from reporting.schema.enums import ReportType`, but **`reporting/schema/enums.py` does not exist** — create it as a `@strawberry.enum` wrapper over `reporting.enums.ReportType`, following `generic/schema/enums.py`; (b) `ReportFilter.filter_types` filters `report_type__in=self.types` while the model field is `Report.type` (`reporting/models.py:22`) — it must become `type__in`; (c) restoring the commented `reporter` / `user` fields in `reporting/schema/scalars.py` means importing `common.schema.scalars.UserScalar`, a new import edge that requires adding `common` to `reporting`'s `depends_on` in `tach.yml` (it currently lists only `operation`).

2. **One vote per person, withdrawable.** Community corroboration is this app's differentiator — no other app in the repo models `Vote` — but the drafted surface would ship it broken in two ways: there is no `UniqueConstraint` on `Vote(report, user)`, so repeated `createVote` calls stuff the ballot, and both `VoteInput.user_id` and `ReportInput.reporter_id` are *client-supplied*, so any caller can vote or file a report as any user. The feature worth building is a single idempotent `toggle_vote(report_id, is_upvote)` resolver in the currently-empty `reporting/schema/mutations.py` that derives the voter server-side and flips or withdraws the caller's existing row instead of appending another. For a "which broken lift is worst" ranking to mean anything, the vote count has to be a headcount.
   **Readiness:** `Partially ready` — every ingredient exists in the repo, but this needs the app's second-ever migration. Add `class Meta: constraints = [models.UniqueConstraint(fields=["report", "user"], name="%(app_label)s_%(class)s_unique_report_user")]` to `Vote` (`reporting/models.py:63`), copying the naming convention `operation.AssetMedia` already uses, then run `makemigrations reporting` (this app has only `0001_initial`). For identity, copy `spotting/schema/schema.py`'s `add_event`: `@strawberry.mutation(permission_classes=[IsLoggedIn, IsRecaptchaChallengePassed])` from `rosak/permissions.py`, take the user from `info.context.user.id`, and return `common.schema.scalars.GenericMutationReturn`. Important caveat: the drafted auto-generated mutations `delete_reports` and `delete_vote` (`strawberry_django.mutations.delete()`) carry **no** `permission_classes` at all — they must not be uncommented as written. Also note `Vote` is `TimeStampedModel` only, so a withdrawn vote is a hard delete with no tombstone; add `SoftDeletableModel` in the same migration if withdrawal needs to be auditable.

3. **"Is the lift at this station working right now?" on the station page.** `operation.schema.scalars.Station` already exposes `assets: List[Asset]`, so any rider-facing station view is *already* fetching the exact objects `Report.asset` points at — the missing half is per-asset fault state. Exposing a batched `open_functional_breakdown_count` and `latest_report_at` per asset (or a root `assetReportSummary(assetIds: [ID!])` field on `ReportingScalars`) turns a pile of report rows into the single most useful thing this app can tell a commuter: whether it is worth walking to that station with a pram, luggage or a wheelchair. Because `operation.AssetType` contains only `ESCALATOR` and `LIFT`, this is squarely an accessibility feature.
   **Readiness:** `Partially ready` — needs a dataloader plus one boundary decision. There is no `reporting/schema/loaders.py` and no `"reporting"` key in the `ContextLoaders` dict in `rosak/context.py`; create both, copying the shape of `batch_load_spotting_count_from_vehicle` in `operation/schema/loaders.py`. Do **not** hang the field on `operation.schema.scalars.Asset`: that would make `operation` import `reporting`, and since `tach.yml` already declares `reporting: depends_on: [operation]` while `operation.depends_on` omits `reporting`, it would introduce a dependency cycle — put the field on a `reporting`-owned type or a root query instead. Separately, `Asset` (`operation/schema/scalars.py:155`) does not currently expose the model's `status` field (`operation.AssetStatus`: `UNDER_MAINTENANCE` / `IN_OPERATION`); adding `status: strawberry.auto` there is one line and lets the UI show official status next to crowd-sourced reports.

4. **An explicit report status lifecycle and an orderable open-fault feed.** Two shortcomings compound here. First, "is this resolved?" is only ever an `EXISTS` over the `ReportResolution` through table — there is no status column, so it cannot be filtered or ordered on. Second, `ReportType` (`reporting/enums.py`) puts `RESOLUTION` on the same enum as `COSMETIC_BREAKDOWN` and `FUNCTIONAL_BREAKDOWN`, meaning a user telling the platform something got fixed is expected to file a *new `Report`* — so the enum conflates "what kind of defect is this" with "what kind of event is this", and a fix announcement is indistinguishable from a defect in any `type`-filtered list. A dedicated `ReportStatus` (`OPEN` / `CONFIRMED` / `RESOLVED` / `REJECTED`) on `Report` plus cached `upvote_count` / `downvote_count` columns gives the product a "most-corroborated unresolved faults" feed and gives moderators a filterable queue. None of that is expressible today: `Vote.is_downvote` is a plain Python `@property`, invisible to the ORM.
   **Readiness:** `Not ready` — the migration-heavy item, but a well-bounded one since `reporting` is an import leaf. Files to touch: `reporting/enums.py` (add `ReportStatus`; decide whether `ReportType.RESOLUTION` is deprecated); `reporting/models.py` (add `status`, `upvote_count`, `downvote_count`, and change `type` from `models.TextField(choices=ReportType.choices)` to `django_choices_field.TextChoicesField(choices_enum=ReportType, max_length=32)` — the repo-wide pattern in `spotting/models.py` and `operation/models.py`, and the only way `strawberry.auto` yields a GraphQL *enum* rather than a bare `String`); a new `reporting/migrations/0002_*` including a data migration for any existing `RESOLUTION` rows; `reporting/apps.py` (`ReportingConfig.ready()` to attach the `post_save`/`post_delete` counter signals); and a new `reporting/schema/orderings.py` modelled on `spotting/schema/orderings.py`. Related gap to fix at the same time: no model in `reporting/models.py` declares a `Meta` at all, so there is no `Meta.ordering` and any paginated list field added today would return rows in unspecified order.

5. **Photo evidence attached to a report.** `Report.medias` (M2M through `reporting.ReportMedia` to `common.Media`) was plainly designed for "here is a picture of the broken escalator", and a photo is what makes a defect report actionable for an operator rather than an assertion. `common` already owns the whole pipeline this would ride on: the `/upload/` `GenericUpload` endpoint, the clearance/NSFW states in `TemporaryMediaStatus`, Discord-backed storage, and the `convert_temporary_media_to_media_task` Celery task that materialises a `Media` row and links it to its parent object. `spotting.EventMedia` and `incident.CalendarIncidentMedia` are both already wired into it; `reporting` is the one that was left out.
   **Readiness:** `Not ready` — one missing enum member cascades into three files. `common.enums.TemporaryMediaType` contains only `SPOTTING_EVENT` and `INCIDENT_CALENDAR_INCIDENT`; add `REPORTING_REPORT` (its own docstring prescribes the `<app>_<model>` format). Then `common/views.py`'s `GenericUpload.post` needs a branch that sets `metadata["report_id"]` and rejects uploads where `user.id != report.reporter_id` — its current `else` returns HTTP 400 for any unknown type — and `common/tasks.py`'s `convert_temporary_media_to_media_task` needs both a Discord embed `title` case and a `ReportMedia.objects.create(media_id=..., report_id=...)` branch, since its `else` raises `RuntimeError("Invalid upload type")`. That makes `common` import `reporting`, so add `reporting` to `common`'s `depends_on` in `tach.yml`. Finally, unlike `operation.AssetMedia`, `ReportMedia` has no `UniqueConstraint(report, media)`, so a retried upload can double-attach the same image — fold that constraint into the migration from item 4.

## 💡 Potential AI Feature Opportunities

1. **Auto-triage and deduplication of incoming reports.** `Report` already carries free-text `description`, a target `asset`, a `type`, and timestamps. An LLM/embedding pass at create time can (a) classify `COSMETIC_BREAKDOWN` vs `FUNCTIONAL_BREAKDOWN` from the text so the reporter need not choose, and (b) embed the description and cluster it against open reports on the same `asset` within a time window, auto-linking duplicates instead of creating noise. `Vote` then becomes corroboration on one canonical report rather than a scatter of near-identical ones, and the `ReportResolution` through table is a ready-made place to record merges.
2. **Confidence scoring and abuse resistance on votes.** Because `Vote` is unconstrained per `(report, user)` and carries `created`, the table is a natural input to a trust model: score credibility from vote velocity, voter history across assets, and reporter track record (how many of their past reports ended in a `Resolution`). A derived `credibility` field lets operators prioritise genuinely broken lifts over spam — and the same signal flags the stuffing the missing DB constraint currently permits.
3. **Resolution drafting and predictive maintenance from report history.** `Resolution.notes` is free text linked to a set of reports; past (reports → notes) pairs form a supervised corpus for suggesting a draft resolution note to whoever closes a report. The longer-term play is per-asset failure prediction: report frequency and time-to-resolution per `operation.Asset`, joined to `AssetStatus`, is enough to forecast which escalators are trending toward failure and pre-empt reports entirely. `reporting` being an import-leaf means such a model layer can be added without perturbing any other app.
