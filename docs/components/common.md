# Component: common

## 📌 Purpose & Scope

- **Core Responsibility:** The foundation app. It owns **identity** (`User`, Firebase-backed), **authorization primitives** (`Clearance`, `UserClearance`, `FeatureFlag`), **the media ingestion pipeline** (upload, moderation, permanent hosting), **the generic vote primitive** (`Vote`), and **the shared analytics and date-bucketing utilities** that other apps' trend endpoints build on. It has no domain concepts of its own.
- **Distinction from sibling apps:** every other app models _things in the world_ (vehicles, stations, spottings, incidents). `common` models _the people, the pictures they take, and the plumbing_.
- **Domain/Layer:** Django persistence and business logic, infrastructure adapters (custom `Storage`, custom `ImageField`), a Strawberry slice (`CommonScalars`, `CommonMutations`) merged into the root schema, one DRF `APIView` outside GraphQL, and 5 Celery tasks (2 on beat).
- **Maturity:** Live and load-bearing. The Imgur storage subsystem is still on the write path and is being retired in favour of Discord CDN hosting.

## 🔌 Interface & Data Flow

### Inputs / Props / Signals

- **GraphQL queries** (`common/schema/schema.py`, mixed into root `Query`):
  - `medias`: `DjangoListConnection[MediaType]` with `MediaOrder`. No `filters=` argument.
  - `media(id: ID!)`: one `MediaType` by the **Relay global id** that `medias` nodes expose (base64 `MediaType:<uuid>`; a raw UUID is not accepted). Nullable: a missing, malformed, non-UUID or other-type id returns `null`, never an error. It resolves through `MediaType.resolve_node`, so it starts from the same default queryset and `MediaType.get_queryset` hook as the connection. The hook hides rows whose `file` is `''` or NULL (legacy rows; `MediaType.file` is non-null), so such a row is absent from the feed and `media(id)` returns `null` for it. Any further visibility rule belongs in the same hook, where both entry points pick it up. `mediasGroupByPeriod` filters `~Q(file="")` only, so it still counts a NULL-`file` row (none on the dev DB).
  - `user`: current viewer (`IsLoggedIn`).
  - `my_votes_cast`: count of the caller's `Vote` rows across all content types (`IsLoggedIn`).
  - `public_user(id)`.
  - `medias_group_by_period(type: DateGroupings)`: upload histogram. One database `GROUP BY` (`ExtractYear` / `ExtractMonth` / `ExtractDay` over the naive local `created`, `values()` plus `Count`), ordered oldest first, over `Media` rows that have a file (neither `''` nor NULL: `FILELESS_MEDIA` in `common/schema/loaders.py`, shared with `MediaType.get_queryset` and the loader below). Only non-empty periods come back (no zero fill). `YEAR` and `WEEK` both group by year (`WEEK` has no weekly bucket; it only echoes `type`), `MONTH` by year and month, `DAY` by year, month and day. `medias` is a lazy field (`medias_from_period_loader`, one query for every period of the request, ids ascending), so a count-only selection such as the gallery's `{ year count }` runs a single query and loads no media row. Before this it aggregated every id with `ArrayAgg` and awaited one loader call per id, which cost one query per photo (2,440 queries and 42 to 59 s on the dev DB).
- **GraphQL mutations** (`CommonMutations`), both `IsLoggedIn`:
  - `update_user(input: UserInput)`: `UserInput` exposes `nickname` and `spotting_data_public` (`Maybe[bool] = UNSET`: omitted keeps the stored value, explicit `null` is a validation error because the column is `NOT NULL`).
  - `request_verification_code()`: mints a `UserVerificationCode` for Telegram account linking.
- **Orderings and filters:** `MediaOrder` (`created`, `modified`; no `uploader`, because sorting by it would group a photo whose uploader is hidden between the same user's visible ones). `common/schema/filters.py` is fully commented out, so `medias` has no filter argument.
- **The primary key is always the last sort key of `medias`.** Photos tie on `created` and `modified` (two uploaded within one millisecond), and offset paging over tied rows skips some and repeats others, because Postgres may order the tie differently for every `LIMIT`/`OFFSET`. `MediaOrder.order` (the library's object-level order method, not a schema field, so the public input is unchanged) appends `pk` to whatever the client asked for, and `MediaType.get_queryset` orders a feed with no `order` argument by `pk`. Ties therefore come back in ascending `pk` order, whichever direction the requested key runs. The `pk` is a random UUID, so a feed with no `order` pages completely and in a fixed order for a given set of rows, but that order means nothing: send `order` for a meaningful one, such as `created: DESC`. A client's `order` replaces the type queryset's ordering outright, so a tie-break set only in `get_queryset` would vanish whenever an `order` is sent. A new `MediaOrder` field needs no change: the `pk` still follows it.
- **REST upload (the real entry point):** `POST /upload/` → `common.views.GenericUpload` (`rosak/urls.py`). Multipart fields: `upload_type` (a `TemporaryMediaType` member), `image`, `related_id`. Authenticated by the `Firebase-Auth-Key` header, not GraphQL context. Responses: 400 (bad `upload_type`), 401, 403 (uploader is not the reporter of the spotting event), 201 (staged). Decorated with `@transaction.atomic` and `@async_to_sync`. **The view never consults `should_upload_media()`**, so uploads are accepted and staged even while the flag is off. **A JPEG's EXIF GPS block is stripped before the file is stored** (`common.exif.strip_gps`, see the media pipeline), whichever client sent it. Every other format is stored as received, GPS included; no image is refused.
- **Auth headers** (allow-listed in `settings.py`): `Firebase-Auth-Key` (`firebase_admin.auth.verify_id_token`) and `G-Recaptcha-Response` (`rosak.permissions.IsRecaptchaChallengePassed`, `RECAPTCHA_MIN_SCORE = 0.85`; unused inside `common`).
- **Signal received:** `post_save` on `TemporaryMedia` (`common/signals.py`, connected in `CommonConfig.ready()`). It is the only receiver in the app. On create:
  - `AWAITING_REVIEW`: returns early and holds the row.
  - Uploader has `TRUSTED_MEDIA_UPLOADER`: sets `TRUSTED_CLEARED` and dispatches convert.
  - Otherwise, if `PENDING`: dispatches convert **and** `check_temporary_media_nsfw` (see the ordering defect under Internal State).
- **Enums:** `TemporaryMediaType` (`SPOTTING_EVENT`, `INCIDENT_CALENDAR_INCIDENT`); `TemporaryMediaStatus` (`PENDING`, `CLEARED`, `TRUSTED_CLEARED`, `OVERRIDE_CLEARED`, `BLOCKED`, `RETRY_ELAPSED`, `INVALID_UPLOAD`, `TO_DELETE`, `AWAITING_REVIEW`); `ClearanceType` (`TRUSTED_MEDIA_UPLOADER`); `FeatureFlagType` (`IMAGE_UPLOAD`). `AWAITING_REVIEW` holds untrusted video staged from Telegram, pending `/approve`. `RETRY_ELAPSED` is declared but assigned nowhere.
- **Management commands:**
  - `get_imgur_token`: interactive OAuth PIN flow that prints `IMGUR_ACCESS_TOKEN` and `..._REFRESH`.
  - `seed_demo_data`: idempotent demo seeder with a fixed RNG (`SEED = 1337`). Defaults: ~150 users (`--users`), ~300 `incident.LineStatusReport`s (`--reports`), ~40 `incident.SocialMediaLink`s (`--links`), 6 lines (`--lines`), plus a few spotting events. It deletes and recreates only rows whose `firebase_id` starts with `demo-seed-`, so re-runs give identical counts. `--flush` deletes only the rows the command created, then exits. Some lines are seeded hot and some with several statuses in the same clock hour, so the pulse and hourly charts show mixed states. `STATION_BIAS = 0.8` tags most reports with one of the line's own stations.

### Outputs / Events / API Responses

- **GraphQL types** (`common/schema/scalars.py`):
  - `MediaType`: Relay `Node` over `Media` (`created`, `created_date`, `uploader` (nullable), `file`, `width`, `height`). `created_date` declares `only=["created"]`, so the optimizer loads `created` with the page instead of refetching it per photo; a resolver-backed field that reads a model column must declare it the same way.
  - `MediaScalar`: non-Relay variant that adds `url`, `discord_suffix`, `caption`, `duration`, `content_type`, `file_name`. `spotting` and `incident` reuse it for their media edges. **`uploader` is nullable on both types** and goes through `uploader_field()` (`CanSeeUploader`): a photo on an anonymous spotting resolves it to `null` unless the viewer is the uploader or an admin (see `docs/privacy-implementation.md`). Any new type that exposes `Media.uploader` must use the same field.
  - `UserScalar`: `firebase_id` (gated by `IsAdmin`), `short_id`, `spotting_data_public`, `favourite_vehicles` (→ `operation.Vehicle`), `with_most_entries`, `spottings` (DataLoader), `spottings_count`, `media_count`, `spotting_trends`. `spottings` and the four spotting figures (`spottings_count`, `favourite_vehicles`, `with_most_entries`, `spotting_trends`) leave out the user's **anonymous** spottings unless the viewer is that user or an admin (`_events_shown_to_viewer`, built on `spotting.schema.resolvers.viewer_is_owner_or_admin`); `favourite_vehicles`, `with_most_entries`, `spotting_trends` and `spottings_count` are async for that check. `with_most_entries` is nullable and returns `null` when the viewer can see no events. `media_count` leaves out photos on anonymous spottings unless the viewer is the user or an admin.
  - `UserVerificationCodeScalar`, `MediasGroupByPeriodScalar`.
  - `GenericMutationReturn` (`{ ok: bool }`): the shared mutation return shape of `spotting` and `chartography`.
  - Plain types in `schema/types.py`: `UserSpottingTrend`, `WithMostEntriesData`, `FavouriteVehicleData`.
- **DataLoaders** (`common/schema/loaders.py`, exposed as `info.context.loaders["common"]`): `spottings_from_user_loader`, `medias_from_period_loader` (the media of each `(year, month, day)` period, `month` and `day` null for coarser groupings; fileless rows excluded) and `is_admin_from_user_loader` (the Firebase admin claim, keyed by `User`: one uncached `has_admin_claim` call per viewer per request, used by `spotting` to show an anonymous event's GPS to admins).
- **Celery tasks** (`rosak.celery.app`):
  - `convert_temporary_media_to_media_task`: the pipeline core (below).
  - `check_temporary_media_nsfw`: RapidAPI NSFW classifier. Skips video. Users with `TRUSTED_MEDIA_UPLOADER` are set to `TRUSTED_CLEARED` and dispatched to convert. Otherwise probability goes to `metadata["nsfw_probability"]`; above `RAPID_API_NSFW_THRESHOLD = 0.5` sets `BLOCKED`, else `CLEARED` and dispatches convert.
  - `cleanup_temporary_media_task`: **beat every 1 minute**. Returns early when `IMAGE_UPLOAD` is off, which also pauses the GC. Otherwise it re-drives `PENDING` rows older than 5 minutes and `OVERRIDE_CLEARED` rows, both with `fail_count < 5`, and hard-deletes `TO_DELETE` rows older than 30 days.
  - `cleanup_expired_verification_codes`: **beat every 10 minutes**. `VERIFICATION_CODE_EXPIRE_MINUTES = 1`.
  - `add_width_height_to_media_task`: back-fills dimensions. It is enqueued from inside `ImgurStorage._save` and `ImgurImageFieldFile._get_image_dimensions`, so a storage backend enqueues work.
- **External side effects:** Discord webhook POST (image plus a `DiscordEmbed` with EXIF fields and the uploader's display name), Imgur API calls, S3/Oracle Object Storage writes, Firebase token verification, Google reCAPTCHA siteverify, RapidAPI.

## ⚙️ Internal State & Logic

- **Media pipeline** (`TemporaryMedia.status` is the state machine):
  1. `GenericUpload` first removes the EXIF GPS block from a JPEG, then writes the file to the default S3/Oracle bucket (`temporary_media/<uuid4>.<ext>`) as `PENDING`. `metadata` carries `spotting_event_id` or `calendar_incident_id`, and for Telegram-staged media the provenance (`telegram_message_id`, `telegram_chat_id`, `caption`, `mime_type`, `uploads_disabled`).
  2. `post_save` dispatches the tasks (see Inputs and Signals).
  3. Convert is gated on `IMAGE_UPLOAD` (`utils.should_upload_media()`). It is content-type aware: images are verified with Pillow and JPEG and JPEG2000 EXIF is extracted, with `bytes` and `IFDRational` values filtered out for JSON. Video skips Pillow and EXIF. Both paths post to the Discord webhook (images through `strip_gps` again, as defence in depth for files staged before the upload-time strip) and store the attachment ids and `caption` / `duration` / `content_type` / `file_name` on a new `Media`. `uploaded_discord` and `discord_res` make the Discord step idempotent across retries.
  4. For `SPOTTING_EVENT` it raises if `uploader_id != event.reporter_id`. It then creates the join row (`EventMedia` or `CalendarIncidentMedia`). For an incident photo the join row's `timestamp` is the EXIF `DateTime` (`"YYYY:MM:DD HH:MM:SS"`) parsed to a naive local datetime before the `Media` row is created; a missing or malformed value is `None` and does not fail the photo. An unknown upload type raises `RuntimeError`.
  5. Success sets `TO_DELETE`. A failure increments `fail_count`, and the beat task retries until it reaches 5. A broad `except Exception` turns every error into that counter; the error is logged but not stored on the row.
- **GPS stripping** (`common/exif.py`, `strip_gps(bytes) -> bytes`). Phone photos embed the position they were taken at, and before this it reached temp storage, the Discord CDN and Imgur even for an anonymous spotting. `GenericUpload` and the Telegram `media` handler strip it **before the file is staged**, and the convert task strips again before the Discord upload. The edit is lossless: it walks the JPEG markers to the EXIF APP1 segment, zeroes the GPS IFD (tag `0x8825`) and its out-of-line values, and unlinks the pointer from IFD0 by moving the later entries up one slot. The segment keeps its length, so the image data, ICC profile, `DateTime`, `Make`, `Model`, `Orientation` and every other tag stay byte-for-byte as sent. Only JPEG is touched: other formats and videos pass through as the same object, and an EXIF segment the parser cannot read is dropped whole (it cannot be shown to hold no position). So is one whose IFD0 holds `MAX_GPS_ENTRIES` (4) or more GPS pointers: a photo has one, and each removal rescans IFD0, so a crafted block of thousands used to pin the event loop for seconds (6 s for 2,500 + 2,500 entries). **HEIC is accepted as is:** `strip_gps` cannot edit it, so a HEIC upload keeps its GPS all the way to temp storage, the Discord webhook and Imgur. The owner chose this on 2026-10-21 ("do not refuse any image uploads"); an earlier version refused HEIC with a 400 (`is_heif`, removed). **Known limits:** HEIC/HEIF, PNG, WebP, TIFF and every other non-JPEG format are not edited server-side and pass through as received, GPS included (Pillow could only re-encode them, which is lossy for WebP); the web client strips JPEG, TIFF and PNG before upload, so a web photo in those formats is clean and the rest is not; XMP (`exif:GPS*`), the EXIF thumbnail, MakerNote and the extra images of a multi-picture JPEG are left alone; photos uploaded before the strip existed still carry their GPS in temp storage (kept 30 days after `TO_DELETE`), on the Discord CDN and on Imgur.
- **Storage strategies.** Three coexist. This is the most important thing to understand about the app.
  1. **Imgur** (legacy, but on the hot path): `ImgurStorage` plus `ImgurField` and `ImgurImageFieldFile`. It is a hand-rolled Django `Storage` that talks to Imgur through an authenticating proxy (`IMGUR_PROXY_API_URL`, with a subclassed `ImgurClient` that adds `Proxy-Authorization`). It is instantiated at import time as `STORAGE = ImgurStorage()` in `common/models.py`. `Media.file` (`# TODO: Deprecate`) is written on **every** upload: `common/tasks.py` creates `Media` with `file=ContentFile(temp_media.file.url, ...)`, which runs `ImgurStorage._save` and a live Imgur call. Both the storage and the module-level client swallow init failures and print "functionality disabled", so bad credentials fail silently. The `IMGUR_*` settings default to empty strings.
  2. **Discord CDN** (the canonical read path): `Media.url` and `discord_resizer_url` build `cdn.discordapp.com/attachments/<channel>/<file_id>/<file_name>` from stored ids. Nothing is written to Django's file system for these.
  3. **S3/Oracle**: Django's `default` storage, used only for the short-lived `TemporaryMedia` staging file. The boto3 resource in `views.py` is initialised but never used.
- **Auth state:** `utils.FirebaseUser` runs `get_or_create` on `firebase_id`, wrapped in `sync_to_async`. Users are created on their first authenticated request; there is no signup flow. Admin status is not stored locally. `IsAdmin` queries Firebase custom claims on every check, which is an uncached network call per field resolution. `get_current_user` keeps only the `User`: the verified token's claims are not put in the request context, so `has_admin_claim` cannot read the `admin` claim from the token and calls `auth.get_user` (which also sees a revoked claim at once, where a token's copy lives up to an hour). A failing Firebase call fails any field that needs the answer (see `MISTAKES.md`).
- **Analytics engine:** `utils.get_trends()` (~170 lines) is a generic date-bucketing aggregator for `DateGroupings` YEAR, MONTH, WEEK, and DAY. It handles ISO weeks, uses `pendulum` intervals, zero-fills through `get_combinations`, and derives `day_of_week`, `week_of_month`, and `is_last_day_of_month`. `operation` and `UserScalar.spotting_trends` reuse it. `get_default_start_time()` uses `date.replace()` in every branch. `free_range=True` starts at the earliest matching row, or at the default start when there is none.
- **Generic votes:** `Vote` is ContentType-based, with `unique_together (user, content_type, object_id)` and a value of +1 or -1. `incident` uses it through `GenericRelation` and `incident/services/votes.py`. `reporting` has its own separate `Vote` model.
- **Schema evolution** (22 migrations): identity first, then badges and nicknames; the `TemporaryMedia` staging table (0005) and its retry counters (0006); dimension back-fill (0007 to 0008); the `Clearance` and status trust model (0011 to 0012); Discord attachment columns (0013, 0017); `FeatureFlag` and Telegram id (0014 to 0016); generic `Vote` (0020 to 0021); media `caption` and `duration` with a widened `content_type` (0022). The arc runs from Imgur-only to staged, moderated, Discord-hosted, flag-gated, and metadata-aware.
- **Tests:** `common/tests.py` (~53 KB) holds the app's tests. `common/schema/mutations.py` is empty.

**Known defects (current):**

1. **The NSFW verdict does not gate publication.** For untrusted `PENDING` uploads, `common/signals.py` dispatches `convert_temporary_media_to_media_task` and `check_temporary_media_nsfw` at the same time. Convert refuses only `BLOCKED`, `TO_DELETE`, and `INVALID_UPLOAD`, so it can publish before the classifier finishes. The NSFW task also dispatches convert on `CLEARED`, so conversion can run twice. A `BLOCKED` verdict then arrives after the `Media` row exists. The intended design is a chain: the NSFW task dispatches convert only on `CLEARED`. Fix by having the signal dispatch only the NSFW task for untrusted `PENDING` uploads.
2. **Unbounded self-re-enqueue.** `check_temporary_media_nsfw`, `convert_temporary_media_to_media_task`, and `add_width_height_to_media_task` each call `time.sleep(2)` and `apply_async` on themselves when the row is not yet visible. There is no retry cap, which breaks the bounded-retry rule in `AGENTS.md`.
3. **Admin breakage.** `TemporaryMediaAdmin.prettified_metadata` calls `self.prettify_json()`, but the class inherits plain `admin.ModelAdmin` and the method never returns, so the page raises `AttributeError`. `search_fields = ["uploader"]` on `MediaAdmin` and `TemporaryMediaAdmin` needs a real lookup path such as `uploader__nickname`, or search raises `FieldError`.
4. **Permanent failures are invisible.** `RETRY_ELAPSED` is assigned nowhere, so a conversion that gives up stays `PENDING`, indistinguishable from a fresh row.
5. **`MediaScalar` and `MediaType` declare `width` and `height` as non-null,** but the model fields are nullable. Legacy rows raise resolution errors when exposed. `MediaType.file` had the same problem: 417 of the 2,856 dev rows (dated 2023-10 to 2024-03) have an empty legacy Imgur `file`, so any `medias` page containing one returned `data: null` (`Cannot return null for non-nullable field MediaType.file.`). Resolved by hiding those rows in `MediaType.get_queryset` (the feed lists 2,439 photos, as `mediasGroupByPeriod` counts); the photos themselves stay unreachable on that type, which has no `url` (Discord CDN).
6. **Feature flag bypasses.** `GenericUpload` ignores `IMAGE_UPLOAD`, and the same flag gates the GC (see Feature 4).

## 🧩 Extension Points & Hooks

- **`MediaMixin`** (`common/mixins.py`): shared `__str__` and `image_widget()`, used by `Media` and `TemporaryMedia` admin. The natural place for thumbnails or alt text.
- **`FeatureFlag` plus `should_upload_media()`**: a DB-backed, admin-toggleable kill switch (`list_editable = ["enabled"]`). Adding a `FeatureFlagType` member is the sanctioned way to gate new runtime behaviour.
- **`ClearanceType` / `Clearance`**: an extensible capability model, separate from Django permissions. New clearances need no join-table migration.
- **`TemporaryMediaType`**: documented naming convention `<app>_<model>`. A new destination needs a member, a branch in `GenericUpload`, and a branch in `convert_temporary_media_to_media_task`. Those two branches are the coupling a registry or strategy dict would remove.
- **Permission classes** (`rosak/permissions.py`: `IsLoggedIn`, `IsAdmin`, `IsRecaptchaChallengePassed`): composable per field or mutation.
- **Storage swap seam:** `ImgurStorage` implements the full `Storage` contract, so replacing it is a field-level change on `Media.file`, not a model rewrite.
- **DataLoader registry:** `CommonContextLoaders` is a plain dict, deep-copied per request. A new batch loader is one entry.
- **Commented-out scaffolding:** `common/schema/filters.py` (Media and User filters), `MediaInput` with `Upload` in `inputs.py`, and `create_medias` / `delete_medias` in `CommonMutations`.

## 💡 Potential Feature Opportunities

1. **Filterable media gallery with back-links to the entry each photo documents.** `medias` is a paginated Relay connection, but it has no filter argument, and `common/schema/filters.py` is fully commented out. Users can only page through every upload. Neither `MediaType` nor `MediaScalar` exposes the reverse side of `spotting.EventMedia` or `incident.CalendarIncidentMedia`, so a media card cannot link back to its entry.
   **Readiness:** `Ready`. Every FK exists. Uncomment and extend `MediaFilter`, pass `filters=MediaFilter` to the connection in `common/schema/schema.py`, and add a batch loader beside `medias_from_period_loader`. Fix the non-null `width` and `height` (Known defect 5) first, or legacy rows will error.

2. **Finish the Imgur retirement and delete the subsystem.** Per Known defects and Storage strategies, every upload still goes through `ImgurStorage._save`. Since all `IMGUR_*` settings default to empty, a deployment without Imgur credentials cannot complete an upload, even though Discord is the real host. The end state is small: `Media.url` as the only read path, the `file` column dropped, `imgurpython` and `get_imgur_token` removed.
   **Readiness:** `Partially ready`. Five call sites hold the coupling: `STORAGE = ImgurStorage()` (`common/models.py`), `MediaMixin.__str__` and `image_widget_html` (they read `self.file.name` and `self.file.url`), `add_width_height_to_media_task`'s `Media.objects.filter(file=filename)` lookup, `medias_group_by_period`'s `~Q(file="")` filter, and `MediaAdmin.fields`. The real blocker is legacy data. Rows created before the Discord attachment columns (migrations 0013 and 0017) have `file` set but `file_id` and `file_name` NULL, so `Media.url` returns `None` and dropping the column would lose the image. A re-host backfill has to run first: fetch `https://i.imgur.com/<file>`, repost through the Discord webhook, and fill the attachment columns. Files: `common/models.py`, `mixins.py`, `tasks.py`, `schema/scalars.py`, `schema/schema.py`, `admin.py`, plus deleting `imgur_field.py`, `imgur_storage.py`, and `get_imgur_token.py`.

3. **Upload receipts and a dead-letter state for failed conversions.** `POST /upload/` returns `201` as soon as the row is staged, and the uploader can learn nothing afterwards. There is no GraphQL type for `TemporaryMedia`. A conversion that dies (an unreadable image, a Discord failure, the `RuntimeError` on ownership mismatch, or an Imgur write) only bumps `fail_count`, and the photo silently never appears. Assign `RETRY_ELAPSED` when the retry cap is reached, persist the exception string in the existing `metadata` JSON instead of only logging it, and expose an uploader-scoped `my_uploads` query so a client can show "3 of 4 published, 1 failed".
   **Readiness:** `Partially ready`. The state machine, retry counter, and beat task exist. Missing: a `TemporaryMediaScalar` with an `IsLoggedIn` resolver, the `RETRY_ELAPSED` transition in the re-drive loop of `cleanup_temporary_media_task`, and an error write in the `except` block of convert. Fix the admin first (Known defect 3).

4. **A platform-wide feature-flag surface.** `FeatureFlagType` has one member, and `should_upload_media()` is its only reader. Two gaps. (a) `GenericUpload` ignores the flag, so with uploads disabled the endpoint still returns `201`, writes to the staging bucket, and never converts. It should reject at the edge with an explanatory `503`, and a `feature_flags` query would let clients hide the upload button. (b) `should_upload_media()` treats a missing row as off, so a fresh environment behaves as "disabled" with no warning. A data migration creating one row per `FeatureFlagType` member removes the ambiguity. Generalising to `is_enabled(FeatureFlagType.X)` makes runtime toggles available to the Telegram commands and to spotting submission.
   **Readiness:** `Ready`. Purely additive apart from a data migration. Also ungate the 30-day `TO_DELETE` garbage collection in `cleanup_temporary_media_task`. Right now the GC pauses whenever the kill switch is off, so the staging bucket grows without bound. Files: `common/enums.py`, `common/utils.py`, `common/views.py`, `common/tasks.py`, `common/schema/schema.py`, and a new migration.

5. **Content-hash de-duplication and duplicate-safe join rows.** Nothing stops the same photo being ingested twice. Every staged file gets a fresh `uuid4()` name, `Media` has no uniqueness beyond its UUID primary key, and neither `spotting.EventMedia` nor `incident.CalendarIncidentMedia` has a unique constraint on its pair. A double-tapped submit therefore spends Discord webhook quota, creates two `Media` rows, and shows the same image twice in an incident gallery. The bytes are already in memory when the webhook is built, so a `hashlib.sha256` digest costs nothing. Store it on `Media`, short-circuit to the existing row on a hit, and give admins a "possible duplicates" view.
   **Readiness:** `Not ready`. Needs a new indexed `Media.content_hash` column and migration. Decide the dedupe scope (global, per uploader, or per entry): `Media.uploader` is `on_delete=PROTECT`, and silently reusing another member's row would reattribute photo credit. Adding the `unique_together` constraints requires de-duplicating existing rows first. A backfill must re-download historical images from `cdn.discordapp.com` (and `i.imgur.com` for rows before 0013) to hash them. Files: `common/models.py` and migration, `common/tasks.py`, `spotting/models.py`, `incident/models.py`.

## 💡 Potential AI Feature Opportunities

1. **Multimodal moderation.** The NSFW step is a single binary RapidAPI call. Replacing it with a multimodal model would yield structured output (safety, is-this-a-train, blur or duplicate detection, plate and face PII flags) in the same `metadata` JSON, with no schema change. Fix the ordering defect first, or the verdict will not bind to publication.
2. **Automatic captioning and searchable tags.** `Media.caption` and `duration` exist (migration 0022) and surface on `MediaScalar`, and Telegram captions land in `metadata`. The open part is a vision-model caption and tags written to the same field. Conversion already has the image, EXIF (capture time, camera make and model; GPS is stripped at upload), the uploader, and the linked entry in hand. The disabled `MediaFilter` is the natural place to expose tags.
3. **Narrative user analytics.** `UserScalar` already resolves `favourite_vehicles`, `with_most_entries`, `spotting_trends` (with day-of-week and week-of-month features), and `spottings_count`. Those make a feature vector for an LLM "year in review" field, or for anomaly detection over `get_trends()` output. Both would be additive resolvers on an existing type, with no migration.
