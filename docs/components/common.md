# Component: common

## 📌 Purpose & Scope

- **Core Responsibility:** The foundation app. It owns **identity** (`User`, Firebase-backed), **authorization primitives** (`Clearance`, `UserClearance`, `FeatureFlag`), **the entire media ingestion pipeline** (upload → moderation → permanent hosting), and the **shared analytics/date-bucketing utilities** every other app's trend endpoints are built on. No domain concepts of its own — it is the substrate.
- **Distinction from sibling apps:** every other app models *things in the world* (vehicles, stations, spottings, incidents). `common` models *the people looking at them, the pictures they take, and the plumbing*.
- **Domain/Layer:** Django persistence + business logic + infrastructure adapters (custom `Storage` backend, custom `ImageField`), plus a Strawberry GraphQL slice (`CommonScalars`, `CommonMutations`) merged into the root schema, plus one DRF `APIView` outside GraphQL, plus 5 Celery tasks (2 on the beat schedule).
- **Maturity:** Live and load-bearing. Contains one clearly deprecating subsystem (Imgur) mid-migration to Discord CDN.

## 🔌 Interface & Data Flow

### Inputs / Props / Signals

- **GraphQL queries** (`common/schema/schema.py`, mixed into root `Query`):
  - `medias` — `ListConnectionWithTotalCount[MediaType]`, Relay connection with pagination + `MediaOrder`.
  - `user` — current viewer, `permission_classes=[IsLoggedIn]`; reads `info.context.user`.
  - `medias_group_by_period(type: DateGroupings)` — histogram of uploads.
- **GraphQL mutations** (`CommonMutations`):
  - `update_user(input: UserInput)` — `UserInput` exposes only `nickname`. `IsLoggedIn`.
  - `request_verification_code()` — mints a `UserVerificationCode` for Telegram account linking. `IsLoggedIn`.
- **Orderings:** `MediaOrder` (`uploader`, `created`, `modified`). **Filters:** `common/schema/filters.py` is entirely commented out — `MediaFilter`/`UserFilter` are drafted but disabled, so `medias` has no filter argument.
- **REST input (the real upload entry point):** `POST /upload/` → `common.views.GenericUpload` (wired in `rosak/urls.py`). Multipart form: `upload_type` (must be a `TemporaryMediaType` member), `image`, `related_id`. Authenticated by the `Firebase-Auth-Key` header, not by GraphQL context. Returns 400 / 401 / 403 / 201. `@transaction.atomic` + `@async_to_sync`.
- **Auth inputs (headers, allow-listed in `settings.py`):** `Firebase-Auth-Key` (verified via `firebase_admin.auth.verify_id_token`), `G-Recaptcha-Response` (consumed by `rosak.permissions.IsRecaptchaChallengePassed`, `RECAPTCHA_MIN_SCORE = 0.85`).
- **Django signal received:** `post_save` on `TemporaryMedia` (`common/signals.py`, registered via `CommonConfig.ready()`) — the only signal receiver in the app. On create it checks the uploader's `TRUSTED_MEDIA_UPLOADER` clearance, stamps `TRUSTED_CLEARED`, and dispatches `convert_temporary_media_to_media_task`. The NSFW branch is commented out, so **the moderation gate is currently bypassed** and every pending upload is converted directly.
- **Enums accepted:** `TemporaryMediaType` (`SPOTTING_EVENT`, `INCIDENT_CALENDAR_INCIDENT`), `TemporaryMediaStatus` (`PENDING`, `CLEARED`, `TRUSTED_CLEARED`, `OVERRIDE_CLEARED`, `BLOCKED`, `RETRY_ELAPSED`, `INVALID_UPLOAD`, `TO_DELETE`), `ClearanceType` (`TRUSTED_MEDIA_UPLOADER`), `FeatureFlagType` (`IMAGE_UPLOAD`).
- **Management command:** `get_imgur_token` — interactive OAuth PIN flow printing `IMGUR_ACCESS_TOKEN` / `..._REFRESH`.

### Outputs / Events / API Responses

- **GraphQL types** (`common/schema/scalars.py`):
  - `MediaType` — Relay `Node` over `Media` (`created`, `created_date`, `uploader`, `file`, `width`, `height`).
  - `MediaScalar` — non-Relay variant, adds `url` and `discord_suffix`. **This is the type `spotting` and `incident` reuse for their own media edges.**
  - `UserScalar` — the app's richest type; `firebase_id` is gated by `IsAdmin`, plus computed fields `short_id`, `display_name`-ish, `favourite_vehicles` (→ `operation.Vehicle`), `with_most_entries`, `spottings` (DataLoader), `spottings_count`, `media_count`, `spotting_trends`.
  - `UserVerificationCodeScalar`, `MediasGroupByPeriodScalar`.
  - `GenericMutationReturn` (`{ ok: bool }`) — **imported by `spotting` and `chartography` as their shared mutation return shape.**
  - Plain output types in `schema/types.py`: `UserSpottingTrend`, `WithMostEntriesData`, `FavouriteVehicleData`.
- **DataLoaders** (`common/schema/loaders.py`, exposed as `info.context.loaders["common"]` by `rosak/context.py`): `spottings_from_user_loader`, `media_from_id_loader`.
- **Celery tasks emitted** (all on `rosak.celery.app`):
  - `convert_temporary_media_to_media_task` — the pipeline core (see below).
  - `check_temporary_media_nsfw` — RapidAPI NSFW classifier, `RAPID_API_NSFW_THRESHOLD = 0.5`; **currently orphaned** (no live caller).
  - `cleanup_temporary_media_task` — **beat: every 1 minute**. Re-drives stalled `PENDING` (>5 min, `fail_count < 5`) and `OVERRIDE_CLEARED` rows; hard-deletes `TO_DELETE` older than 30 days.
  - `cleanup_expired_verification_codes` — **beat: every 10 minutes**, `VERIFICATION_CODE_EXPIRE_MINUTES = 1`.
  - `add_width_height_to_media_task` — back-fills dimensions; fired from *inside* `ImgurStorage._save` and `ImgurImageFieldFile._get_image_dimensions`, i.e. a storage backend enqueues work.
- **External side effects:** Discord webhook `POST` (image + `DiscordEmbed` carrying EXIF fields and uploader display name), Imgur API calls, S3/Oracle Object Storage writes, Firebase token verification, Google reCAPTCHA siteverify, RapidAPI.

## ⚙️ Internal State & Logic

- **The media pipeline** is the app's central state machine, driven by `TemporaryMedia.status`:
  1. `GenericUpload` writes the raw file to the **default S3/Oracle bucket** (`STORAGES["default"] = S3Boto3Storage`, key `temporary_media/<uuid4>.<ext>`) as `PENDING`, with `metadata` carrying `spotting_event_id` or `calendar_incident_id`.
  2. `post_save` signal → `convert_temporary_media_to_media_task`.
  3. The task gates on the `IMAGE_UPLOAD` feature flag (`utils.should_upload_media()`), verifies the image with Pillow, extracts JPEG/JPEG2000 EXIF (filtering `bytes` and `IFDRational` for JSON-serializability), POSTs to the Discord webhook, and persists the returned attachment ids onto a new `Media` row.
  4. Ownership re-check: for `SPOTTING_EVENT` it raises if `uploader_id != event.reporter_id`. Then creates the join row (`EventMedia` / `CalendarIncidentMedia`).
  5. Terminal state `TO_DELETE`; failures increment `fail_count` (retried until 5) — a broad `except Exception` swallows everything into that counter.
  - `uploaded_discord` + `discord_res` make step 3 idempotent across retries.
- **Three storage strategies coexist** — the most important thing to understand about this app:
  1. **Imgur** (`ImgurStorage` + `ImgurField`/`ImgurImageFieldFile`) — a hand-rolled `django.core.files.storage.Storage` talking to Imgur through an authenticating proxy (`IMGUR_PROXY_API_URL`, subclassed `ImgurClient` injecting a `Proxy-Authorization` header), with album auto-creation, base64 upload, and Django cache-backed `size`/dimension lookups. Instantiated at **module import time** as `STORAGE = ImgurStorage()`; both it and the module-level `ImgurClient` swallow init failures and print "functionality disabled", so a bad credential degrades silently. `Media.file` is marked `# TODO: Deprecate`.
  2. **Discord CDN** (current) — the canonical read path. `Media.url` / `discord_resizer_url` are computed properties composing `cdn.discordapp.com/attachments/<channel>/<file_id>/<file_name>`; **nothing is stored in Django's file system for these**, only the ids.
  3. **S3/Oracle** — Django's `default` storage, used exclusively for the short-lived `TemporaryMedia` staging file. `boto3` resource in `views.py` is initialized defensively and, notably, **never actually used**.
- **Auth state:** `utils.FirebaseUser` is a `sync_to_async`-wrapped helper doing `get_or_create` on `firebase_id` — **user rows are created lazily on first authenticated request**, so there is no signup flow. Admin status is *not* stored locally; `IsAdmin` re-queries Firebase custom claims per check (an uncached network call per field resolution).
- **Analytics engine:** `utils.get_trends()` is a ~170-line generic date-bucketing aggregator (`DateGroupings` YEAR/MONTH/WEEK/DAY, ISO-week handling, `pendulum` intervals, zero-filling via `get_combinations`, derived `day_of_week` / `week_of_month` / `is_last_day_of_month` flags). It is the analytical backbone reused by `operation` and by `UserScalar.spotting_trends`. Note `get_default_start_time()` attempts to assign to `date.month`/`date.day`, which are read-only — the YEAR/MONTH/WEEK branches would raise if reached.
- **Schema evolution** (17 migrations, `0001`–`0017`): identity first, then badges/nicknames, then the `TemporaryMedia` staging table (`0005`) and its retry counters (`0006`), a dimension back-fill (`0007`/`0008`), the `Clearance`/status trust model (`0011`/`0012`), Discord attachment columns (`0013`, `0017`), and `FeatureFlag` + Telegram id (`0014`–`0016`). The arc reads clearly as *Imgur-only → staged, moderated, Discord-hosted, flag-gated*.

## 🧩 Extension Points & Hooks

- **`MediaMixin`** (`common/mixins.py`) — shared `__str__` and `image_widget()` (`mark_safe` `<img>`) consumed by both `Media` and `TemporaryMedia` and rendered in their `ModelAdmin` `readonly_fields`. The natural place to hang thumbnails or alt-text rendering.
- **`FeatureFlag` + `should_upload_media()`** — a DB-backed, admin-toggleable kill switch (`list_editable = ["enabled"]`). Adding a member to `FeatureFlagType` is the sanctioned way to gate new behavior at runtime.
- **`ClearanceType` / `Clearance`** — an extensible capability model decoupled from Django's own permissions; new clearances slot in without migration of the join tables.
- **`TemporaryMediaType`** — documented naming convention (`<app>_<model>`); adding a member plus a branch in `GenericUpload` and `convert_temporary_media_to_media_task` extends the pipeline to a new destination model. The two branch statements are the coupling to reduce (a registry/strategy dict would remove it).
- **Strawberry permission classes** (`rosak/permissions.py`: `IsLoggedIn`, `IsAdmin`, `IsRecaptchaChallengePassed`) — composable per-field/per-mutation; `IsRecaptchaChallengePassed` is defined and available but unused inside `common`.
- **Storage swap seam** — `ImgurStorage` implements the full `Storage` contract, so replacing it (with a Discord- or S3-native storage) is a field-level change on `Media.file`, not a model rewrite.
- **DataLoader registry** — `CommonContextLoaders` is a plain dict deep-copied per request; new batch loaders are one entry.
- **Commented-out scaffolding ready to activate:** `common/schema/filters.py` (Media/User filters), `MediaInput` with `Upload` in `inputs.py`, `create_medias`/`delete_medias` in `CommonMutations`, and the NSFW check call in `signals.py`. `common/schema/mutations.py` and `common/tests.py` are both empty (0 bytes) — **the app has no test coverage at all**.

## 💡 Potential Feature Opportunities

1. **Filterable media gallery with back-links to the entry each photo documents.** `medias` is a Relay connection with pagination and `MediaOrder`, but `strawberry_django.connection()` in `common/schema/schema.py:25` is passed **no `filters=` argument at all** and `common/schema/filters.py` is 100% commented out — the only way to narrow the gallery is to page through every upload in `created`/`uploader`/`modified` order. Neither `MediaType` nor `MediaScalar` exposes the reverse side of `spotting.EventMedia.media` or `incident.CalendarIncidentMedia.media`, so a media card cannot link back to the spotting or incident it belongs to. Adding uploader / date-range / `content_type` filters plus an `entry` resolver batched through a new loader beside `media_from_id_loader` turns an unbrowsable upload firehose into a community photo wall — the thing rail enthusiasts actually want to scroll.
   **Readiness:** `Ready` — every FK already exists; the work is uncommenting and extending `MediaFilter` in `common/schema/filters.py`, wiring `filters=MediaFilter` into `common/schema/schema.py:25`, and adding a batch loader to `common/schema/loaders.py`. One trap to fix on the way: `MediaScalar` and `MediaType` in `common/schema/scalars.py` both declare `width: int` / `height: int` as non-null while `Media.width` / `Media.height` are `null=True, default=None`, so exposing more rows will start raising non-null resolution errors on legacy media.

2. **Finish the Imgur retirement and delete the subsystem.** `Media.file` carries a `# TODO: Deprecate` comment but is still on the hot path: `common/tasks.py:202` creates every new `Media` with `file=ContentFile(temp_media.file.url, name=temp_media.file.name)`, which routes through `ImgurStorage._save` and makes a live Imgur API call for every single upload. Because `ImgurStorage.__init__` catches every exception, prints `"Imgur login error, functionality disabled."` and never assigns `self.client`, that call then dies with `AttributeError` inside the broad `except Exception` in `convert_temporary_media_to_media_task` and merely increments `fail_count` — and since all eight `IMGUR_*` settings default to `""` (`rosak/settings.py:357-364`), a deployment without Imgur credentials cannot complete a single upload despite Discord being the real host. The end state is small and testable: `Media.url` as the only read path, the `file` column dropped, `imgurpython` and `get_imgur_token` removed.
   **Readiness:** `Partially ready` — five call sites hold the coupling: `STORAGE = ImgurStorage()` (`common/models.py:19`), `MediaMixin.__str__` / `image_widget_html` which read `self.file.name` and `self.file.url`, `add_width_height_to_media_task`'s `Media.objects.filter(file=filename)` lookup, `medias_group_by_period`'s `~Q(file="")` filter, and `MediaAdmin.fields`. The real blocker is legacy data: rows created before the Discord attachment columns landed (migrations `0013`/`0017`) have `file` set but `file_id`/`file_name` `NULL`, so `Media.url` returns `None` for them and dropping the column loses the image — a re-host backfill (fetch `https://i.imgur.com/<file>`, repost through the Discord webhook, fill the attachment columns) must run first. Touches `common/models.py`, `common/mixins.py`, `common/tasks.py`, `common/schema/scalars.py`, `common/schema/schema.py`, `common/admin.py`, and deletes `common/imgur_field.py`, `common/imgur_storage.py`, `common/management/commands/get_imgur_token.py`.

3. **Upload receipts and a dead-letter queue for failed conversions.** `POST /upload/` returns `201` the instant the `TemporaryMedia` row is staged, and after that the uploader can learn nothing — there is no GraphQL type for `TemporaryMedia` anywhere. A conversion that dies (unreadable image, Discord webhook failure, the `RuntimeError` raised when `uploader_id != event.reporter_id`, or the Imgur write above) only bumps `fail_count`, and the photo silently never appears on the entry. Worse, `cleanup_temporary_media_task` stops re-driving at `fail_count >= 5` but never marks the row: `TemporaryMediaStatus.RETRY_ELAPSED` is declared at `common/enums.py:23` and **assigned nowhere in the codebase**, so permanently dead uploads sit in `PENDING` forever, indistinguishable from ones staged ten seconds ago. Assign `RETRY_ELAPSED` at the cutoff, persist the exception string into the existing `metadata` JSONField instead of only `logger.exception`, and expose an uploader-scoped `my_uploads` query so the front-end can say "3 of 4 photos published, 1 failed — retry".
   **Readiness:** `Partially ready` — the state machine, retry counter and beat task all exist. Missing: a `TemporaryMediaScalar` plus an `IsLoggedIn`-gated resolver (`common/schema/scalars.py`, `common/schema/schema.py`), the `RETRY_ELAPSED` transition in the re-drive loop at `common/tasks.py:255-264`, and an error field written in the `except Exception` block at `common/tasks.py:240`. The operator half is outright broken today and should be fixed first: `TemporaryMediaAdmin.prettified_metadata` (`common/admin.py:98`) calls `self.prettify_json()` but the class inherits plain `admin.ModelAdmin` instead of `generic.admin.JsonPrettifyAdminMixin` (and the method never `return`s), so the one admin page for triaging a stuck upload raises `AttributeError`; `search_fields = ["uploader"]` on both `MediaAdmin` and `TemporaryMediaAdmin` also needs a real lookup path such as `uploader__nickname` or admin search raises `FieldError`.

4. **A real platform-wide feature-flag surface.** `FeatureFlag` is already admin-toggleable via `list_editable = ["enabled"]`, but `FeatureFlagType` has exactly one member and `should_upload_media()` is its only reader. Two concrete gaps make this a feature rather than just a seam. (a) `GenericUpload` never consults the flag: with image upload disabled the endpoint still answers `201 CREATED`, the file is written to the S3 staging bucket, and it is never converted — the flag should reject at the edge with an explanatory `503`, and a `feature_flags` GraphQL query would let the client disable the upload button up front instead of failing invisibly. (b) `should_upload_media()` treats a *missing* row as disabled (`feat_flag is not None and feat_flag.enabled`), so a fresh environment with no fixture silently behaves as "off"; a data migration creating one row per `FeatureFlagType` member removes the ambiguity. Generalising to `is_enabled(FeatureFlagType.X)` then makes runtime toggles available to the Telegram bot commands, spotting submission, and the gallery above.
   **Readiness:** `Ready` — purely additive apart from a data migration. Fix one coupling bug in the same pass: `cleanup_temporary_media_task` early-returns on that *same* flag (`common/tasks.py:252`), so disabling image upload also halts the stalled-`PENDING` re-drive **and** the 30-day `TO_DELETE` garbage collection — the GC half must be ungated or the staging bucket grows unboundedly for as long as the kill switch is off. Files: `common/enums.py`, `common/utils.py`, `common/views.py`, `common/tasks.py`, `common/schema/schema.py`, plus a new migration in `common/migrations/`.

5. **Content-hash de-duplication and duplicate-safe join rows.** Nothing stops the same photo being ingested twice: `get_temporary_media_file_name` gives every staged file a fresh `uuid4()` name, `Media` has no uniqueness beyond its UUID pk, and neither `spotting.EventMedia` nor `incident.CalendarIncidentMedia` declares a `unique_together` on `(event, media)` / `(calendar_incident, media)`. A double-tapped submit button therefore burns Discord webhook quota, creates two `Media` rows, and renders the same image twice in an incident's gallery — which matters when a single big service disruption draws dozens of near-simultaneous uploads. The bytes are already fully in memory at `common/tasks.py:151` (`requests.get(...)` immediately before `webhook.add_file(...)`), so a `hashlib.sha256` digest costs nothing: store it on `Media`, short-circuit conversion to the existing row on a hit, and give admins a "possible duplicates" grouping.
   **Readiness:** `Not ready` — none of it exists yet. Needs a new indexed `Media.content_hash` column plus migration; a decision on dedupe scope (global vs per-uploader vs per-entry — it matters because `Media.uploader` is `on_delete=PROTECT` and silently reusing another member's row reattributes photo credit); `unique_together` constraints on the two join models, which requires de-duplicating existing rows before the migration will apply; and a backfill that re-downloads every historical image from `cdn.discordapp.com` (and `i.imgur.com` for pre-`0013` rows) to hash it. Files: `common/models.py` + migration, `common/tasks.py`, `spotting/models.py`, `incident/models.py`.

## 💡 Potential AI Feature Opportunities

1. **Restore and upgrade the moderation gate.** `check_temporary_media_nsfw` already defines the whole shape — status transitions, threshold config, `metadata["nsfw_probability"]`, an `OVERRIDE_CLEARED` human-review escape hatch, and a re-drive loop in the beat task. Swapping the single RapidAPI call for a multimodal model turns one binary score into structured output (safety, plus is-this-actually-a-train, blur/duplicate detection, plate/face PII flags) written to the same `metadata` JSON field with no schema change.
2. **Automatic media captioning and searchable tagging.** The pipeline already opens every image with Pillow and has EXIF (timestamp, GPS-capable), the uploader, and the linked `Event`/`CalendarIncident` in hand at the exact moment of conversion. Adding a vision-model caption plus tags on `Media` would make `medias` genuinely searchable — and the disabled `MediaFilter` in `filters.py` is the natural place to expose it.
3. **Narrative user analytics.** `UserScalar` already computes `favourite_vehicles`, `with_most_entries`, `spotting_trends` (with day-of-week and week-of-month features) and `spottings_count`. That is a ready-made feature vector for an LLM-generated "your spotting year in review" field, or for anomaly detection over `get_trends()` output — both additive resolvers on an existing type, requiring no migration.
