## [2026-10-24] spotting: report_spotting_today at 03:01 for the 27-hour service day

- `report_spotting_today` fires at 03:01 local, not 00:00 (`rosak/celery.py`, `crontab(hour="3", minute="1")`). Each run digests the submissions in `[D 03:01, D+1 03:01)`, selected by `Event.created`, and is headed with D. A run on Tuesday 03:01 covers `[Mon 03:01:00, Tue 03:01:00)` and is headed Monday. Submission time was chosen over the user-entered `spotting_date`. (`f03d8d8`)
- D is `effective_spotting_date(now)` minus one day, with the default 03:00 cutoff rather than 03:01, so a worker clock up to 60 s behind beat's still reports the window that just closed. A run from 03:00:00 to 03:00:59 reports the window that closes at 03:01, which is still open for up to 60 s. A run before 03:00 reports the last fully closed window. A late pickup reports the same window as an on-time run. (`f03d8d8`)
- `telegram_provider.utils.get_daily_updates` takes a keyword-only `created_between`. With a window, it selects spotted vehicles by `Event.created` in `[start, end)`. Without one, the `spotting_date` path is unchanged, so `/spotting_today` keeps its `spotting_date` and 03:00 cutoff. (`f03d8d8`)

The new checks cover the 03:01 beat and its timezone, the window edges, submission time over `spotting_date`, on-time and late runs, runs before 03:01, and a window with no submissions. `GetDailyUpdatesTests.test_without_a_window_events_are_picked_by_spotting_date` (`telegram_provider/tests.py`) pins the `spotting_date` path. ## [2026-10-24] common: UserScalar.spottings pages with limit and offset (F252)

- `UserScalar.spottings(limit: Int = null, offset: Int! = 0)`. With no `limit` the field is unchanged: the `spottings_from_user_loader` batch. With a `limit` of 1 to 200 it returns one page after the first `offset` rows, newest submission first (`created` descending, then `id` descending, so rows that tie never skip or repeat between pages). A `limit` outside 1 to 200, a negative `offset` and an `offset` without a `limit` are `GraphQLError`s. (`939f1a5`)
- Privacy is the rule of the full list, on both paths: the owner always, anyone else only on a public history (`null` otherwise), and anonymous spottings only for the owner and admins through `_events_shown_to_viewer`. The loader never ordered its rows (it collects them into a `set`), so the unpaged list has no promised order; the page order is new and matches the owner's own history (`events(order: {created: DESC})`). (`939f1a5`)
- The page is a queryset, not a list, so the optimizer joins `vehicle` and prefetches `lines`: on the dev DB a 30-row page with `vehicle { vehicleType lines }` and `isMine` costs 4 queries (93 as a list of instances), however many rows. `reporter` is still joined by hand because the optimizer cannot see that `isMine` reads it (34 queries without it). The first page of the largest dev history (20,610 spottings) takes 27 ms and a page at offset 20,000 takes 34 ms, so no index was added. (`939f1a5`)
- Tests: `UserSpottingsPagingTests` (`common/tests.py`, 7): owner paging with anonymous rows and a three-way `created` tie across page sizes 1 to 200, visitor paging without the anonymous rows (signed in and logged out), admin paging with them, a private profile (`null` for visitors, paged for the owner), the paged walk agreeing with the full list for every viewer on a public and a private profile, bad `limit` / `offset` rejected, and a page costing the same queries at 1 and 9 rows. Six mutations of the resolver (drop `select_related`, drop the privacy gate, leak anonymous rows, flip the tie-break, flip the direction, drop the limit check) each fail at least one test. (`939f1a5`)
