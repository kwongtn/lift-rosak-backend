## [2026-10-22] incident / operation: calendarIncidents filters

- `calendarIncidents` takes five new opt-in inputs on `CalendarIncidentFilter`: `activeNow`, `upcomingWithinDays`, `lines` and `stations` (`699126d`), and `status` (`07c8289`). The schema change is additive. Each input is a plain `Q` condition. The inputs AND with each other and with `date`, they OR through `OR: {...}`, and null means no filter.
- `activeNow: true` means started and not yet ended, or open-ended, with both edges inclusive. `activeNow: false` is the exact complement. `upcomingWithinDays: N` means not started yet and starting within N days. An N outside 1 to 60 raises a `GraphQLError`. The lower edge is strict, so no incident matches both inputs.
- `lines` and `stations` take the nested `LineFilter` and `StationFilter`. They match an incident tagged with at least one matching row. A declarative draft repeated an incident once per matching row, so the first commit matched with `pk IN` (`699126d`). That version ran the nested filter on `CalendarIncident` with a prefix, and review showed that `StationFilter.location` then raised `FieldError`. The nested filter now runs on `Line` or `Station` itself, and the match is a `pk IN` over the many-to-many through table (`4d30b6b`). Every nested input works, an incident is never repeated, `NOT` keeps untagged incidents, and an empty filter means no filter.
- `StationFilter.stationLine` never worked. The declarative field looked up `station_line`, and Django names the reverse relation `stationline`. It is now a `filter_field` with a `stationline__` prefix (`b8a56ab`, mypy ignore in `b917479`). This also fixes the root `stations(filters: {stationLine: ...})`. The public input is unchanged and only its place in the SDL moved.
- `status` is an exact match on `CalendarIncidentStatus` and is opt-in. The root `calendarIncidents` still has no status gate, because the insiden calendar shows and tags drafts. A surface that must show only approved notices, such as the Rider board, sends `status: LIVE` together with `activeNow: true` or `upcomingWithinDays`.
- Docs: `docs/components/incident.md` and `operation.md` (`5df5fef`, `b8a56ab`, `4d30b6b`, `07c8289`). The SDL snapshot was regenerated in `699126d`, `b8a56ab` and `07c8289`. There is no breaking change.
- Tests: 15 new. `CalendarIncidentWindowAndTagFilterTests` (12, through GraphQL) covers both windows and their validation, `OR` and `date` composition, one row per incident for `lines` and `stations`, `location` and `stationLine` through `stations`, `NOT`, null and empty inputs, the `status` filter and soft-deleted incidents staying hidden. `CalendarIncidentWindowEdgeTests` (2, frozen clock) pins the inclusive and the strict edges. `operation.tests` gains `test_stations_filter_by_nested_station_line` for the root query.
- Verification: full serial suite `manage.py test --keepdb` - 616 tests, OK; `ruff`, `manage.py check` and `makemigrations --check` clean. Live on the dev API, `activeNow: false` returned all 280 incidents, and validation errors, de-duplication, `NOT` and `OR` behaved as in the tests. Dev has no current or upcoming incident, so `activeNow: true` and `upcomingWithinDays` return nothing there. The tests prove the positive paths.
- Left out: no server-side status gate on `calendarIncidents`. `MAX_UPCOMING_DAYS` is not shared with the 60-day width cap of the `date` filter, because the two limits are unrelated. The root nested filters (`stations` with `line` or `stationLine`, `assets` with `station`) still join, so a station repeats per matching row unless the client sends `DISTINCT: true`. The `month` branch of `CalendarIncidentFilter.date` keeps its known off-by-one.

## [2026-10-22] incident: status-history daysAgo and lineStatusWeekProfile

- `lineStatusHistory`, `networkStatusHistory` and `linesStatusHistory` take `daysAgo: Int = 0` (`19db35f`). `null` reads as 0. The valid range is 0 to 56 (`MAX_HISTORY_DAYS_AGO`). Any other value raises `LineStatusValidationError`, even for an empty `lineIds`. `daysAgo: N` reads the service day that started N service days before the current one. It counts service days with the 03:00 default start, not calendar days. A past day is read whole, `[day_start, day_start + 24h)`, bucketed like today, and answers `[]` when it has no report.
- The end of a past day is exclusive: the read uses `created__lt` and `bucket_hourly` caps at `day_start + 24h`. Without both, a report at the next day's first instant would turn an empty day into 24 empty buckets.
- New query `lineStatusWeekProfile(lineId: ID!, weeks: Int = 6, dayStartHour: Int = 3): [LineStatusWeekBucket!]!` (`0755450`). One query over the rolling window `[now - weeks * 7 days, now]` feeds the pure `bucket_week_profile`. The result is all 168 (weekday, hour) slots once the line has any report in the window, and `[]` otherwise. `weekday` is 0 (Monday) to 6 (Sunday) of the service day. `hour` is the local clock hour. `count` is a raw total over the window. Slots run Monday first and, within a weekday, in service-day hour order. `weeks` must be 1 to 12 and `dayStartHour` 0 to 23. An unknown line answers `[]`. The dominant-status tie-break and the `statusCounts` order are shared with the hourly buckets through `_dominant_status`, `_dominant_status_enum` and `_status_count_rows`.
- Review fixes: `lineStatusHistory` rejected a non-numeric `lineId` with a raw `ValueError`. It now answers `lineId must be a numeric line id.` through the shared `_numeric_line_id` (`5f94ae8`). A settings test pins `USE_TZ` off, because the weekday and the hour read the stored clock as local time. The Python tally of the week profile carries a `# shortcut:` comment and a doc warning (`4e1686c`).
- Docs: `docs/components/incident.md` (`fca4991`, `5f94ae8`, `4e1686c`). Both schema changes are additive, and the SDL snapshot was regenerated in `19db35f` and `0755450`.
- Tests: 27 new in `incident/tests.py`. `DaysAgoHistoryTests` (7) covers the previous service day, an empty day, service days across the 03:00 rollover, the network and multi-line loaders, one query per loader, the range check, and the next day's first instant. `DaysAgoQueryTests` (4) goes through the schema. `WeekProfileBucketingTests` (6, `SimpleTestCase`, so any database access fails) covers the slots, their order, the service-day weekday, the empty window, parity with `bucket_hourly` and the `USE_TZ` pin. `LineStatusWeekProfileTests` (4) covers the loader. `LineStatusWeekProfileQueryTests` (5) covers the query. `test_graphql_history_queries_reject_a_non_numeric_line_id` covers the review fix. Mutation checks confirmed that a broken end exclusivity, service-day shift, window bound, severity tie-break or hour rotation each fails a test.
- Verification: full serial suite - 656 tests, OK; `ruff`, `manage.py check` and `makemigrations --check` clean on the final commit. The live endpoint serves the final schema (introspection). Every live probe returned `[]` because dev has no report in the probed windows, so the with-data behaviour is proven on the test database only.
- Left out: no database-side aggregation for the week profile. It tallies every row of the window in Python, and the `# shortcut:` comment and the doc warning name the upgrade (`Count` grouped by status, hour and shifted weekday). `daysAgo`, `weeks` and `dayStartHour` are nullable `Int` with literal defaults, not `strawberry.Maybe`, because the SDL needs literal defaults such as `weeks: Int = 6`. No index was added. `(line, created)` serves the line reads, and the network read stays a sequential scan of the day's rows.
- Open product questions for the frontend to confirm: (1) `weekday` is the weekday of the service day, so a 01:30 Tuesday report counts as Monday hour 1 at the default 03:00 start, and `dayStartHour: 0` gives calendar weekdays. (2) Slots run Monday first and in service-day hour order, so a client that wants 0 to 23 re-sorts by `hour`. (3) `null` reads as the default, not as `Maybe`. (4) `weeks` is a rolling window that includes today so far, so a slot holds `weeks` or `weeks + 1` occurrences, and `count` is raw for the client to threshold.

## [2026-10-22] incident: web push subscriptions and MAJOR-incident alerts

- New model `incident.PushSubscription` (`TimeStampedModel`): a unique FCM `token`, a `user` FK with CASCADE and a `lines` many-to-many. It ships with migration `0033_pushsubscription` and an admin page that shows the token prefix, the user and the creation time (`ce3d947`).
- `registerPushToken(token, lineIds)` and `unregisterPushToken(token)` are `IsLoggedIn` and return `GenericMutationReturn`. `pushSubscription(token)` is `IsLoggedIn` and returns the caller's own row, or null for an unknown token or another account's token. Register upserts by token, replaces the lines, and re-owns a token that another account held. Unregister deletes only the caller's row and answers ok when nothing matches. The schema change is additive and the SDL snapshot was regenerated (`ce3d947`).
- `notify_major_incident` in `incident/services/push.py` sends nothing unless the incident is `LIVE` and `MAJOR`. It sends to the distinct tokens of the affected lines in chunks of 500 through `messaging.send_each_for_multicast`. The title is the line codes plus the incident title, cut to 100 characters. The body is `brief` cut to 150. The link is `{FRONTEND_BASE_URL}/insiden/YYYY-MM-DD`. A token that FCM reports as unregistered or bound to another sender is deleted. At most one push goes out per line per 30 minutes, claimed with an atomic `cache.add` (`ce3d947`).
- `incident.tasks.notify_push_subscribers` wraps it with `autoretry_for=FirebaseError`, `max_retries=3` and a backoff capped at 600 s. `approve_incident` queues it through `transaction.on_commit(..., robust=True)`, so a broker outage is logged and never fails a saved approval. It is queued when a `PENDING_APPROVAL` incident goes `LIVE`, whatever its severity, because the task does the `MAJOR` check. It is also queued when a revision merge leaves the parent `LIVE` and `MAJOR` and the parent was not both before (`ce3d947`, `4d66938`).
- Review fixes (`4d66938`): `send_each_for_multicast` returns an FCM outage per token instead of raising. The retry therefore never fired, and the cooldown stayed claimed. The service now raises `UnavailableError` when a chunk delivered nothing and saw a transient error. That releases the claims and lets the retry run. A token that FCM rejects as an invalid argument is deleted only when another message in its chunk was delivered. A token is 1 to 2048 ASCII characters, because the unique btree index refuses a row over 2704 bytes. An account keeps at most 20 tokens, and registering past that deletes the least recently registered ones. `lineIds` holds at most 100 distinct ids, and a line id past the bigint range is reported as unknown. The cooldown is claimed only for affected lines that have subscribers. A merge that escalates a `LIVE` `MINOR` parent to `MAJOR` pushes.
- Docs: `docs/components/incident.md` and `docs/APPS.md` (`d5cac94`, `3c398f7`).
- Tests: 21 new in `incident/tests_push.py`, collected by `manage.py test incident`. `PushRegistrationTests` (10, through GraphQL) covers create, upsert, re-owning, an anonymous caller, bad tokens and line ids, a maximum-length token under the unique index, the per-account cap, unregister and the own-row-only query. `NotifyMajorIncidentTests` (7, `LocMemCache`, FCM mocked) covers recipients and payload, MINOR and unapproved incidents, the cooldown per line, claims only for lines with subscribers, pruning of dead tokens, an invalid argument with nothing delivered, and four sends with released claims for an outage. `ApprovalEnqueuesPushTests` (4) covers approval, a MINOR approval, a revision merge and a broker outage.
