# Progress — 2026-10-03

## [2026-10-03] incident: network + multi-line service-day status history (B1, B2)

- **What**: two **additive** root queries beside the existing `lineStatusHistory`:
  `networkStatusHistory(dayStartHour: Int = 3): [LineStatusHourBucket!]!` (B1 — one
  read over *every* line's reports in the service day) and
  `linesStatusHistory(lineIds: [ID!]!, dayStartHour: Int = 3): [LineStatusHistory!]!`
  (B2 — per-line buckets for N lines in ONE query, new
  `LineStatusHistory { lineId, buckets }` scalar). Both are public, like
  `lineStatusHistory`.
- **The shape of the change**: not two new implementations, but one shared private
  helper. `_service_day_entries(line_ids, day_start_hour=, now=)` in
  `services/line_status.py` is now the single place the `dayStartHour` validation, the
  `service_day_start` arithmetic and the `LineStatusReport` read live; it returns
  `(now, day_start, rows)` with each row paired to its `line_id`, and `line_ids`
  selects the scope — `None` = every line, a sequence = `line_id__in`, and an **empty
  sequence returns before the query**, so `lineIds: []` costs zero queries. All three
  loaders bucket through `bucket_hourly`, so the 24-hour contract cannot drift.
  `load_line_status_history` keeps its public signature and its one-query-per-call
  contract (its SQL now filters `line_id__in=[…]` rather than `line_id=…` — same rows,
  same one query).
- **Return invariants the client can rely on**: 24 buckets (`03:00 → 02:00`, empty
  hours zero-filled) once anything is reported in the window, and `[]` when nothing is.
  `networkStatusHistory` is a **network** aggregate — an hour's `count` /
  `dominantStatus` / `statusCounts` tally every line, so it is not a per-line series.
  `linesStatusHistory` returns one entry per requested id **in the requested order**,
  and an entry existing does not mean the line reported anything: `buckets: []` is the
  per-line "no data" state. Duplicate ids collapse to one entry. `lineIds` is capped at
  `MAX_LINES_PER_HISTORY_REQUEST = 64` (a `LineStatusValidationError` → `GraphQLError`,
  not a silent truncation), and an unparseable id is a validation error rather than a
  500. The cap bounds rows pulled into one response, not query count.
- **Also de-duplicated at the GraphQL edge**: `_hour_bucket()` in
  `schema/resolvers.py` is now the only place a `HourBucket` becomes a
  `LineStatusHourBucket`, so the three fields cannot disagree about the
  `PassengerStatus` mapping or the `statusCounts` order (enum declaration order, zeros
  omitted, always summing to `count`).
- **SDL snapshot** regenerated (`type LineStatusHistory` + the two `Query` fields);
  the diff is 7 pure insertions, so `EXPECTED_ACCEPTED_BREAKING_CHANGES` is untouched.
  No model change and **no migration**.
- **Tests**: 22 new Django-unittest tests in `incident/tests.py` (not the pytest tree —
  pytest is not installed in the container, so `incident/tests.py` is the gate-visible
  home): `NetworkStatusHistoryTests` (7), `LinesStatusHistoryTests` (8),
  `StatusHistoryQueryTests` (7, both queries executed through the real `rosak.schema`
  plus a cross-check that the single-line, batched and network reads agree bucket for
  bucket). Service-level fixtures are anchored to **absolute** wall time
  (`datetime(2026, 1, 2, 3, 0)` + `now=datetime(2026, 1, 2, 20, 0)`), never through
  `service_day_start`; query counts are pinned with `CaptureQueriesContext` (1 for the
  network read at 6 rows, 1 for 2 lines × 3 rows, **0** for an empty id list). The
  resolver-level fixtures place their reports on the *current* hour and pass that hour
  as `dayStartHour`, which keeps them inside `[day_start, now]` at every hour of the
  day without going near `service_day_start`.

## [2026-10-03] tests: freezing `django.utils.timezone.now` does NOT freeze `auto_now_add`

- **Discovered while** clock-auditing the new history tests, and it qualifies the
  prevention advice in the 2026-10-01 `service_day_start` MISTAKES entry (which
  recommends re-running a suspect test module "with `django.utils.timezone.now`
  frozen at a few hours"). That technique **cannot** work on a fixture that creates its
  rows with `objects.create()` and no explicit `created` — see the MISTAKES entry
  written today for the mechanism and the symptom.
- **Observed, not assumed**: with `django.utils.timezone.now` patched to
  `2026-10-03 00:05`, a `LineStatusReport.objects.create(...)` in the same test body
  produced `created = 2026-10-03 00:15:48` (the REAL clock), while
  `timezone.now()` read `00:05` and `line_status.service_day_start(...)` correctly
  resolved to the previous day's 03:00. The resulting spurious failure
  (`len(buckets) == 24` → `0`) looks exactly like the rollover trap the audit was
  hunting, which is what makes it worth writing down.
- **Mechanism**: `model_utils/fields.py` binds the function at import —
  `from django.utils.timezone import now` — so `AutoCreatedField.pre_save` /
  `AutoLastModifiedField.pre_save` call that captured reference, while
  `django.db.models.fields.DateTimeField.pre_save` (a `auto_now_add` on a plain
  `models.DateTimeField`) goes through `timezone.now()` and IS patched. Two spellings
  of "now" that look interchangeable and are not.
- **Consequence for this change**: it is why the resolver-level fixtures place their
  reports on the current hour (so the loader's real `now` and the row's stamp always
  agree) while the service-level fixtures set `created` explicitly — the two layers
  need different anchors for this reason, not for style.
