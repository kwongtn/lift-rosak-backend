# 2026-10-01

## Incident: `SocialMediaLink` — flat one-level thread → ordered nested tree

- **What**: related social-media links could be grouped into a "thread" that was a
  **flat, one-level group**: a root row with members hanging off it, a
  service-enforced "depth is exactly 1" rule, and no ordering inside the group.
  Grouping is now an **ordered nested tree** — a sublink can have its own
  sublinks, to a bounded depth, with siblings in a defined, user-settable
  sequence. This supersedes `SocialMediaLink.thread` and everything documented
  about it in `docs/progress/2026/09/30.md`.
  - **Dependency**: `django-tree-queries>=0.26.1` added to `pyproject.toml`;
    `"tree_queries"` added to `INSTALLED_APPS` (omitting it raises
    `tree_queries.E001`); image rebuilt. Both lockfiles regenerated with `rye`
    and the diff is **one inserted line each** (`django-tree-queries==0.26.1`) —
    no unrelated pin churn. Chosen over `django-treenode` because it stores
    **nothing**: `tree_path` is a recursive-CTE annotation recomputed per query,
    so there is no redundant column, no per-process in-memory tree and no signal
    on every `save()`. That matters because `SocialMediaLink` is a high-write
    table served by several processes (granian + celery worker + beat).
  - `incident/models.py`: `SocialMediaLink(TimeStampedModel, OrderableTreeNode)`.
    The `thread` self-FK is replaced by
    `parent = TreeNodeForeignKey("self", null=True, blank=True, default=None,
    on_delete=SET_NULL, related_name="children")` plus the library's `position`
    (`PositiveIntegerField(default=0, db_index=True)`), with
    `class Meta(OrderableTreeNode.Meta)` inheriting `ordering = ["position"]`.
    `on_delete=SET_NULL` is a deliberate non-destructive trade and the **opposite**
    of the library's default (the inherited FK is hardcoded `CASCADE`):
    deleting a link **promotes** its sublinks to roots instead of cascade-deleting
    a group the operator never asked to delete. It works because the library
    finds the tree by the field **name** `parent` and its CTE hardcodes
    `parent_id`, and it never inspects `on_delete` — so changing only
    `on_delete` is safe while **renaming the field would break the tree**.
  - **Cycle guard in `save()`**: the library's loop protection lives in
    `TreeNode.clean()`, which only `full_clean()` ever calls, so a plain
    `link.parent = other; link.save()` writes a cycle **silently** — and the
    recursive CTE anchors on `parent_id IS NULL`, so the row is then unreachable
    from every tree query while `ancestors()` on it raises `DoesNotExist` (a 500,
    not an empty list). `SocialMediaLink.save()` therefore runs
    `_guard_tree_cycle` before delegating to `super()`, raising
    `ValidationError` (the same type `TreeNode.clean()` raises, so a caller
    already handling `full_clean()` needs no new `except`; deliberately not
    `IncidentServiceError`, which a model cannot import without a cycle, and a
    bare `assert` is stripped under `python -O`). The degenerate self-parent case
    is caught up front because the ancestor walk cannot see it. `full_clean()`
    is **not** called instead — it would re-validate every unrelated field on
    every save, and the library's own `clean()` still runs for any caller that
    opts in, so the guard is additive. The check is skipped when `update_fields`
    is passed without `parent`, **matching both of the field's spellings** —
    Django accepts a field's `name` or its `attname` in `update_fields` and
    matches on either, so `save(update_fields=["parent_id"])` is a legal
    re-parent write and a carve-out that tested `"parent"` alone was a hole
    straight into the cycle (verified by intercepting `Model._do_update`: the
    UPDATE carried `['modified', 'parent']` and nothing raised). The
    `telegram_provider.handlers` `save(update_fields=["status"])` path still
    skips the two-query walk.
    `save.alters_data = True` is set explicitly so the override does not look
    like an accessor to Django's collector.

- **Migration `0031_socialmedialink_tree_parent_and_more.py`** — hand-ordered,
  not as `makemigrations` emitted it (which put `RemoveField(thread)` second):
  `AddField(parent)` → `AddField(position)` → `AlterModelOptions` (state-only;
  `ordering` is not a DB property) → `RunPython(convert_threads_to_tree,
  revert_tree_to_threads)` → `RemoveField(thread)`. The order is load-bearing:
  the conversion needs `parent` to exist, the rank must read the *final*
  `parent_id`, and `thread` must still be there when the conversion reads it.
  The forward `RunPython` is a single `UPDATE parent_id = F("thread_id")` for
  members followed by a `Window(RowNumber())` partitioned by `parent_id`, ordered
  by `(occurred_at ASC, id ASC)`, **times 10**, written with `bulk_update` in
  batches of 500. Reversibility is real: Django replays the list backwards, so
  `AddField(thread)` happens *before* the reverse `RunPython` can reconstruct
  `thread` from `parent` — which is only possible because `RemoveField` is the
  **last** forward operation. `position` is zeroed on the way back (no pre-0031
  column maps onto it) and a deeper tree collapses, which restores the
  pre-0031 *shape* without dropping a row.
  - **The conversion is defensive code, not a data rescue.** The dev database
    holds **44 links and zero group members** (verified after the migration:
    44 rows, 44 of them roots, 0 with a parent), so the `thread_id` loop matches
    nothing there. It is written anyway and deliberately not short-circuited,
    because a data migration runs on every apply, not only the deploy it was
    authored against. The `position` backfill does real work either way.
  - No `TreeQuerySet` appears in the file: `apps.get_model()` returns a
    historical model with a plain `Manager`, and the ranking spells its
    `ORDER BY` out on the `Window` so the rank is a total, deliberate sequence
    rather than an inherited default. (The historical `Meta.ordering` *is*
    `["position"]` here — `AlterModelOptions` runs before the `RunPython`.) The
    migration reads no datetime into Python (only the integer rank is written
    back), so the naive-local-timezone trap catalogued in `MISTAKES.md` cannot
    bite it — the docstring says so, and says that a future revision growing a
    Python-side loop must re-check it first.

- **`incident/services/social_link_threads.py`** — rewritten. Nesting replaces
  the old depth-1 rule ("`thread` always points at a ROOT") with two invariants
  plus the unchanged permission half: **no cycles**, and **depth ≤
  `MAX_THREAD_DEPTH = 3`** (a root is 0, so four levels). Neither is a DB `CHECK`
  — a cross-row invariant is not a row constraint — and both are checked **before
  any write**, so a rejected call writes nothing.
  - `group_social_media_links(user, *, is_admin, link_ids, parent_id=None)`:
    `parent_id=None` **starts a new conversation** (the root is elected as the
    smallest `(occurred_at, id)`, the rest become its direct children in that
    order); `parent_id=<a link>` **nests the selection as direct children of that
    link**, root or sublink alike — the old service resolved a sublink target up
    to its root and flattened onto it, and removing that flattening is the point
    of the wave. Returns the **root of the affected conversation**.
  - `ungroup_social_media_links`: clears `parent` on exactly the named links.
    **Deliberately not a cascade** — a link's own sublinks stay parented to it,
    so the branch continues under a representative that is now itself a root, and
    every intermediate state is a legal tree. It does not renumber the promoted
    roots, so two roots can legitimately share a `position`.
  - `reorder_social_media_links` (**new**): a **permutation of one existing
    sibling set**, not a move. Every id must already be a child of `parent_id`
    (of `null` when `parent_id is None`); anything else is rejected with a
    message pointing at `groupSocialMediaLinks`. It exists because `position` is
    a stored, user-visible sequence and nothing else in the API could set it:
    `group` only ever appends in `occurred_at` order, so the console could not
    put a link first, and a stored sequence nobody can set is not a feature.
  - **Positions are assigned explicitly and deterministically** (`10, 20, 30, …`)
    rather than relying on the library's auto-append, because **re-parenting
    never recomputes `position` at all**, the auto-assign is a non-atomic
    read-then-write, and `bulk_create` bypasses it entirely. `_reindex_siblings`
    renumbers the whole affected sibling set on every structural write.
  - **Permission**: admin any / submitter own, checked per link on the whole
    selection **and on the named target parent**, rejected as a unit. Checked on
    the *named* link rather than the conversation's root — a submitter who owns a
    sublink of a tree an admin created can deepen it, which is integrity and not
    confidentiality. That trade disappears the moment submitters may nest under a
    conversation they did not contribute to.
  - Every multi-link write is one `transaction.atomic()` block, and every
    `select_for_update` carries a deterministic `order_by` (an unordered lock
    takes rows in planner order, so two overlapping calls deadlock — a 500,
    contained by the single atomic block). Grouping orders by
    `(occurred_at, id)` because that ordering *is* the root-election rule;
    everything else orders by `pk`.

- **GraphQL** — ⚠️ a **deliberate, un-aliased breaking change**:
  - **Removed**: `SocialMediaLinkScalar.threadId` / `threadSize` / `threadLinks`
    and `Mutation.groupSocialMediaLinks`'s `threadId` argument. No alias: an
    alias would keep serving the one-level behaviour it named, so a stale client
    would keep nesting under the thread *root* and never discover the sublink
    level it now wants.
  - **Added**: `parentId: ID` (the parent link's id, read straight off the row —
    no query, no loader), `position: Int!`, `sublinkCount: Int!`, and
    `sublinks: [SocialMediaLinkScalar!]!` (recursive; direct children in
    `position` order). Plus `reorderSocialMediaLinks`.
  - **`isThreadRoot: Boolean!` is NOT added — it pre-existed at `HEAD` and was
    *repointed*.** The wire name and type are byte-identical before and after
    (`isThreadRoot: Boolean!`, at snapshot `:833` → `:835`), so it is invisible
    in the breaking-changes list, but the backing column is not: the old
    resolver derived it from the loaded `thread_id` (`thread_id is None`) and
    `scalars.py::is_thread_root` now derives it from `parent_id`. The
    *definition* also changed meaning under the same name — under `thread`, "no
    thread" meant "in no group"; under `parent` it means "**IS** a root" — and
    the field's docstring says so, because a name that survives a rename is
    exactly where a reader auditing that rename will not look.
  - `reorderSocialMediaLinks(parentId)` is a `strawberry.Maybe[…] = UNSET`
    because an explicit `null` ("reorder the roots") and an omitted argument are
    genuinely different requests, while `groupSocialMediaLinks(parentId)` is a
    plain `ID = null` because there they mean the same thing. Worked example
    added to `docs/STRAWBERRY_MIGRATION.md`.
  - **One loader, `sublink_subtrees`, replaces `thread_members`**: one existence
    probe (`filter(parent_id__in=keys)`) for the whole batch plus one
    `descendants()` CTE per key that has children, so a page costs
    `1 + (rows with children)` queries and never one per tree level (where
    `node.children` — a plain `RelatedManager` — would cost one per level per
    node). The answer is assembled **positionally** from `keys` so a duplicate
    key is answered at its own position, and returned **flat** in depth-first
    order with siblings already in `position` order (`_depth_first` /
    `_sibling_groups`, which bucket on `parent_id` because `position` is a
    *sibling* order that a flat mixed-level sort cannot express).
  - `sublinkCount` and `sublinks` are **two reads of that one fetch**, so the
    badge is structurally incapable of disagreeing with the list it labels; there
    is no second count anywhere in the schema to drift from. `is_publicly_visible`
    is applied in exactly **one** place — `scalars.py::_publicly_visible_subtree`
    — with the extra rule that **a descendant of a suppressed row is itself
    suppressed** (a hidden middle node stays in the tree, so its visible children
    are in the rows but unreachable through `sublinks`; counting them would be
    precisely the badge/list disagreement the design exists to prevent). The
    pass relies on the loader's depth-first ordering, which is why the loader
    sorts the way it does.

- **Resolvers**:
  - `collapseThreads` narrows to `parent__isnull=True` — cheaper than the flat
    column it replaces, not merely differently spelled: both are plain indexed
    null tests, but the old column existed only to *mark membership*, a second
    statement of what `parent` now says structurally.
  - `_event_window`'s correlated `EXISTS` is replaced by
    `_in_window_subtree_roots(bound)`: an **un-correlated** recursive-CTE
    subquery taking `tree_path[1]`, folded in as `pk__in`. A correlated subplan
    re-runs the recursion **per candidate root** (a `Recursive Union` nested
    inside `EXISTS(SubPlan 2)`), so one walk per query instead of one per row is
    the whole difference — and the ORM cannot even express the correlated form
    (`tree_path__contains` is literal-only; `RawSQL` cannot carry an `OuterRef`
    *parameter*). The widening now follows the subtree at any depth; moderation
    stays **root-only**, and the asymmetry is deliberate and documented (a window
    asks "what happened in this window", a moderation gate asks "may this be
    shown", and under a tree the distance between the moderated row and the row
    that happened is no longer bounded by one hop).
  - 🔴 **`tree_filter` was evaluated and rejected** — it restricts the base
    table *before* the recursion, so filtering to the in-window rows deletes an
    out-of-window root from the CTE, the recursion cannot reach below it, each
    orphan becomes a root of its own truncated tree, `tree_path[1]` returns the
    descendant rather than the conversation's root, and the widening silently
    stops working. Verified against a 3-level tree whose root and child are both
    out of window. The subquery is unfiltered by design (no status, no
    moderation excludes, no `incident_id`); everything that decides
    *visibility* stays on the outer query, which is the one that returns rows.
  - The library's implicit depth-first `ORDER BY tree_ordering` is suppressed by
    `.distinct()` — **not** by `.order_by()`, which the compiler ignores because it
    tests the ordering for *truthiness* and a bare `.order_by()` leaves the tuple
    empty. The suppression is also **conditional**: the compiler's
    `skip_tree_fields` is `query.distinct and query.subquery` (or a summary
    annotation), so it applies here precisely because this *is* a subquery — and
    `.distinct()` is the dedup it needs anyway.

## Incident: `publicSocialMediaLinks` — `lastWeekOnly` excludes today (`displayTodayInLastWeek`)

- **What**: `lastWeekOnly` had only a LOWER bound (`last_week_start` = local
  midnight six days ago), so "the last week" silently included the day in
  progress — a view that changes under the reader, whose newest day is
  half-formed next to six completed ones, and whose `totalCount` moves hourly.
  The window now closes at local midnight **this morning**, so the default range
  is the half-open `[six days ago 00:00, today 00:00)` = the last six
  **completed** calendar days. The new argument
  `displayTodayInLastWeek: Boolean! = false` drops the upper bound and restores
  the inclusive seven-day window; it is inert when `lastWeekOnly` is `false`.
  - `_event_window_before(bound, *, collapse)` is the upper-bound counterpart of
    `_event_window`: `occurred_at < bound`, and under `collapse_threads` widened
    to the whole subtree as `occurred_at < bound & ~Q(pk__in=_in_window_subtree_roots(bound))`
    — so a card is **excluded** when the ROOT or any descendant at any depth
    occurred at/after the cut. Reusing `_in_window_subtree_roots` verbatim is
    what keeps the two ends of the window the same question, and it is the only
    correct reading for a collapsed card: grouping elects the EARLIEST link as
    root, so "root yesterday, follow-up today" is the ordinary shape, and since
    the collapsed surface renders the ROOT, a root-only upper bound would carry
    a today reply inside a view that claims to be the previous days. The plain
    `occurred_at__lt` conjunct is kept on the collapsed path as deliberate
    symmetry with `_event_window`'s explicit `occurred_at__gte` (documented as
    such in the docstring, since `~Q(pk__in=…)` already covers the root itself).
  - The cut is **calendar** midnight, deliberately NOT `service_day_start`'s
    03:00 rollover: a calendar-day view opening at 03:00 would hide this
    morning's first three hours from the reader, and the day headers the same
    page draws are calendar days. `timezone.now()` is captured once and shared
    by both bounds so a request landing at 23:59:59.9 cannot straddle a
    midnight. Applied **before** `totalCount`, so page and count agree.
  - No model change, no migration. `_event_window` and
    `_in_window_subtree_roots` are byte-identical; ordering, cursor and
    `align_page_to_day` untouched. One `datetime.combine(now.date(), time.min)`
    per request replaces the two independent `timezone.now()` calls the window
    block used to make.
  - **Verification**: `manage.py test incident --keepdb` → **238 OK** (was 232;
    6 new flat tests, and the 3 pre-existing tests whose fixtures relied on today
    being inside the window were re-pointed at the inclusive form rather than
    having their expectations rewritten, so both behaviours stay covered).
    `manage.py test tests.incident.<9 feed/tree modules> --keepdb` → **225 OK**
    (5 new nested tests, 2 of them pinned on the emitted SQL). The SDL snapshot

    - The pre-existing 30 `tests/incident/` modules that do `import pytest` are

    - `align_page_to_day` composes with the exclusion rather than fighting it:

    - `_feed_capture` counts `WITH RECURSIVE` per statement, so a collapsed

## [2026-10-01] incident: migration 0031 aborted on threaded rows — deferred-FK events vs. the trailing DDL

- **Symptom**: staging (`postgres-staging`, still at `incident.0030`) served the
  tree code and every link query failed with
  `column incident_socialmedialink.position does not exist`.
- **Root cause**: the staging pod's startup `migrate` aborted with
  `psycopg2.errors.ObjectInUse: cannot ALTER TABLE "incident_socialmedialink"
  because it has pending trigger events` (read from the pod log). `parent` and
  `thread` are `DEFERRABLE INITIALLY DEFERRED` (Django's PostgreSQL default), so
  the re-parenting `UPDATE` inside the `RunPython` queues constraint-trigger
  events that only fire at COMMIT; the next operation is DDL
  (`RemoveField(thread)` forward, `RemoveField(position)` in reverse), which
  PostgreSQL refuses while those events are pending. The dev database held
  **zero** thread members when 0031 was authored, so nothing was ever queued
  there — the migration only ever worked on databases with nothing to convert,
  and staging's three threaded rows exposed it. `makemigrations --check` and a
  fresh-DB `migrate` cannot see this; only applying the migration to a database
  that already has threaded rows can.
- **Fix**: each half of `0031`'s `RunPython` now ends with
  `flush_deferred_constraints` (`SET CONSTRAINTS ALL IMMEDIATE`), which fires the
  queued checks and empties the queue before the DDL. It is a no-op on databases
  that already applied 0031 (schema operations and ranking are unchanged), so
  editing the already-applied migration is safe here.
- **Tests**: new `ExecutorRoundTripTests` replays 0031 through the
  `MigrationExecutor` over a genuinely threaded row (reverse → insert → forward →
  reverse → forward). Verified to fail with the exact `ObjectInUse` error before
  the flush and pass after; it is a `TestCase` (not `TransactionTestCase`) so the
  whole round trip rolls back and cannot strip migration-seeded rows from the
  shared test DB.
- **Staging**: stays at `0030` until the fixed commit is deployed (CI image +
  GitOps bump), at which point the pod's startup `migrate` applies 0031. The
  current staging image contains the un-fixed file, so re-running `migrate`
  inside it would fail the same way.
