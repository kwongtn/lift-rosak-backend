## Incident: scheduled ingestion task, backfill command and tests (Phase 1, part 2)

- **What**:
  - `incident/tasks.py`: `ingest_official_posts` (`crontab(minute="*/5")` with
    `{"expires": 240, "time_limit": 180}` — `expires` sits under the 5-minute period
    so a wedged run is never re-dispatched on top of itself). It returns
    `{"skipped": "disabled"}` without `OFFICIAL_POST_INGESTION_ENABLED` and
    `{"skipped": "no_token"}` without a bearer token, so the beat entry is safe to
    deploy before the X API tier is provisioned. `get_system_author()` is resolved
    once per run and left to raise; each handle fetches with
    `since_id=latest_post_id(handle)`; a per-handle `OfficialPostFetchError` is logged
    and the remaining handles still run. One structured log line per handle carries
    `handle, fetched, created, skipped, duplicate_urls, duration_ms`, and the task
    returns the totals dict. **No `self.retry` and no sleeps** — retries must be
    bounded (see `infinite_retry_on_error` in the APPS.md traps table) and an
    unbounded loop pins a worker.
  - `incident/management/commands/ingest_official_posts.py`: the manual backfill over
    the same service. `--handle` (repeatable), `--since` / `--until` (whole UTC days,
    `--until D` = `D 23:59:59.999999Z`; mutually exclusive with the `since_id` fast
    path, so a windowed run never passes `since_id`), `--limit`, `--fixture`,
    `--dry-run`. One summary line per handle; a fetch or ingest failure becomes a
    `CommandError` (non-zero exit) rather than a traceback; `--fixture` is rejected
    with a date window, and a multi-handle run is rejected as ambiguous only when the
    handle came from settings rather than an explicit `--handle`. `--since` with a
    window the API cannot reach warns honestly about the ~3,200-post ceiling
    (distinguishing "fetched nothing" from "oldest post is newer than your window").
  - `ingest_posts` gains an additive keyword-only `dry_run: bool = False`: it counts
    would-be creations through the same code path and returns `created_ids=()`
    without writing.
- **Tests**: 5 new classes in `incident/tests.py` — `OfficialPostFixtureParsingTests`,
  `OfficialPostIngestTests`, `OfficialPostTaskGuardTests`, `OfficialPostBoundedFetchTests`
  and `IngestOfficialPostsCommandTests`. No network (the HTTP layer is patched at
  `official_posts._get_json`), no Telegram, `TestCase` + `unittest.mock` per repo
  convention. Two repo traps needed handling: `DEBUG=True` swaps the default cache for
  `DummyCache`, so the user-id-caching test needs `@override_settings` with a real
  `locmem` backend or it asserts nothing; and `USE_TZ = False` with
  `TIME_ZONE = "Asia/Kuala_Lumpur"` means aware datetimes are stored naive-local, so
  `posted_at` comparisons go through `timezone.make_naive(...)`.
- **Verification**: `ruff check . --fix` + `ruff format .` clean; `manage.py check` clean;
  `makemigrations --check --dry-run` → "No changes detected"; `manage.py test incident
  --keepdb` → 69 tests OK; **full suite 323 tests OK**. Dry-run proven inert against
  the dev DB: `ingest_official_posts --fixture
  incident/fixtures/x_user_tweets_sample.json --dry-run` reported `fetched=2 created=2`
  with `SocialMediaLink.objects.count()` 40 before **and** after. A nonexistent
  fixture exits 1 with `CommandError: fixture /nonexistent.json could not be read
  (FileNotFoundError)`.
- **Commit**: this commit (`feat(incident): scheduled official-post ingestion task,
  backfill command and tests`).

## Incident: official-post Phase 2 — admin notification, reply approval, and the public-feed gate

- **What**:
  - `telegram_provider/utils.py`: `send_message` gains an additive keyword-only
    `return_log: bool = False`. When set, it stamps the sent PTB `Message` into
    `log.payload["message"]` (new `_outbound_message_payload()` — `message_id` plus
    `chat.id`, the same block `views.TelegramInbound` records for inbound rows and the
    same keys `handlers.submit_link` matches on) and returns `(message, log)`. The
    default path is untouched: bare `Message` return, no payload write, no PTB kwarg
    leak. Retry/backoff/rate-limit behaviour is unchanged; failure and dead-letter
    still return `None` in both modes. This one flag is what makes any outbound
    announcement resolvable by a later reply, with **no handler change**.
  - `incident/tasks.py`: `_notify_created_links(handle, summary.created_ids)` runs
    after each handle's `ingest_posts` and sends one message per entry in
    `created_ids` — so a re-scrape is silent, because a skipped/duplicate post has no
    id in that tuple. The whole pass is skipped when `TELEGRAM_ADMIN_CHAT_ID` is blank
    (nothing constructed, nothing sent). Message content: handle, the post's own time
    (`_format_posted_at`, degrades to `unknown` on null), the **verbatim** `description`
    body, a permalink and a `{FRONTEND_BASE_URL}/console/insiden/links` deep link —
    **never** `raw_payload`. Every dynamic value goes through `_telegram_escape`.
    Truncation (`TELEGRAM_MAX_TEXT_LENGTH = 4096`, `TRUNCATION_MARKER = "…[truncated]"`)
    escapes first, then cuts, so a post full of `&` cannot push the message over
    Telegram's hard limit; a pathological negative budget drops the body and keeps
    the actionable links. On success, `TelegramSocialMediaLinkLog(social_media_link=link,
    telegram_log=log)` records the join — the existing `/approve` handler then resolves
    the reply and flips the row to `LIVE`. Per-link failure isolation: a raising send is
    caught and logged (type name + message only), a dead-lettered send returns `None`,
    and the loop continues either way. A new per-handle `notified` counter is added to
    the result dict and the structured log line; it is deliberately **not** in
    `INGEST_COUNTERS`, so it reports per handle without rolling into the task's
    top-level totals. No `self.retry`, no sleeps — a rejected message is never retried
    anyway, because the 5-minute beat only re-runs the *fetch*.
  - `rosak/settings.py`: new `FRONTEND_BASE_URL` (env override, default
    `https://community.mlptf.org.my`) beside the Telegram block. There is no frontend
    config in the API today, so this is the one place that knows the SPA's address.
  - `incident/schema/resolvers.py`: `get_public_social_media_links` now applies exactly
    `exclude(is_automated=True, status=SocialMediaLinkStatus.PENDING_APPROVAL)`, after
    the `status` filter and **before** `total_count`, so the count and the page agree
    with what is published. Scoped to `is_automated` on purpose: a *community* link
    awaiting approval keeps today's behaviour and still surfaces with its pending icon.
    No new enum member, no new GraphQL field, no mutation change.
- **Decisions worth keeping**:
  - **No stamping on the default path.** `payload["message"]` is written *only* under
    `return_log=True`, so every existing caller of `send_message` is byte-identical —
    the audit row is still created, just not annotated. A new send path that wants reply
    resolution asks for the log.
  - **`html.escape(..., quote=False)`**, deviating from `handlers.py` which uses the
    default. The Bot API documents only `&lt;` `&gt;` `&amp;` as entities that must be
    produced, and every value escaped here is either element text or a double-quoted
    `href` this code generates — none can contain a raw `"`. Escaping quotes as well
    would only risk a rejected send. Asserted by a test.
  - **`getattr` defaults in `_outbound_message_payload`** so a partial/`None` PTB
    message can never raise out of the audit write itself; the stamp is applied before
    `log.asave()` (no `update_fields`) so the row persists it.
  - **Two module-level cross-app imports** added to `incident/tasks.py`
    (`telegram_provider.utils.send_message`,
    `telegram_provider.models.TelegramSocialMediaLinkLog`). Spec §2.7 sanctions the
    `incident → telegram_provider` direction, and `tach.yml` does not exist in this repo
    to be violated. This does make the app pair two-way at the app level —
    `telegram_provider/handlers.py` already imported `incident.services` — but **not** a
    module-level import cycle: `telegram_provider.utils` and `.models` never reach
    `incident.tasks`.
- **Tests** (16 new, all network-free): `incident/tests.py` — `OfficialPostNotificationTests`

## Incident: official-post Phase 3 — dataset export command

- **What**: `incident/management/commands/export_official_posts.py` (the read side of the
  pipeline Phases 1–2 wrote).
  - Rows: `SocialMediaLink.objects.filter(is_automated=True)`, narrowed by `--handle`
    (`source_handle`, repeatable, `@` tolerated like the ingest command), `--since` /
    `--until` (inclusive **UTC calendar days** over `posted_at`, matching the ingest
    command's own window semantics) and `--format jsonl|csv` (default `jsonl`).
    Ordered `posted_at` asc, `post_id` asc, then `id` — the `id` tiebreak is additive over
    the spec's two keys and is what makes acceptance criterion 9 (same input → same bytes)
    a guarantee rather than luck, since two rows can share a null `posted_at` *and* a null
    `post_id`. Nulls sort last on both keys, so rows with no known post time trail the
    archive instead of interleaving with it.
  - Columns are the HuggingFace dataset schema in a fixed order — `post_id`, `posted_at`,
    `handle`, `text`, `permalink`, plus `raw_payload` under `--include-raw`. Mapping:
    `post_id ← post_id`, `posted_at ← row.posted_at.isoformat()` (`None` stays `None`),
    `handle ← source_handle`, `text ← description` **verbatim**, `permalink ← url`.
  - JSONL is one `json.dumps(record, ensure_ascii=False)` per line. CSV is a plain
    stdlib `csv.writer` (no bespoke escaping) with the header always written, even for an
    empty export; a structured cell (`raw_payload`) is JSON-encoded inline with
    `sort_keys=True` so the same row always produces the same bytes.
  - Streaming: rows come out of `.only(...)` + `.iterator(chunk_size=500)` — a server-side
    cursor, never a full-table list. `_row_fields()` adds `raw_payload` to the SELECT only
    when it is actually exported, so the large JSON blob is not read just to be dropped.
    `--push-to-hub` is the single documented exception: `Dataset.from_dict` wants the whole
    record set, so that path materialises it once and reuses the list for the file write.
  - `--output -` (default) writes rows to stdout and the summary line to **stderr**, so
    `export_official_posts | jq` works; a path writes that file in utf-8 (`newline=""` per
    the csv docs) and the summary goes to stdout. `--dry-run` prints the exact row count and
    writes nothing at all: no file, no rows, no hub push.
  - `--push-to-hub REPO_ID` lazy-imports `datasets` **inside** the flag's path and converts a
    missing package into an actionable `CommandError` ("`--push-to-hub requires the
    'datasets' package…`"), so an install that never pushes neither hard-depends on nor pays
    for the Hub client — `pyproject.toml` is deliberately unchanged. The token is read from
    `os.environ.get("HF_TOKEN")`, passed straight to `push_to_hub`, and never logged,
    printed or written into the dataset. `private=True` is unconditional: tweet content
    redistributed on the Hub is outside X's terms, so a bare invocation can never publish.
    An `OSError` opening `--output` becomes a `CommandError` (non-zero exit) rather than a
    traceback, matching the ingest command's treatment of a bad fixture path.
- **Decisions worth keeping**:
  - **`--handle` is repeatable** (a strict superset of the spec's single-handle usage line)
    so it filters the queryset once instead of iterating per handle, and so passing it twice
    narrows instead of silently taking the last value.
  - **The summary line moves to stderr whenever rows go to stdout.** Otherwise the default
    `--output -` would splice a `key=value` line into a pipeable JSONL/CSV stream, and no
    downstream `jq`/`csvkit` would survive it.
  - **`posted_at` is exported as the stored column's own ISO-8601 value** — which, under
    `USE_TZ = False`, is a naive **local** wall time. Recorded in `MISTAKES.md` as a trap:
    the instant is right, the offset is missing, and re-interpreting the value would shift
    it twice. The `--since`/`--until` bounds stay aware so the *window* is genuinely a UTC
    day regardless of storage.
  - **Stable ordering needed a third key.** `posted_at` and `post_id` are both nullable, so
    criterion 9 is only satisfiable with a total order; `id` closes it.
- **Tests** (28 new, all offline, `TestCase` + `unittest.mock`): `ExportOfficialPostsCommandTests`
  (23) — exact column mapping incl. key order and verbatim text, `posted_at` ISO-8601 and the
  `null` case, `posted_at` order beating a disagreeing `post_id`, the `post_id` tiebreak, a
  byte-identical second run, `--since`/`--until`/`--handle` narrowing (plus `@handle`),
  a UTC-day-vs-local-day window boundary, community rows provably absent, a
  `nosuchaccount` empty export, CSV escaping of commas/quotes/newlines parsed back with
  `csv.reader`, a header on an empty CSV, JSONL validity, `--include-raw` toggling the
  column in both formats, JSON-encoding a raw blob into a CSV cell, `_row_fields` not
  selecting `raw_payload`, the stdout/stderr split, three `--dry-run` shapes, the
  generator-not-a-list streaming guard, and four refusals (unknown `--format`, malformed
  date, reversed window, unwritable destination). `ExportOfficialPostsHubPushTests` (5) —
  `from_dict` receiving the expected column dict and `push_to_hub(repo_id, token=…,
  private=True)`, the token absent from the output, the raw column reaching the dataset, a
  push coexisting with a file write, an actionable `CommandError` when `datasets` is
  absent, and `--dry-run` never pushing.
  - The `datasets` seam is `mock.patch.dict(sys.modules, {"datasets": module})` for the
    happy path and `{"datasets": None}` for the failure path — CPython raises
    `ModuleNotFoundError` (an `ImportError`) for a `None` module entry instead of searching
    the filesystem, so the negative test is hermetic whether or not the package is
    installed.
