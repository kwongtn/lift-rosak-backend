## Incident: `publicSocialMediaLinks` — `lastWeekOnly` + `alignPageToDay`

- **What**: two optional arguments on the root `publicSocialMediaLinks` query,
  inferred from the resolver signature (no `schema.py` edit), for the frontend's
  collapsed "Last Week" section.
  - `incident/schema/resolvers.py`: new module-level pure helper
    `last_week_start(now)` = local midnight six days before `now`
    (`datetime.combine((now - timedelta(days=6)).date(), time.min)`; naive-local
    like `service_day_start`). `get_public_social_media_links` gains
    `last_week_only: bool = False` — filters `created >= last_week_start(now)`
    alongside `current_service_day_only`, before `total_count` — and
    `align_page_to_day: bool = False`.
  - `align_page_to_day` (complete-day pages, **no cap**): after the existing
    `first + 1` lookahead fetch, if the lookahead shares the page's last local
    calendar day, the lookahead plus every remaining row of that day is appended
    via `queryset.filter(created__date=<day>, keyset-after(lookahead))`, so the
    page may exceed `first` (a whole day lands together). `endCursor` = the new
    last row; `hasNextPage` = an `.aexists()` keyset probe after it. A lookahead
    on a different day (or none) leaves the page byte-identical to before.
    `total_count` stays the full filtered-set size, cursor- and
    alignment-independent. Docstring documents both flags; the connection type
    shape (`SocialMediaLinkConnection`/edge/pageInfo) is untouched.
  - `rosak/tests/snapshots/schema.graphql`: one line regenerated (the two new
    args) so the schema snapshot gate stays green.
  - Tests (`incident/tests.py`): new `PublicFeedLastWeekAndDayAlignTests`
    (8 tests) — the exact 00:00 six-days-ago boundary is included while 23:59
    seven days ago and much older rows are not; `alignPageToDay=false` still
    returns exactly `first`; alignment completes a 3-row day at `first=2`
    (page exceeds `first`, `hasNextPage=true`, `endCursor` = last day-A row) and
    the follow-up `after=endCursor` returns the older day; a 5-row final day
    returns whole with `hasNextPage=false`; a page already ending on a day
    boundary is untouched; a final page smaller than `first` is returned whole;
    `lastWeekOnly` + `alignPageToDay` combine; `totalCount` respects the window
    and ignores alignment. Rows are stamped with `.update(created=…)` after
    create (the `auto_now_add` trap, catalogued in `MISTAKES.md`).
  - Docs: the resolver-arguments paragraph in `docs/components/incident.md`
    documents both flags and their semantics.

## Incident: `SocialMediaLink.occurred_at` — an explicit event datetime

- **What**: a submitted link previously displayed and ordered by its
  **submission** time, so an operator post captured 40 minutes after it was
  published appeared out of place and a hand-typed event time was impossible.
  `SocialMediaLink` now carries the "when did this happen" instant beside the
  "when did someone report this" one.
  - `incident/models.py`: `occurred_at = models.DateTimeField(default=timezone.now,
    db_index=True)` — **deliberately NOT NULL**, because keyset pagination orders
    by `-occurred_at, -id` and needs a *total* order; a nullable column would
    push `Coalesce` into every filter/`.order_by()` and would sort NULLs last
    (Postgres default) on a DESC scan instead of first. `db_index=True` is
    subsumed by the composite index below (same leading column, btree serves
    both directions) and is kept only because the column is a public contract.
  - `posted_at` is **retained as read-only provider provenance** for
    `manage.py export_official_posts`; the command's docstring now states
    explicitly that it stays on `posted_at` and why (an archive wants the
    provider's own value; swapping the column would change the meaning of every
    previously published export). Ingestion writes **both** columns from the one
    `RawPost.posted_at` in `services/official_posts.py::ingest_posts` — the only
    writer of `SocialMediaLink` on the automated path (beat tick, the manual
    command's live/`--fixture` runs and the X webhook all funnel through it), so
    the pair is drift-proof by construction. Nothing read-modify-writes
    `posted_at`.
  - Write paths:
    - `services/social_links.py::SocialMediaLinkWrite.occurred_at` is
      `dt.datetime | None | _Unset = UNSET` — a private falsy `_Unset` sentinel
      (`repr` = `UNSET`) named after `strawberry.UNSET`. **Submit**: a `datetime`
      is passed to the INSERT, anything else omits the kwarg entirely so the
      column default fires (passing `None` would violate NOT NULL). **Update**:
      three states that mean three different things — `UNSET` leaves the stored
      value alone, a `datetime` sets it, explicit `None` resets it to
      `link.created` ("this happened when it was reported"), the one
      always-present non-null fallback because a community link has no provider
      post time.
    - `services/feed_links.py::submit_feed_link` takes a **flat**
      `occurred_at: dt.datetime | None = None` kwarg instead of a sentinel: that
      path only ever INSERTs, so "omitted" and "explicit null" have exactly one
      meaning. A duplicate canonical URL still short-circuits to the
      pre-existing row and does **not** overwrite its `occurred_at` — the feed
      dedups on canonical URL, so a re-submission is a second report *of the
      same event*.
    - `schema/inputs.py`: `SocialMediaLinkInput.occurred_at: Maybe[dt.datetime | None]
      = strawberry.UNSET` (full tri-state) and `FeedLinkInput.occurred_at:
      Maybe[dt.datetime | None] = strawberry.UNSET` (two states, both meaning
      "let the default fire").
    - `schema/mutations/interactions.py` translates the `Maybe` into the service
      sentinel by hand (`OCCURRED_AT_UNSET if not input.occurred_at else
      input.occurred_at.value`) because Strawberry's `Some.__bool__` is always
      True — an omitted field and `Some(None)` are not distinguishable that way.
  - `schema/scalars.py`: `occurred_at → occurredAt: DateTime!` on
    `SocialMediaLinkScalar` (non-null, naive local, serialised with no offset).
- **Migration**: `incident/migrations/0030_socialmedialink_occurred_at_socialmedialink_thread_and_more.py`,
  operations in order — `AddField occurred_at`, `AddField thread`,
  `RunPython(backfill_occurred_at, revert_occurred_at_to_created)`, `AddIndex`
  — so the btree is populated from final values instead of churned by the
  UPDATE. Forward `occurred_at = Coalesce("posted_at", "created")` in a **single
  SQL statement**; reverse `occurred_at = F("created")` (deliberately lossy-but-
  safe: there is no way to recover which rows had a `posted_at` from
  `occurred_at` alone, and re-deriving the coalesce in reverse would
  reintroduce the shift for rows deliberately reset to `created`). Neither half
  touches `posted_at`. The composite index is
  `socialmedialink_occurred_idx` on `("-occurred_at", "-id")` — `id` has to be in
  the index because it is the tie-break that makes the order total.
- **Why a raw SQL `COALESCE` and not a Python loop**: with `USE_TZ = False` +
  `TIME_ZONE = "Asia/Kuala_Lumpur"` every stored datetime is already naive
  **local** wall time, so the two columns are in the same frame and the backfill
  is a byte copy. A `for link in …: link.occurred_at = …; bulk_update(…)` loop
  would round-trip each value through the field adapter and perform exactly the
  conversion the choice avoids, shifting every row by +08:00 — invisible at the
  UI's minute precision, surfacing only as links landing in the wrong calendar
  day against the service-day window. See `MISTAKES.md` 2026-09-26 (the original
  `posted_at` trap) and the 2026-09-30 entry added for the backfill.
- **Tests**: `tests/incident/test_social_link_occurred_at_write.py` (21) — the
  submit/update/mutation tri-state contract including "explicit null resets to
  `created`" and "omitted leaves it alone"; `tests/incident/test_social_link_occurred_at_backfill.py`
  (9) — drives `backfill_occurred_at` / `revert_occurred_at_to_created` directly
  against real rows, pinning `COALESCE(posted_at, created)`, the `created`
  reverse and the depth-1 thread invariant;
  `tests/incident/test_official_post_occurred_at.py` (7) — ingestion, the
  webhook path and the export staying on `posted_at`, with the stored values
  pinned by literal.

## Incident: every social-link ordering, window and cursor moved to `occurred_at`

- **What**: ordering is part of the feature, not a cosmetic extra — a page that
  *renders* `occurredAt` but *sorts* on `created` puts a backdated report at the
  top of a day it does not belong to.
  - `get_public_social_media_links` (`schema/resolvers.py`): order
    `-occurred_at, -id`; `current_service_day_only` and `last_week_only` filter
    `occurred_at__gte`; `align_page_to_day` compares `occurred_at.date()` for
    the same-day lookahead and builds its half-open naive-local day range on
    `occurred_at` (a `__date` cast could not use the index); the keyset predicate
    and `encode_keyset_cursor(link.occurred_at, link.id)` follow.
  - `get_social_media_links` (the console queue): order `-occurred_at, -id`.
    **⚠️ Intentional breaking GraphQL argument rename** — `createdAfter` /
    `createdBefore` → `occurredAfter` / `occurredBefore`, both inclusive and both
    windowing on the same column the sort uses. The old names are **not**
    aliased, so a stale client gets a validation error ("Unknown argument")
    rather than a silent filter on the wrong column.
  - `batch_load_incident_links` (`schema/loaders.py`) and the nested
    `CalendarIncidentScalar.links(first, after)` field both moved to
    `-occurred_at, -id`, so a per-incident card list and a feed page cannot
    disagree about which link is newest, and the cursor the nested field mints
    matches the ordering that reads it.
  - `schema/keyset.py`: the helpers stay shared but are now explicitly
    **field-agnostic** — `encode_keyset_cursor(ts, row_id)` /
    `decode_keyset_cursor(cursor)` carry no column name, and the module docstring
    records both consumers (`SocialMediaLink` surfaces on `occurred_at`,
    `get_line_status_reports` on `LineStatusReport.created`) plus the hazard that
    a cursor minted for one column is happily accepted by a consumer ordering on
    another.
- **Tests**: `tests/incident/test_social_link_feed_ordering.py` (16) — every
  fixture deliberately *disagrees* `created` and `occurred_at` so an
  implementation still ordering on `created` cannot pass by accident; the
  pagination tests walk the whole result set so a keyset that skips or repeats a
  row is caught. Covers feed order, keyset round-trip, what a pre-change cursor
  does now, both windows, `alignPageToDay`, `collapseThreads` and the console
  queue.
- Existing fixtures in `incident/tests.py` (`PublicFeedContractTests._link`,
  `PublicFeedLastWeekAndDayAlignTests._link`) now stamp **both** columns —
  `created` is `auto_now_add` and can only be written by a later `.update()`, and
  stamping only `created` would leave those tests testing the wrong column.

## Incident: `SocialMediaLink.thread` — thread grouping

- **What**: related links can be grouped into a **thread**, represented by its
  root row.
  - `incident/models.py`: `thread = models.ForeignKey("self", null=True, blank=True,
    default=None, on_delete=models.SET_NULL, related_name="thread_members")`.
    The **invariant** — `thread` ALWAYS points at a root (`link.thread.thread_id
    is None`), so depth is exactly 1 and there are no cycles — is documented on
    the field and enforced by the service, not by a DB constraint (a cross-row
    invariant is not expressible as a row `CHECK`). `on_delete=SET_NULL` is a
    deliberate trade: deleting a root un-threads its members instead of cascade-
    deleting links the operator never asked to delete.
  - `incident/services/social_link_threads.py` (new) owns the invariant and the
    permission. One `transaction.atomic()` block resolves the target root, re-
    points the selection at it and **flattens** any members already hanging off
    a selected link onto the same root — dropping the flatten step is how merging
    two live threads silently produces depth 2, which every reader below then
    mis-reads. Root selection is `ORDER BY occurred_at, id` (the earliest
    *event*, never the earliest submission; `id` only breaks ties), `_resolve_root`
    follows a member up to its root with a cycle guard, and `bulk_update(["thread"])`
    writes only that column so `normalized_url` is not recomputed and the
    `modified` stamp does not move (regrouping is a presentation change and must
    not reshuffle the console's "recently edited" ordering).
    **Permission**: admin → any links; submitter → own links only, checked per
    link on the whole selection **and on the target thread**, and rejected **as a
    unit** (a partial group would leave links threaded to a root the caller does
    not own — a leak with no undo but one link at a time, so there is no "do what
    you can" path). A repeated id is rejected for grouping (a client bug that the
    flatten step would widen) and tolerated for ungrouping (idempotent bulk clear).
    Ungroup is deliberately asymmetric with grouping: ungrouping a root leaves
    its members attached, and ungrouping members one at a time is the intended
    dissolve path — every intermediate state is a legal depth-1 graph.
  - `incident/services/social_link_visibility.py` (new):
    `is_publicly_visible(link)` — "not `HIDDEN` and not (`is_automated` and
    `PENDING_APPROVAL`)" — is the **single source of truth** for the two
    moderation gates. `get_public_social_media_links` keeps its queryset-level
    `.exclude()` pair as its *twin* (a per-row Python filter would not shrink
    `totalCount` or the fetched page, so page and count would stop agreeing); the
    scalar's thread fields filter loader results with the predicate. Any change to
    the rule goes into the shared predicate first. Imported by module path in both
    places, deliberately not re-exported through `incident.services`.
  - `schema/loaders.py`: `batch_load_thread_members` registered as
    `thread_members` in `IncidentContextLoaders` (so `rosak/context.py` needed no
    change — it registers the whole dict). Keyed by root id, `occurred_at, id`
    ASC, **members only** (never the root, which the caller already has). It is
    **not** visibility-filtered: that is the data layer, and duplicating the
    moderation rule here is how a stale copy leaks hidden rows through a thread
    badge. There is deliberately **no** sibling count loader — `threadSize` and
    `threadLinks` both read this one call (the loader caches per request) and
    derive from the same filtered list, so the badge and the list it labels are
    structurally incapable of disagreeing. A raw member-COUNT loader was written
    and removed; its docstring records why.
  - `schema/scalars.py`: `thread_id → threadId: ID` (a free attribute read, null
    exactly on a root), `is_thread_root → isThreadRoot: Boolean!` (derived from
    the already-loaded attribute — true for an unthreaded link too, the degenerate
    one-member thread), `thread_size → threadSize: Int!` (1 + publicly-visible
    members), `thread_links → threadLinks: [SocialMediaLinkScalar!]!`
    (publicly-visible members, oldest first).
  - **Mutations** (`schema/mutations/interactions.py`, both `IsLoggedIn`, both
    service-enforced): `groupSocialMediaLinks(linkIds: [ID!]!, threadId: ID = null):
    GenericMutationReturn!` — omit `threadId` to start a new thread, supply it to
    append to an existing one; the root's id comes back in `id` so the client
    refetches exactly that thread. It is a **dedicated id-only mutation** rather
    than a mode of `updateSocialMediaLink`, because that input is
    replace-not-patch and routing a grouping action through it would strip every
    link's metadata. `ungroupSocialMediaLinks(linkIds: [ID!]!): GenericMutationReturn!`
    — `ok` only; there is no row to name back.
  - **Feed collapse**: `publicSocialMediaLinks(..., collapseThreads: Boolean! = false)`.
    When true the queryset narrows to `thread IS NULL` **before the count and
    before the cursor**, so `totalCount` counts roots and "Showing N of M" stays
    truthful. It is suppressed when `mine` is requested — "My Submitted Links" is
    the caller's own list, where every row they submitted is the row they expect
    to find. **Why roots must be paginated rather than grouped client-side:** under
    `occurred_at` ordering a thread's members are *not* adjacent — an admin can
    group a 09:00 post with an 11:00 post and unrelated links (including members
    of other threads) sit between them, so a member's root may not even be on the
    page. No post-processing of one page can reconstruct that. The accepted
    coupling that follows: **a thread is public iff its root is public**, which is
    why the gates are queryset-level and see the root row; the console surfaces
    `threadSize` so an admin can see what a moderation decision will take with it.
- **Tests**: `tests/incident/test_social_link_threads.py` (27) — root selection by
  `occurred_at` (including the tie-break), appending to an existing thread,
  ownership/admin on both the selection and the target, all-or-nothing rejection,
  duplicate/missing id input validation, the flatten step and the depth-1
  invariant, self-reference, both mutations over the wire and the
  `FeedLinkInput.occurredAt` wiring. `tests/incident/test_social_link_thread_fields.py`
  (29) — the four scalar fields over the real feed: `occurredAt` vs `created`,
  root/unthreaded shapes, `threadSize`/`threadLinks` agreement, the visibility
  gates, loader unit behaviour and per-request batching asserted with
  `CaptureQueriesContext`.
- **Four decisions taken during planning, recorded because a later change will look
  like a bug otherwise**: (1) a **new** field was added rather than repurposing
  `posted_at` — that column stays provider provenance; (2) **ordering** changes,
  not just the displayed value; (3) a thread is a **self-FK root**, not a shared
  key or a separate table; (4) grouping is available to **submitters** on their
  own links as well as to admins.
