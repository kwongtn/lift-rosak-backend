# 2026-09-28

## Incident: X Activity API webhook receiver (primary official-post ingestion path)

- **What**: `GET/POST /webhooks/x-api` — the receiver X actually pushes to, and the
  primary path now that polling is opt-in. It reuses the Phase 1 services rather than
  re-implementing them, so a post arriving by webhook and one arriving by poll produce
  byte-identical rows.
  - `rosak/settings.py`: new `X_API_OAUTH2_CLIENT_SECRET` (preferred) and
    `X_API_SECRET_KEY` (legacy OAuth 1.0 consumer secret) — the webhook signing
    secrets, which are *not* API credentials for calling X. Never logged, echoed,
    rendered into a body, or exposed over GraphQL.
  - `incident/services/x_webhooks.py` (new): `sign_body` (`sha256=<base64 HMAC>` over
    **raw bytes**), `crc_response_token`, `has_signing_secret`,
    `verify_webhook_signature`, `ingest_webhook_payload`, `WebhookIngestResult`.
    - `SIGNATURE_CANDIDATES` pairs each header with its secret
      (`X-Twitter-Webhooks-Signature-OAuth2`×OAuth2, legacy
      `X-Twitter-Webhooks-Signature`×consumer secret) and tries a candidate **only**
      when its secret is configured — comparing against an empty secret would accept
      a signature anyone can compute. `hmac.compare_digest` on UTF-8 bytes both sides,
      so a non-ASCII header cannot turn a 403 into a 500. Header values never logged.
    - CRC is signed with the *preferred* secret only; the legacy header is not tried
      for CRC, because X verifies the answer against exactly one secret.
    - The parsed JSON is never re-serialized to recompute a digest.
    - Handle resolution: `includes.users` username on `payload.author_id` (free, and
      unforgeable — it is inside the signed body) → `resolve_handle_for_user_id(
      author_id or filter.user_id)`. `author_id` beats `filter.user_id` so a reply by
      another account is not misattributed. Unresolvable → counted `unresolved`,
      warned, dropped rather than given an invented permalink. The deprecated AAA
      `tweet_create_events` shape is parsed defensively too.
    - Invariant `ingested + skipped + unresolved == events`, and idempotency is
      structural: redelivery reuses `ingest_posts`, so `(platform, post_id)` holds and
      a redelivery creates nothing and notifies nobody.
  - `incident/services/official_posts.py`: `_tweet_to_raw_post` → **public**
    `tweet_to_raw_post` (both callers updated, no back-compat alias — it is now a
    cross-module contract); new `resolve_handle_for_user_id(user_id)` walks
    `OFFICIAL_POST_HANDLES` against the cached per-handle id, catching a per-handle
    `OfficialPostFetchError` and logging it, and caching **only positive matches** so
    widening `OFFICIAL_POST_HANDLES` needs no cache flush.
  - `incident/views.py` (new): the `x_api_webhook` transport. GET answers the CRC
    (200 / 400 missing token / 503 no secret), POST verifies and ingests (200 counts /
    400 bad JSON / 403 bad signature / 503 misconfigured), anything else 405 with
    `Allow: GET, POST`. Two deliberate non-errors: the master switch off acknowledges
    `{"status": "ignored"}` (an operator decision is not X's fault, and erroring would
    only earn a retry storm) and a non-`post.create` event is acknowledged having done
    nothing. `OfficialPostIngestError` (missing system author) is a 503 so X may
    redeliver instead of the post being dropped; a broker failure on enqueue is logged
    and still 200, because the row is already committed and approvable from the
    console. Plain sync Django, `csrf_exempt` (X sends no CSRF token and cannot be
    given one) — no DRF, no serializer, no content negotiation.
  - `rosak/urls.py`: `path("webhooks/x-api", csrf_exempt(incident_views.x_api_webhook),
    name="x_api_webhook")` inside a new `apps.is_installed("incident")` block.
  - `incident/tasks.py`: new off-beat `notify_official_post_links` task. X requires a
    200 within 10 s, so the Telegram send is never inline; it reuses
    `_notify_created_links("webhook", ids)` — inheriting the
    `TELEGRAM_ADMIN_CHAT_ID`-blank guard, the escaping, the truncation and the
    `TelegramSocialMediaLinkLog` join row that makes reply-`/approve` work — instead of
    duplicating them. `WEBHOOK_HANDLE_LABEL = "webhook"`.
  - `incident/management/commands/x_webhook.py` (new): the operator's lifecycle lever,
    because a URL that merely runs receives nothing. `register URL` / `list` /
    `delete ID` / `revalidate ID` / `subscribe HANDLE...`, `--webhook-id` optional (else
    exactly one registered webhook must exist, else a `CommandError` naming every id —
    guessing would attach subscriptions to the wrong endpoint and stay silent until
    events stop arriving). Uses `settings.X_API_BEARER_TOKEN` (**App-only**, unrelated to
    the signing secrets) in an `Authorization` header only; failures collapse to status
    + the `CrcValidationFailed` / `UrlValidationFailed` title, never the upstream body,
    because a `CommandError` gets pasted into chats. `_resolve_user_id` is imported
    **inside** `_user_id` so the seam is patchable at its source.
  - Tests (`incident/tests.py`): 6 new classes — `XWebhookSigningTests` (RFC 4231 case
    1 as an outside vector, both candidates, wrong-secret/different-bytes rejection,
    no-configured-secret, case-insensitive header, non-ASCII header),
    `XWebhookCrcViewTests`, `XWebhookHandleResolutionTests`,
    `XWebhookDeliveryViewTests` (signed create, redelivery idempotency, OAuth2 header,
    reply with `referenced_tweets`, 400/403/405, master switch off, non-`post.create`,
    AAA shape, unresolvable handle, post with no id, broker outage, two posts in one
    delivery), `NotifyOfficialPostLinksTaskTests`, `XWebhookCommandTests` (every HTTP
    call mocked). Every secret and flag is pinned with explicit `override_settings`:
    the dev env carries *real* X keys, so a test relying on shipped defaults would
    verify against the operator's secret and print it in a failure message. Also fixed
    the pre-existing `test_since_id_start_time_and_end_time_reach_the_request`, which
    asserted an empty bearer token while the dev env now sets a real one.
  - Docs: webhook contract + attribution rules + env/settings matrix + CRC
    troubleshooting in `docs/components/incident.md`; ingress surface, the off-beat
    task and the registry row in `docs/APPS.md`.
- **Verification**: `ruff check . --fix` + `ruff format .` clean; `manage.py check` no
  issues; `makemigrations --check --dry-run` → "No changes detected";
  `manage.py test incident --keepdb` → **180 tests, all passing** (the environment-driven
  bearer-token failure is fixed); full `manage.py test --keepdb` → **440 tests, all
  passing**. Live smoke against the running app: CRC `GET` answered 200 with a token
  matching an independently computed HMAC and did not echo the challenge; a POST with a
  wrong signature and one with no signature both returned 403; a correctly signed
  delivery returned 200. No migration, no model, no GraphQL, no dependency change.
- **Commit**: this commit (`feat(incident): receive X Activity API webhook deliveries`).

## Incident: webhook read `includes` from the wrong level — every real delivery was dropped

- **What**: a live end-to-end delivery found a bug the tests could not see.
  `services/x_webhooks.py::_usernames_by_id` read the `includes.users` expansion from
  the **top level** of the body, but X nests it on the event object:
  `ActivityStreamResponse.data.includes` (confirmed against X's published OpenAPI
  schema, where `data` carries `event_type` / `event_uuid` / `filter` / `includes` /
  `payload` / `tag`). A correctly signed `post.create` delivery therefore resolved no
  handle, fell through to the reverse lookup, and was counted `unresolved` —
  `200 {"events": 1, "ingested": 0, "unresolved": 1}`. The whole ingest path was dead
  in production while the suite was green, because the test helper built the payload
  with a top-level `includes` — the bug was in the fixture *and* the parser, so they
  agreed with each other.
- **Fix**:
  - New `_expansion_containers(payload)` returns the objects an expansion may hang
    off, most-current first: `data` (when it is a dict) then the payload itself.
    `_usernames_by_id` walks them with `setdefault`, so the **nested** entry wins and
    a top-level duplicate for the same id is ignored rather than allowed to shadow
    it. Every shape check stays tolerant — a missing, non-dict or non-list
    `includes`/`users`, or a non-dict user entry, degrades to the reverse lookup
    rather than raising.
  - Audited the other envelope readers: `_create_items`'s `data.payload` and
    `data.filter` are both correct per the same schema (only the expansion nests
    deeper), and no other function touches envelope keys. Commented the distinction
    in place so the next reader does not re-audit it from scratch.
  - Test helper `xaa_post_create_payload` now defaults to the **real** nested
    location (`nested_includes=True`), so the whole existing webhook suite exercises
    the shape X actually sends; `nested_includes=False` + `top_level_includes=True`
    reproduce the defensive fallback, and `top_level_username` supplies a conflicting
    value for the precedence assertion.
- **Regression tests** (`incident/tests.py`, `XWebhookHandleResolutionTests`, +5):
  - `test_the_nested_includes_expansion_resolves_the_handle_with_no_network` — full
    nested payload ingests with `incident.services.x_webhooks.resolve_handle_for_user_id`
    patched to raise, proving zero network.
  - `test_a_top_level_includes_expansion_is_still_accepted`
  - `test_the_nested_includes_wins_over_a_top_level_one` (also asserts the handle
    through the built permalink, not just the lookup table)
  - `test_a_malformed_includes_expansion_is_tolerated` (5 malformed shapes)
  - `test_an_incomplete_user_expansion_is_skipped` (non-dict entry, missing id,
    blank id, `@`-prefixed / padded username)
- **Verification**: `ruff check . --fix` + `ruff format .` clean; `manage.py check` no
  issues; `makemigrations --check --dry-run` → "No changes detected";
  `manage.py test incident --keepdb` → **185 tests, all passing** (was 180); full
  `manage.py test --keepdb` → **445 tests, all passing** (was 440). Live, after
  restarting `app`: a signed POST carrying the nested-`data.includes` payload returned
  `200 {"status": "ok", "events": 1, "ingested": 1, "skipped": 0, "unresolved": 0}` and
  wrote the row with handle `askrapidkl` and the expected permalink; the row was
  deleted and 0 remain for that `post_id` (0 automated rows overall — the 40 rows in
  the dev DB are pre-existing user-submitted links with an empty `source_handle`).
  Bad signature 403, missing signature 403, and the CRC `GET` 200 with a token matching
  an independently computed HMAC all still behave.
- **Docs**: attribution rule now states the real nesting and names
  `_expansion_containers` as the envelope-location seam (`docs/components/incident.md`);
  trap catalogued in `MISTAKES.md`.
- **Commit**: this commit (`fix(incident): read the X includes expansion from data`).

## Incident: official-post polling is now opt-in (webhook path is primary)

- **What**: the scheduled official-post **polling** tick is explicitly opt-in and ships
  OFF, clearing the way for the webhook receiver (separate follow-up) to become the
  primary ingestion path.
  - `rosak/settings.py`: new `OFFICIAL_POST_POLLING_ENABLED` (env
    `OFFICIAL_POST_POLLING_ENABLED`, default `false`). Polling is opt-in; toggling
    requires restarting `celerybeat` because the beat schedule is built at import.
  - `rosak/celery.py`: the `ingest_official_posts` beat entry is factored into an
    importable helper `official_post_polling_entry() -> dict | None` (returns `None`
    when disabled) so the branch is testable with `override_settings`, no module
    reload. The entry is set into `beat_schedule` **only** when the helper returns
    one; the purge entries are untouched. Default-off means the 5-minute poll is not
    scheduled at all.
  - `incident/tasks.py`: `ingest_official_posts` gains a second guard — after the
    master kill-switch (`OFFICIAL_POST_INGESTION_ENABLED`) and before the token
    check, `not settings.OFFICIAL_POST_POLLING_ENABLED` logs one line and returns
    `{"skipped": "polling_disabled"}` (no network, no writes). Order stays: master
    switch → polling flag → token check. No behavior change when polling is enabled.
  - Tests (`incident/tests.py`): every existing test that flips the master flag now
    also sets `OFFICIAL_POST_POLLING_ENABLED=True` (three sites: the no-token guard
    test, the per-handle-failure test, and the `_ingest` helper used by all
    `OfficialPostNotificationTests`) — otherwise they would no-op for the wrong
    reason. New `OfficialPostPollingDisabledTests` proves the task returns
    `{"skipped": "polling_disabled"}` with master on + token set and makes no HTTP
    request / no write; new `OfficialPostPollingEntryTests` proves
    `official_post_polling_entry()` returns `None` off and the exact entry (task
    name, `crontab(minute="*/5")`, `{"expires": 240, "time_limit": 180}`) on.
  - `docs/APPS.md`: the `ingest_official_posts` beat row marked opt-in via
    `OFFICIAL_POST_POLLING_ENABLED` (default off; webhook path is primary).
- **Verification**: `ruff check . --fix` + `ruff format .` clean; `manage.py check`
  no issues; `makemigrations --check --dry-run` → "No changes detected";
  `manage.py test incident --keepdb` → 110 tests (109 OK; the 1 failure is a

## Incident: post text is HTML-entity decoded once, at the ingest boundary

- **What**: X delivers post text with `&amp;` / `&lt;` / `&gt;` / `&quot;` / `&#39;` and
  numeric references still encoded, and ingestion stored them verbatim, so the feed
  rendered `Gangguan laluan utama &amp; penyehjangan` instead of `&`.
  - `incident/services/official_posts.py::tweet_to_raw_post`: `html.unescape` (stdlib)
    applied to the tweet text **exactly once**, in the single mapping shared by the poll,
    `load_fixture_posts` and the webhook parser — so both ingest paths store the
    characters the operator actually published. Docstrings updated to say so:
    `RawPost.text` is "verbatim apart from the decode", and `raw` keeps the encoded
    original. `ingest_posts` is untouched: `title` truncates to `TITLE_MAX_LENGTH` *after*
    decoding and `description` keeps every decoded character.
  - No double decode: `&amp;amp;` stores as `&amp;`, and `raw_payload` is left as the
    provider sent it for export fidelity, so nothing downstream may unescape again. Both
    properties are pinned by tests.
  - Two existing assertions in `incident/tests.py` were comparing the stored
    `description`/`title` against the *encoded* fixture text (`WEBHOOK_POST_TEXT`); they
    now compare against a new `WEBHOOK_POST_TEXT_DECODED` and additionally assert
    `raw_payload["text"]` is still the encoded original.
- **Tests**: new `OfficialPostEntityDecodingTests` (named + numeric refs through
  `tweet_to_raw_post`; a plain `&` untouched; single-decode guard; the fixture loader
  leaves a plain `&` alone; the stored row is decoded while `raw_payload` is not; title
  truncation measures decoded characters) and `XWebhookEntityDecodingTests` (a real
  `post.create` delivery stores decoded text and keeps the encoded payload; an
  already-escaped entity is not decoded twice) — the full webhook payload path.
- **Verification**: `ruff check . --fix` + `ruff format .` clean; `manage.py check` no
  issues; `manage.py test incident --keepdb` → 200 tests OK; full
  `manage.py test --keepdb` → 460 tests OK. No model, migration, schema or dependency
  change; no polling/webhook behaviour change beyond the stored characters.
- **Commit**: this commit (`fix(incident): decode HTML entities once at the ingest
  boundary`).
