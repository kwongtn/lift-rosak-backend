# 2026-09-22

## Incident: PassengerStatus, LineStatusReport, and canonicalized social-link URLs

- **What**: Added the `PassengerStatus` `TextChoices` enum (`NORMAL`, `BUSY`, `CROWDED`,
  `EXTREMELY_CROWDED`, `BACKLOGGED`, `DELAYED`, `DISRUPTED`) and a new `incident.LineStatusReport`
  model — `line` FK→`operation.Line` (`PROTECT`, `related_name="status_reports"`), `stations` M2M,
  `status` `TextChoicesField`, nullable `delay_minutes`, `notes`, `user` FK→`common.User`, and an
  optional `link` FK→`SocialMediaLink` (`SET_NULL`, `related_name="status_reports"`;
  `Meta.ordering=["-created"]`). `SocialMediaLink` gained `normalized_url` (plain indexed
  `CharField`, **not** unique) and a `votes` `GenericRelation`.
- **Why**: The community front page needs a crowd-reported passenger-load signal per line, and a
  stable identity for a shared social post that ignores tracking parameters.
- **How**:
  - `incident/enums.py` — `PassengerStatus` (`f3fb273`).
  - `incident/models.py` — `LineStatusReport`; `SocialMediaLink.normalized_url` recomputed on every
    `save()` (`f3fb273`).
  - `incident/services/urls.py` — `canonicalize_url`: strips tracking params (`fbclid`, `gclid`,
    `igshid`, `si`, `utm_*`, …), lowercases the host, drops the fragment and trailing slash, keeps
    non-default ports; non-http(s) or unparseable input is returned unchanged (`e0884ae`).
  - `incident/migrations/0024_socialmedialink_normalized_url_linestatusreport.py` — adds the column,
    backfills it in 500-row batches (reversible `RunPython`), then creates `LineStatusReport`.
- **Deliberate deviation**: `normalized_url` carries **no** DB unique constraint — legacy rows may
  already share a canonical URL, so a `UNIQUE` would abort the backfill and raise `IntegrityError`
  on Telegram/admin ingestion. Cross-row dedup is enforced in the `submit_feed_link` service.
  Known ceiling: a race between two first-submits can create two rows.
- **Validated**: full suite 303 passed.

## Incident: deterministic line-status consolidation

- **What**: New `incident/services/line_status.py`. `consolidate(entries, scores, *, now,
  window=6h, min_reports=1)` is a pure function: a report linked to a `SocialMediaLink` is weighted
  `1 + max(net_vote, 0)`, an unlinked report `1`; the highest weight wins, ties broken by recency
  then enum severity rank; below `min_reports` it returns `None`. Message:
  `According to N social media entr{y|ies}, this line is X.` `load_line_pulses(line_ids)` is the
  batched async loader — 3 queries flat (reports, one vote aggregate, one link fetch) regardless of
  line count; a line with no recent report maps to `(status=None, message=None, count=0, links=[])`.
- **Why**: The front-page pulse must be deterministic and cheap. Amplification lets corroborated
  posts outweigh a lone tag, while a downvoted post loses influence but never disappears.
- **How**: `incident/services/line_status.py` — `ReportEntry` / `Consolidation` / `LinePulseData`
  dataclasses, `WINDOW_HOURS=6`, `MIN_REPORTS=1`, `_MAX_PULSE_LINKS=5` (`ab7af0e`).
- **Validated**: full suite 303 passed; `tests/incident/test_line_status_consolidation.py` +
  `tests/incident/test_line_status_loader.py`.

## Operation: per-status report breakdown on Line

- **What**: `operation.Line` gained `passengerStatusCounts: [PassengerStatusCount!]!` with the new
  type `PassengerStatusCount { status: PassengerStatus!, count: Int! }`. Every report inside the
  rolling window is grouped by the status it declared; only statuses with `count >= 1` are emitted,
  in `PassengerStatus` declaration order, and the counts sum to `statusReportCount`.
  `Consolidation` / `LinePulseData` now carry the already-computed per-status dict out of
  `consolidate()` → `load_line_pulses()`; winner selection, `passengerStatusCount` and
  `statusReportCount` are unchanged, and the field reuses the existing batched `line_pulse_loader`
  (no N+1).
- **Why**: The frontend's consolidated status pill needs the full "Normal 1 / Busy 2" hover
  breakdown; only the winning status's count (`passengerStatusCount`) was exposed before.
- **How**: `incident/services/line_status.py`, `operation/schema/scalars.py`,
  `operation/schema/loaders.py`, `rosak/tests/snapshots/schema.graphql` (this commit).
- **Validated**: targeted `operation incident rosak --keepdb` 91 tests (3F/1E, all stale-`--keepdb`
  seed failures); fresh-DB full suite 251 tests (4F/5E — the documented telegram-config failures
  plus two pre-existing `SocialMediaLinkTests` context failures). A fresh database clears the stale
  keepdb failures (18 → 9).
- **Live check**: `POST /graphql/` returns `MRT KGL` → `statusReportCount: 3`,
  `passengerStatusCounts: [{BUSY 1}, {CROWDED 2}]`; report-less lines → `[]`.

## Spotting: Firebase credential mount points at the real home path

- **What**: `docker-compose.yml` mounted a literal host path that did not exist, so Docker
  auto-created the missing source as a root-owned empty **directory**; `firebase_admin`'s
  `google.auth` credential load then failed with `IsADirectoryError` when an id token was verified.
  The mount now resolves from `${HOME}/.firebase/…`, `SpottingConfig.ready()` fails fast with
  `ImproperlyConfigured` when `GOOGLE_APPLICATION_CREDENTIALS` is set but is not a file, and
  `.firebase/` was added to `.gitignore`.
- **Why**: `google.auth` reads the credential path only at **request** time (on
  `verify_id_token`), so a bad mount looked like a generic Firebase auth failure rather than a
  boot-time config error.
- **How**: `docker-compose.yml`, `spotting/apps.py`, `.gitignore` (`46cfde5`).
- **Validated**: `manage.py check` clean; id-token verification succeeds against the credential
  mounted from the real path.

## Incident: line-status history covers the whole service day

- **What**: `bucket_hourly` now returns the full 24-hour service-day series (03:00 through 02:00
  next morning) for a line that has at least one report that service day, zero-filling hours
  without reports, instead of stopping at the current hour. A line with no report in the service
  day still returns `[]` — the frontend's "No data" placeholder state is unchanged.
- **Why**: A browser measurement at ~17:00 found only 15 hour labels (`03`–`17`) on the front
  page's "Reports by hour — today" chart; the API was returning a growing prefix of the day, not
  the day's 24 slots.
- **How**: `incident/services/line_status.py` — new `HOURS_IN_SERVICE_DAY=24` constant;
  `bucket_hourly` returns `[]` when no entry falls in `[day_start, now]`, otherwise emits
  `range(HOURS_IN_SERVICE_DAY)` buckets from `day_start`; `load_line_status_history` and
  `get_line_status_history` docstrings corrected (this commit).
- **Validated**: `manage.py check` + `makemigrations --check` clean; live `lineStatusHistory`
  after re-seed — `KTM ETS` (id 10) → **24 buckets** `03:00 … 02:00` (12 non-zero, 51 reports),
  `LRT KJL` (id 4, no reports) → **`[]`**. Full serial suite 255 tests (4F/5E, identical to the
  253-test HEAD baseline's 4F/5E — the documented telegram-config/`SocialMediaLinkTests`
  failures); new `incident/tests.py::LineStatusHistoryTests` passes; the pytest mirror in
  `tests/incident/` was updated (that tree is not collected by `manage.py test`).
