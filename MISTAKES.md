## Traps

### [2026-10-22] operation: a declarative nested filter field looks up its relation by the Python field name

**Problem**: `StationFilter.stationLine` failed on every query that used it, with `Unsupported lookup 'station_line__display_name__icontains'`. That covered the root `stations(filters: {stationLine: ...})` and `calendarIncidents(filters: {stations: {stationLine: ...}})`. The input type was in the schema, so a client could send it. No test did.
**Root Cause**: A declarative nested field (`station_line: Optional["StationLineFilter"]`) filters on the relation named after the Python attribute. The GraphQL name plays no part. `Station` has no `station_line` relation. Django names the reverse relation of `StationLine.station` `stationline`.
**Fix**: `StationFilter.station_line` is a `filter_field` that runs `process_filters(value, queryset, info, f"{prefix}stationline__")`. The public input name and type are unchanged, and the field moves after `DISTINCT` in the SDL (`b8a56ab`, mypy ignore in `b917479`). Tests: `test_stations_filter_by_nested_station_line` (root query) and the `stationLine` cases of `CalendarIncidentWindowAndTagFilterTests`.
**Prevention**: Send every new nested filter input through GraphQL in a test, because the SDL proves nothing about the lookup. Before declaring a nested filter field, check that its Python name is the relation name Django uses (`Model._meta.get_fields()`). If it is not, write a `filter_field` with the real prefix.

### [2026-10-22] incident: a nested filter on a to-many relation joins, ignores prefixes and breaks NOT

**Problem**: Using one model's filter inside another model's filter went wrong in four ways:

- A declarative nested filter joins, so a row repeats once per matching related row. On the dev DB `calendarIncidents(filters: {lines: {displayName: {iContains: "LRT"}}})` returned 173 rows for 138 incidents, and `stations: {line: {id: "4"}}` returned 109 rows for 69 incidents.
- Running the nested filter on the incident queryset with a prefix (`process_filters(value, queryset, info, "stations__")`) breaks every `filter_field` inside it. A `filter_field` ignores the prefix and builds its lookup on the queryset's own model. `stations: {location: {...}}` failed with `Cannot resolve keyword 'location' into field`.
- A `pk IN` subquery built from the related model's reverse accessor (`values("incidents")`) holds NULL for related rows with no incident. `NOT (pk IN (..., NULL))` is never true, so `NOT: {lines: ...}` would drop every row.
- The root-level nested filters still join. `stations(filters: {line: ...})`, `stations(filters: {stationLine: ...})` and `assets(filters: {station: ...})` return a station once per matching row (dev: 264 rows for 198 stations) unless the client sends `DISTINCT: true`.

**Root Cause**: strawberry-django applies a nested filter as a join on the outer queryset. A custom `filter_field` takes its model from the queryset, not from the prefix. SQL `NOT IN` is false when the list holds a NULL.
**Fix**: `_tagged_with` in `incident/schema/filters.py` runs the nested filter on `Line` or `Station` itself with no prefix. It then matches incidents with `pk IN` over the many-to-many through table (`CalendarIncident_lines`, `CalendarIncident_stations`), whose columns are never NULL (`4d30b6b`). An empty nested filter is no filter. The root-level filters are unchanged. Tests cover `location`, `stationLine`, an incident with two matching rows, `NOT`, null and `{}`.
**Prevention**: Give a nested filter on a to-many relation the `pk IN` shape, built from the related model and its through table. Test two matching related rows, a `filter_field` inside the nested type, and `NOT`. Use `CalendarIncident.lines` and `.stations`, never the unused `Line.calendar_incidents` table (see the 2026-08-24 entry on the duplicate join tables).

### [2026-10-22] incident: `calendarIncidents` has no status gate, so anonymous callers see drafts

**Problem**: The root `calendarIncidents` returns every incident that is not soft-deleted, whatever its `status`, to anonymous callers. That includes `DRAFT` revisions of a `LIVE` incident (`parent_incident` set), `PENDING_APPROVAL` rows and `REJECTED` rows. A work package assumed "only `LIVE`, as before". That was never true. The new `activeNow` and `upcomingWithinDays` filters would have put drafts on the Rider board unless each client sent `status: LIVE`.
**Root Cause**: The query has no gate, and `CalendarIncidentFilter` had no `status` input. The insiden calendar depends on this: it shows drafts and tags them.
**Fix**: _Opt in, root still open._ `CalendarIncidentFilter.status` is an exact match on `CalendarIncidentStatus` (`07c8289`). A server-side gate would break the insiden calendar, so the root is unchanged. A surface that must show only moderator-approved notices sends `status: LIVE`.
**Prevention**: Do not assume a `calendarIncidents` filter narrows by status. The dev DB cannot confirm any of this: all 280 incidents are `DRAFT` and historical, so `status: LIVE`, `activeNow: true` and `upcomingWithinDays` return nothing there. Test in the test DB with a frozen clock (`patch("incident.schema.filters.timezone.now")`, which patches `django.utils.timezone.now` for the whole block).

### [2026-10-22] rosak: a schema change fails the full suite until the SDL snapshot is regenerated in the same commit

**Problem**: All five packages changed the GraphQL schema. The coupling to `rosak/tests/snapshots/schema.graphql` is easy to miss, and one work-package brief did not mention it. `test_schema_snapshot_matches_committed_baseline` fails until the file equals `str(schema)`. Two cases surprise people:

- Turning a declarative filter field into a `filter_field` moves it after `AND`, `OR`, `NOT` and `DISTINCT` in the printed SDL. The name and type are unchanged, but the snapshot differs (`stationLine`, `b8a56ab`). A pure reorder is not a breaking change.
- A removed or retyped field is breaking by graphql-core's definition. `test_no_breaking_changes_detected` compares the live schema with the SDL committed at `HEAD` and fails until the change is named in `EXPECTED_ACCEPTED_BREAKING_CHANGES` and the pinned count is raised (16 entries now). An added input field needs no entry.

**Root Cause**: The snapshot is a second copy of the schema that a person must refresh, and the failure shows only in the full suite. The printed order is the declarative fields, then `AND`, `OR`, `NOT` and `DISTINCT`, then the `filter_field` methods.
**Fix**: Each package regenerated the file in the same commit as its schema change. Generate it in the container and write it from the host shell, so the file keeps your ownership: `docker compose exec -T app python -c 'import os, django; os.environ.setdefault("DJANGO_SETTINGS_MODULE", "rosak.settings"); django.setup(); from rosak.schema import schema; print(str(schema))' 2>/dev/null > new.graphql`. Diff `new.graphql` against the snapshot, then copy it over `rosak/tests/snapshots/schema.graphql`. Stderr carries a Telegram warning, so drop it.
**Prevention**: Put the regenerate step in every schema work package and read the diff. A removal is a decision that needs an allowlist entry and a reason in `rosak/tests/test_schema_snapshot.py` (see the `Asset.stations` entry below). Earlier occurrence: 2026-09-12, under Fixed.

### [2026-10-22] operation: converting a `choices=` field to `TextChoicesField` turns bad rows into read-time crashes

**Problem**: `Asset.status` was a `CharField(choices=...)`, which stores anything. A `TextChoicesField` raises `ValidationError` on save and on every read of a value outside the enum, and it reads `""` as `None`. The conversion migration is an `AlterField` with no SQL change, so a production row such as `ACTIVE`, or a blank one, would crash each request that loads it (`assets`, `stations { assets }`, the admin list), and a blank would fail `AssetStatus!`. A test fixture hit the same wall: `reporting/tests.py` stored `status="ACTIVE"`.
**Root Cause**: `django-choices-field` validates on read and `CharField` does not. A migration that changes no SQL says nothing about the rows it makes unreadable. The dev DB has no assets, so it could not show the problem. `HistoricalAsset` uses the same field, so its rows count too.
**Fix**: Migration `0019` begins with a reversible `RunPython` guard. It reads `Asset` and `HistoricalAsset` through the models as they stood at `0018`, where `status` is a plain `CharField`, and raises `ValueError` naming each table, the bad values and their counts. It rewrites nothing. It spells the allowed values out, so a later enum rename cannot change what the migration accepts (`3b2b949`). It ran for real on a throwaway Postgres database: it failed while bad rows existed and applied after they were fixed. `0019` was edited in place, although applied migrations are never edited, because it had never left the branch and the guard changes no schema state. If `0019` is deployed from a commit that predates the guard, the guard needs its own migration. On deploy, `SELECT status, count(*) FROM operation_asset GROUP BY status;` shows the rows the guard would refuse.
**Prevention**: Before converting a choices field, check production data and grep the fixtures for values outside the enum. Put the check in a `RunPython` that runs before the `AlterField` and reads through the historical models, because the new field would raise on the very rows you look for. To unit-test such a function without migrating the test database, take the apps from `MigrationLoader(None).project_state(("operation", "0018_line_telegram_channel_id_not_unique")).apps` and write the bad rows with raw SQL, because the live model refuses to store them. Build that state inside the test: attributes set in `setUpTestData` are deep-copied per test. Pinned by `AssetStatusMigrationGuardTests`.

### [2026-10-22] incident: history bucketing reads the stored clock as local time and needs an exclusive day end

**Problem**: Two traps in `incident/services/line_status.py`:

- `bucket_hourly` and `bucket_week_profile` read the hour and the weekday straight from `created`. That is correct because `created` is naive Kuala Lumpur time (`USE_TZ = False`). If `USE_TZ` is turned on, every slot shifts silently.
- `bucket_hourly` had no upper bound at `day_start + 24h`. That was harmless while a window ended at now. Once `daysAgo` reads a whole past day, a report at exactly the next service day's first instant landed in the hour map, made the day look non-empty, matched none of the 24 slots and produced 24 empty buckets instead of `[]`.

**Root Cause**: `USE_TZ = False` makes the storage frame a convention, so nothing raises when code relies on it (see the 2026-09-26 entry). A bucketing function that clips only at "now" has an open upper edge that a past day exposes.
**Fix**: The read uses `created__lt` for the day end, and `bucket_hourly` ignores an entry at or after `day_start + 24h` (`19db35f`). `DaysAgoHistoryTests.test_bucket_hourly_ignores_the_instant_the_next_service_day_opens` pins it. `WeekProfileBucketingTests.test_use_tz_stays_off_because_slots_read_the_stored_clock_as_local` fails if `USE_TZ` is turned on (`4e1686c`).
**Prevention**: If `USE_TZ` ever flips, localise in both bucketing functions before anything else. Give every window an exclusive end that the query and the pure function agree on, and test the instant that opens the next window.

### [2026-10-22] incident: `raise_service_error` is annotated `-> None`, so a helper that ends in it lacks a return

**Problem**: A value-returning helper that ends in `except IncidentServiceError as exc: raise_service_error(exc)` fails mypy with `Missing return statement`.
**Root Cause**: `raise_service_error` (`incident/schema/mutations/shared.py`) always raises `GraphQLError`, but it is annotated `-> None`, not `-> NoReturn`, so mypy thinks it returns.
**Fix**: In a value-returning helper, raise `GraphQLError` directly, as `_numeric_line_id` does (`5f94ae8`). The annotation is unchanged.
**Prevention**: Call `raise_service_error` only where code after it may be reachable, or raise directly. Annotating it `NoReturn` would fix every caller at once and is not done.

### [2026-10-22] incident: `send_each_for_multicast` reports an FCM outage per token instead of raising

**Problem**: The push task had `autoretry_for=(FirebaseError,)`, and its test mocked `send_each_for_multicast` to raise. On a real outage (503, no connection, 500, 429 or a timeout) the library raises nothing. It returns one `SendResponse` per token, each holding the error. The service counted those as "kept", logged one warning and returned 0. The retry never ran. The cooldown stayed claimed for 30 minutes, which also muted the next MAJOR incident on that line.
**Root Cause**: In `firebase_admin` 7.7, `send_each` catches every `requests` exception per message and returns it. It raises `UnknownError` only when its thread pool fails. A test that mocks a raise passes while the bug is present.
**Fix**: After each chunk, the service raises `exceptions.UnavailableError` when nothing in the chunk was delivered and a response holds one of `TRANSIENT_ERRORS` (`UnavailableError`, `InternalError`, `ResourceExhaustedError`, `DeadlineExceededError`). Any raise first deletes this run's cooldown claims, so each Celery retry finds the keys free (`4d66938`). `INVALID_ARGUMENT` can mean a bad token or a bad payload. A token is deleted for it only when another message in the same chunk was delivered, because every message in a chunk has one payload. A failure beside a delivered message is logged, not retried, and a retry after a multi-chunk send re-sends chunks that already went out. Both limits carry a `# shortcut:` comment in `push.py`. The retry test returns per-token `UnavailableError` responses (no raise) through `notify_push_subscribers.apply()` and asserts four sends and released claims.
**Prevention**: Read what the library returns before trusting `autoretry_for`, and mock that shape. Release a cooldown claimed with `cache.add` on every failure path, or each retry finds the key taken and sends nothing. Test a retry with `task.apply()`: eager mode runs the retries synchronously, while calling the task directly re-raises without retrying. Queue the task with a lambda or a `def` under `transaction.on_commit(..., robust=True)`, because its error path logs `__qualname__` and a `functools.partial` has none.

### [2026-10-22] incident: `registerPushToken` meets three database behaviours at its trust boundary

**Problem**: Any logged-in user can call `registerPushToken`, so its limits decide how far the table, and every later fan-out, can grow. Three behaviours shaped them:

- The unique btree index on `PushSubscription.token` refuses a row over 2704 bytes with a raw `OperationalError` (`index row size N exceeds btree version 4 maximum 2704`), which reaches the client as a server error. The specified 4096-character cap could never be stored.
- `update_or_create` writes the auto-updated fields, and `TimeStampedModel.save` adds `modified`, so `modified` changes on every re-register.
- Django 5.2 drops an integer past the bigint range from a `pk__in` list without an error, so such a line id shows up as missing, not as a `DataError`.

**Root Cause**: Postgres caps an indexed value by size, not by the length a form allows. `modified` is stamped on every save. The ORM prunes IN members that no row can match.
**Fix**: A token is 1 to 2048 ASCII characters (`MAX_TOKEN_LENGTH`; ASCII keeps characters equal to bytes, and FCM web tokens are about 150 to 200 characters). Each account keeps at most 20 tokens (`MAX_TOKENS_PER_USER`): registering past that deletes the account's least recently registered ones, ordered by `-modified, -pk`, so the `modified` bump is what keeps a live browser's row. `lineIds` holds at most 100 distinct ids (`MAX_LINE_IDS`), and an out-of-range id is reported as an unknown line (`4d66938`). Tests: `test_register_stores_a_max_length_token_under_the_unique_index`, `test_registering_past_the_per_user_cap_evicts_the_stalest_token`, `test_register_rejects_unknown_or_non_numeric_line_ids`.
**Prevention**: Cap an indexed text column in bytes at the trust boundary, and test with random characters, because repeated characters compress and hide the limit. Bound what one account can register. Do not expect an id filter to raise for a value the column cannot hold.

### [2026-10-22] incident: `calendarIncidentsBySeverityCount` MONTH was a running total, and DAY fails at 278 days

**Problem**: Two defects in one resolver:

- `MONTH` compared month numbers with no year bound, so every row was a running total that reset each January. It counted every status. It also left out incidents that start in the window and end after it, and months after today. A test with one incident per status saw `5` for a February where only the `LIVE` one, `1`, should count.
- `DAY` builds six conditional aggregates per day (three severities, long and short term). Postgres refuses more than 1,664 select-list entries, so a window of 278 days or more with at least one matching incident fails with a `GraphQLError` (`target lists can have at most 1664 entries`). `DAY` also leaves out an incident that ends after `endDate`.

**Root Cause**: `MONTH` compared per-month numbers instead of grouping. `DAY` pays one aggregate per bucket, so the statement grows with the range.
**Fix**: _MONTH fixed, DAY open._ `MONTH` is one `GROUP BY` on the (year, month) of `start_datetime` and the severity, over `LIVE` incidents that started in `[startDate, endDate]`, so each incident counts once, in its start month (`9832a3d`). The bounds are exact dates, so a bound inside a month gives that month a partial count (`1e72161`). `DAY` only gained the `LIVE` filter. Tests: `TestSeverityCountBuckets` (five tests, which fail on the old code). For long ranges use `MONTH`. A `GROUP BY` rewrite of `DAY` is not done.
**Prevention**: Bucket with one `GROUP BY` on the bucket key, never with one aggregate per bucket, and filter `status` once. Test a window across a year boundary, every non-`LIVE` status and an incident that spans months. The dev DB has no `LIVE` incidents, so the aggregate returns `[]` there. Verify in the test DB. No frontend code calls the aggregate yet, so the new `MONTH` meaning is unconfirmed.

### [2026-10-22] common: offset paging over a non-unique sort key skips and repeats rows

**Problem**: Paging `medias` ordered by `created` skipped some photos and repeated others. Photos tie on `created` (26 pairs on the dev DB share a millisecond), and Postgres may order a tie differently for each `LIMIT`/`OFFSET`. A walk of the dev feed at 24 per page returned 2,439 rows with only 2,438 distinct ids. `EventOrder` (the `events` list in `spotting`, offset pagination, keys `id`, `spotting_date` and `created`) has the same defect and is not fixed. On the dev DB, 50-row pages over the first 3,000 events ordered by `spotting_date DESC` returned 3,000 rows with 2,486 distinct ids, and 521 ids of the canonical first 3,000 never appeared. The same walk ordered by `created DESC` returned 3,000 distinct ids, so `created` ties are rare on that data, but nothing prevents them. The web app pages `events` by both keys with `pagination: { limit, offset }`. `spotting.queries.ts` sends `order: { spottingDate: DESC }`, and `profile.queries.ts` sends `order: { created: DESC }`. Only the `spottingDate` listing is measured to skip and repeat rows.
**Root Cause**: Offset paging is stable only over a total order, and neither `created` nor `spotting_date` is unique. In strawberry-django an `order` argument replaces whatever ordering the type's `get_queryset` set. A tie-break placed only in `get_queryset` therefore vanishes whenever a client sends `order`.
**Fix**: _medias fixed, events open._ `MediaOrder.order`, an object-level order method, calls `process_order(..., skip_object_order_method=True)` and appends `pk`. `MediaType.get_queryset` orders a feed with no `order` argument by `pk` (`7a02ef4`). The public `MediaOrder` input and the schema are unchanged. After the fix the dev walk returned 2,439 distinct ids under three order variants. A feed with no `order` is stable but meaningless, because the `Media` pk is a random UUID. The method uses strawberry-django internals (`process_order`, `skip_object_order_method`, `OrderSequence`), so `pyproject.toml` pins `strawberry-graphql-django` to `>=0.82.1,<0.83.0` and says why (`e5db865`). `MediasFeedPagingTests` is the guard: run it first when moving that range. A custom connection class would be cleaner, but `test_connection_total_count_field` pins `CommonScalars.medias` to `DjangoListConnection[MediaType]`.
**Prevention**: Every offset-paginated list with a non-unique order key needs a unique final key in its order type. Apply the `MediaOrder.order` pattern to `EventOrder`, ideally as one shared helper. `calendarIncidents` is unpaginated and not affected. Test by walking the feed at several page sizes with tied rows and comparing the distinct count.

### [2026-10-22] operation: plural list fields over a single foreign key fail for every row

**Problem**: `Asset.stations: List[Station]` was in the schema, but the model has one foreign key, `station`. Selecting `stations` failed for every asset with `'Asset' object has no attribute 'stations'`. `StationLine.stations` and `StationLine.lines` have the same defect, over the single `station` and `line` foreign keys, and are not fixed.
**Root Cause**: The scalar fields were declared plural by copy, and nothing selected them. No test did, no client did, and the dev DB has no assets.
**Fix**: _Asset fixed, StationLine open._ `Asset.station: Station!` replaces `stations`. The optimizer joins it, so the query count does not grow with the number of assets (`6ac24b8`). Removing a field is a breaking schema change, so `Asset.stations was removed.` is named in `EXPECTED_ACCEPTED_BREAKING_CHANGES` (16 entries now, `EXPECTED_ACCEPTED_BREAKING_CHANGE_COUNT = 16`), and a live-schema pin asserts that `Asset` has `station` and no `stations`. The snapshot is regenerated. An alias was rejected because it would keep a field that can only fail. The web app never selected `Asset.stations`: it reads `Line.stations[].assets`, which is `Station.assets`.
**Prevention**: Select a new plural field in a test before building on it. Before removing a field, grep `rosak_firebase/src` and the `wt/*` worktrees for its name. Fixing `StationLine.stations` and `StationLine.lines` is a breaking change of the same kind: `station: Station!` and `line: Line!`, plus allowlist entries. The web app selects neither.

### [2026-10-21] common: the admin claim is a live Firebase call on every anonymous-gated view

**Problem**: `spotting.schema.resolvers.viewer_is_owner_or_admin` backs every anonymous-spotting gate: the profile list and figures, `EventScalar.location`, a photo's `uploader` and `mediaCount`. For a logged-in viewer who is not the row's owner it asks `is_admin_from_user_loader`, which calls `auth.get_user` (a network call, about 100 to 300 ms) once per request; before the profile gate a profile view made no such call. `has_admin_claim` itself still catches only `UserNotFoundError`, but the loader now catches `FirebaseError` (quota, network, unavailable), logs a warning and treats the viewer as non-admin, so an outage no longer fails the profile's figures or `uploader` of a gallery page: admins see the non-admin view until Firebase recovers, and nobody sees hidden data.
**Root Cause**: `FirebaseUser.get_current_user` keeps only the `User` row; the verified token's claims (`key_contents`) are dropped, so nothing in the request context carries the `admin` claim. Reading it from the token instead would be cheaper but weaker: a revoked claim would stay valid for the token's lifetime (up to an hour), where `auth.get_user` sees it at once. Audit round 4 skipped this for that reason.
**Fix**: _Errors fixed, cost still open._ `batch_load_is_admin_from_user` fails closed on `FirebaseError` (F043, tested by `test_a_firebase_error_on_the_admin_check_fails_closed` in `AnonymousPhotoUploaderTests` and `AnonymousSpottingsOnProfileTests`). The per-request cost is not fixed. Either cheaper-but-correct: call the check only when the page holds a hidden row (the profile has an anonymous event, a listed photo is on an anonymous event; the photo loader already does this). Reading the token's claim needs a decision on the revocation window first.
**Prevention**: A per-viewer gate should cost nothing for the viewers and pages it does not affect; an external call in a gate must fail closed.

### [2026-10-21] operation: the dev DB holds `Line.telegram_channel_id` uniqueness as a bare unique index, so name-based `DROP CONSTRAINT` fails

**Problem**: `manage.py migrate` of a plain `AlterField(unique=True -> False)` on `Line.telegram_channel_id` failed on the dev DB with `ProgrammingError: constraint "operation_line_telegram_channel_id_key" of relation "operation_line" does not exist`, while the test DB (built by migrations) applied it fine.
**Root Cause**: Schema drift. Migrations create a UNIQUE **constraint**, but the dev DB (restored from a dump) has only a unique **index** of the same name, and no `_like` index. Django's AlterField emits `ALTER TABLE ... DROP CONSTRAINT <name>`, which cannot drop a bare index. Seen only on this column (`code`/`display_name` are real constraints); production's form is unverified.
**Fix**: `operation/migrations/0018` drops the uniqueness by column through `connection.introspection.get_constraints()`: `DROP INDEX` for an index, `DROP CONSTRAINT` for a constraint, plus the `_like` index (`d0a2dd9`). Run forward, reverse and forward again on the dev DB.
**Prevention**: Before a migration that removes or renames a constraint or index, compare `pg_constraint` / `pg_indexes` on the dev DB with what migrations would build, and drop by column rather than by name when they differ.

### [2026-10-21] common: media tasks re-enqueue themselves forever (`time.sleep(2)`, no cap) when their row is missing

**Problem**: `check_temporary_media_nsfw`, `convert_temporary_media_to_media_task` and `add_width_height_to_media_task` (`common/tasks.py`) treat "row not found" as transient: `time.sleep(2)`, then `apply_async` of themselves with the same kwargs. There is no counter and no cap (`bind=True` but nothing reads `self.request.retries`). A row that never appears (deleted by the `TO_DELETE` purge in `cleanup_temporary_media_task`, a wrong id, a `filename` that never matches `Media.file`) loops forever, and each cycle blocks a worker for 2 s.
**Root Cause**: A "wait for the row" workaround written as an unbounded self-requeue instead of a bounded Celery retry.
**Fix**: _Not fixed._ Replace the sleep-and-requeue with `self.retry(countdown=2, max_retries=N)` (or `apply_async(countdown=2)` with a carried attempt counter) and log or dead-letter at the cap.
**Prevention**: Every task that re-enqueues itself needs an attempt cap and must never `sleep` inside a worker (repo rule: Celery retries are bounded).

### [2026-10-21] common: the NSFW verdict cannot reliably gate publishing — convert and the NSFW check race

**Problem**: `common/signals.py::convert_temporary_media_to_media` dispatches `convert_temporary_media_to_media_task` **and** `check_temporary_media_nsfw` together for every `PENDING` upload from a non-trusted uploader. Convert refuses only `BLOCKED` / `TO_DELETE` / `INVALID_UPLOAD`, so it processes a `PENDING` row without waiting for a verdict and ends by setting `TO_DELETE`; the NSFW task then returns at `status is not PENDING` and never scores the image. Which task wins decides whether `BLOCKED` stops publication. The NSFW task's `CLEARED` branch dispatches convert again, and `cleanup_temporary_media_task` re-drives `PENDING` rows older than 5 minutes into convert regardless of any verdict. Videos skip the NSFW check by design.
**Root Cause**: Moderation sits beside conversion instead of in front of it: `PENDING` is both the state the NSFW task needs to see and a state convert accepts, and no code orders the two tasks.
**Fix**: _Not fixed._ Order them explicitly: NSFW first, convert only from `CLEARED` / `TRUSTED_CLEARED` (videos exempt on purpose), and revisit the cleanup task's `PENDING` re-drive.
**Prevention**: A moderation gate must be the only path to publish. Test that a `BLOCKED` verdict (and a missing verdict for a non-trusted image) leaves no `Media` row.

### [2026-10-20] operation: date-only `lastSpottingDate` cannot order same-day sightings

### [2026-10-01] incident: `tree_path` is a recursive-CTE **annotation**, not a column — five ORM idioms that are correct elsewhere break on it

**Problem**: `django-tree-queries` stores nothing: `tree_path` / `tree_depth` / `tree_ordering` are computed per query by a CTE the library prepends. Consequences:

- **A bare `SocialMediaLink.objects` has no tree fields.** `objects.get(pk=…).tree_path` raises `AttributeError`; add them with `with_tree_fields()` or read them off `ancestors()` / `descendants()`, which add them implicitly.
- **They are gone after `save()` / `refresh_from_db()`**; only the queryset result carried them.
- **`.update()` on a queryset filtered by a tree field breaks** with `no such column: __tree.tree_path` (UPDATE targets the base table, the filter references the CTE alias). Use `filter(pk__in=…)` or `bulk_update`.
- **The CTE identifier `__tree` is library-internal.** `schema/resolvers.py::_in_window_subtree_roots` depends on it via `RawSQL("(__tree.tree_path[1])::bigint")`; an upstream rename surfaces as a `ProgrammingError` on the first collapsed windowed feed, not as an empty list.
- **Only an explicit `.order_by(…)` suppresses the implicit ordering; a bare `.order_by()` does not.** The compiler adds `ORDER BY tree_ordering` under `if not (skip_tree_fields or self.query.order_by)` and `query.order_by` is a tuple, so a bare `.order_by()` leaves it empty (falsy) and the depth-first sort of the whole table on an un-indexable computed array is still added. `.distinct()` is conditional: `skip_tree_fields = (query.distinct and query.subquery) or <any summary annotation>`, so it suppresses tree columns and ordering only in a **subquery**, which is exactly where the window subquery needs it (and why it is also the dedup that subquery wants). An explicit `.order_by(…)` on a tree queryset replaces the depth-first order outright, so it is a semantic choice, not cosmetic.

**Root Cause**: The library is a queryset compiler that rewrites the statement and joins a CTE named `__tree`, not a model mixin that adds columns, so every ORM assumption about columns, aliases and ordering is false here.
**Fix**: _Use, do not fight._ The cycle guard calls `ancestors()` rather than reading `tree_path` off a bare manager; structural writes go through `bulk_update`; `.distinct()` does dedup and ordering suppression in one call. Raw SQL is unavoidable only in the window subquery: the library's `tree_path__contains` lookup is literal-only (`OuterRef("pk")` raises `TypeError`) and `RawSQL` cannot carry an `OuterRef` parameter.
**Prevention**: Confirm the queryset is a `TreeQuerySet` before touching `tree_path`/`tree_depth`; never hand a tree field to `.update()`, `.only()`/`.defer()` or a raw alias list; grep for `__tree` before bumping the library. For "no ordering" use `.distinct()` (in a subquery) and read the compiler before assuming `.order_by()` does it.

### [2026-10-01] incident: `position` is a stored sequence the library does **not** maintain — re-parenting never recomputes it

**Problem**: `OrderableTreeNode` gives `position` a column, default `0` and a `save()` auto-assign of `max(siblings) + 10`, and nothing more. The stored number stops being a sequence when:

- **Two inserts race.** The auto-assign is a non-atomic read-then-write; concurrent inserts can read the same `max()`.
